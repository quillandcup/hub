# SECURITY DEFINER function review

> **Status:** living. **Last reviewed:** 2026-11-23. Review: yearly. Kept up to date with the code; if it is wrong, fix it.

Done 2026-11-21 for the second half of item 3 of "Threat model follow-ups" in `docs/TODO.md` ("is each `SECURITY DEFINER` function correct, and does any build SQL dynamically"), the A03 and A01 rows of `docs/trust/THREAT_MODEL.md`. It goes past the 2026-11-18 review and the guard in `supabase/tests/database/security_guards.test.sql` (PR #1467, described in `docs/trust/RLS_SECURITY.md`, "Security definer functions and the guard"), which prove each callable function has a recognizable caller check and a pinned `search_path`, but not that the check is right, and say nothing about dynamic SQL.

## What was checked, and how

- **Source of truth: production, read-only.** The definitions come from `pg_get_functiondef` on the linked project (`supabase db query --linked`, `select` only), with `prosecdef`, `proconfig` and the grants. The body of every function below hashes the same (`md5(prosrc)`, 54 of 54) as in a local database built from the repo's migrations, so the latest `CREATE OR REPLACE` in `supabase/migrations/` is what is live.
- **Counts (prod, 2026-11-21).** `public` has 211 functions, 101 of them `SECURITY DEFINER`. 54 of those can be executed by `authenticated` (this table), 1 by `anon` (`is_admin()`, also `PUBLIC`), and 47 by neither (triggers, service-role-only helpers: they are not reachable from a signed-in session). No other schema exposed to the API has a callable definer function (`storage`, `vault` and `pgbouncer` hold Supabase's own, none executable by `anon` or `authenticated`). Every one of the 101 pins a `search_path`.
- **Each body was read** for: dynamic SQL (`EXECUTE`, `format`, `query_to_xml`, `quote_*`, `set_config`, `SET ROLE`, string concatenation into a query), where the caller is established (and whether before the first read or write), whether a caller-supplied member id, channel id or course id is trusted, whether rows of other members come back, and whether a write has an ownership check.
- **Advisor** (`supabase db advisors --linked --type security`): 56 findings, all related to this list. 54 `authenticated_security_definer_function_executable` (exactly the 54 rows below) and 1 `anon_security_definer_function_executable` (`is_admin()`) are the functions in the table, each reviewed here. 1 `function_search_path_mutable` was on `member_activities_stamp_sudo()`, an invoker trigger function (not definer, not callable on its own): fixed by `20270874000000_pin_search_path_member_activities_stamp_sudo.sql`.
- **Defaults worth knowing.** Postgres here grants `EXECUTE` on every new function in `public` to `anon`, `authenticated` and `service_role` (default privileges of `postgres` and `supabase_admin`), so a definer function is callable the moment it is created unless its migration revokes it. The 47 non-callable ones each have that revoke. `anon`, `authenticated` and `PUBLIC` have no `CREATE` on `public`.

## Result

- **Dynamic SQL: three functions, all fine.** `member_owned_row_counts(text)` builds a `count(*)` per table with `format('... %I ... %I = %L')`: table and column names come from `pg_constraint`, the member id is quoted as a literal, and an admin or service-role check comes first. `duplicate_course(text)` calls `set_config('app.audit_skip_course', <generated id>, true)`: a fixed key, a value it generates, transaction-local, admin or service role only. `delete_course(text)` (added 2026-11-23, after the counts above) does the same with the course id it was asked to delete, set only after the course is found and checked to be a Hub-owned draft, and reset at the end. No function concatenates a caller value into SQL, switches role, or reads a setting the caller can choose, except `current_acting_as_member_id()` which reads the `x-acting-as` request header and honours it only when it names the caller's own user id and the caller is an admin.
- **Needs fix: none** among the definer functions. One hardening fix shipped for the non-definer trigger function above.
- **Decisions: 3 low-severity items, all settled 2026-11-22** (details in "Decisions"): D1 tightened (`20271005000000_chat_find_or_create_dm_tighten.sql`), D2 left as is on purpose with a guard for new functions, D3 deliberate and consistent with what members were told. None let a caller read or write what they have no right to under the product rules.
- **New guards** (`supabase/tests/database/security_definer_review.test.sql`): every function in `public` pins its `search_path` (definer or not; a `CREATE OR REPLACE` that drops the `SET` clause fails CI); a new `SECURITY DEFINER` function must pin `public, pg_temp` or an empty path (the older ones are on a shrink-only list, see D2); a callable definer function that builds SQL dynamically must be on a reviewed list (3 entries, stale entries fail too); a member cannot list or revoke another member's sign-in sessions; a hostile member id cannot change the query `member_owned_row_counts` builds.

## The table

Columns: **Dyn.** is dynamic SQL; **Path** is the pinned `search_path` (`public`, or `""` with every name schema-qualified); **Check** is how the caller is established. "Admin" means `is_admin()` (role `admin` only), "staff" adds `is_community_manager()`, "own" means a member id compared with `current_member_id()` or a row filtered by it, "service" is `auth.role() = 'service_role'`. Every function here is executable by `authenticated`; `anon` and `PUBLIC` only for `is_admin()`.

## Decisions

- **D1. `chat_find_or_create_dm(p_other_member_id)`: tightened (2026-11-22).** It accepted any row in `members`, including people who are not active, and calling it again set `left_at = NULL` for both people, which put a conversation back in the other person's list after they left it. No message was created, so nothing was delivered and the caller could read nothing new, but the owner decided to close it. Now (`20271005000000_chat_find_or_create_dm_tighten.sql`, same signature and return type):
  - an id that is not a member, or is the caller, still raises `chat_dm: bad_member`;
  - a member whose `status` is not `active` (on hiatus, cancelled or a lead) raises `chat_dm: not_active`. That is the rule the New message picker already applied (`searchDmCandidates`: active, with a Hub login), and on-hiatus and cancelled members cannot sign in, so there was nobody to read the message. It applies to an existing conversation too: the button on their profile now says so instead of opening it;
  - if the other person has left the conversation (`left_at` set on their membership), it is not reopened for them and the caller gets `chat_dm: other_left`. Members have no way to leave a Hub DM in the app ("A direct message is between the two of you", `membership-abilities.ts`), so this only applies to a leave made by staff or data repair; production has no Hub DM at all yet (0 rows with a `dm_key`, read 2026-11-22);
  - the caller's own earlier leave is still undone when they open it again (they asked for it); a pair that nobody left behaves exactly as before: created on first use, found from either side, both in it. If both left, the first caller gets `other_left` too, so staff would have to put someone back first;
  - the two new errors are mapped to plain messages in `src/app/(member)/chat/dm-actions.ts` (the same place that maps `bad_member`). Slack-bridged DMs (`openSlackDm`, `docs/product/SLACK_BRIDGED_CHAT.md`) do not call this function and are unchanged. The function also pins `public, pg_temp`. pgTAP: `chat_find_or_create_dm_tighten.test.sql`.
- **D2. `search_path = public` without `pg_temp`: left as is, on purpose (2026-11-22).** Postgres searches the temporary schema first for tables when `pg_temp` is not named, so a caller who could create a temporary table could shadow a table a definer function reads. That is not reachable here: calls come through PostgREST, which runs no DDL, and `anon`, `authenticated` and `PUBLIC` have no `CREATE` on `public`. Changing the 44 plain `public` pins (45 callable today, 80 definer functions in all, counting trigger and service-role-only ones) is one `ALTER FUNCTION` each but touches functions many tests exercise, for a risk that is theoretical, so the owner decided not to. What changed instead is the rule for new code: a `SECURITY DEFINER` function must pin `SET search_path = public, pg_temp` (or an empty path with every name schema-qualified), enforced by `security_definer_review.test.sql`. The 80 older functions sit on an explicit allow-list in that test that only shrinks: a function fixed or dropped must be removed from it (a stale entry fails), and a new one cannot be added to it without a reviewer noticing the diff. `.claude/rules/migrations.md` says the same.
- **D3. `mentorship_counts()`: deliberate, closed (2026-11-22).** It returns each mentor's id, match count and first and last start dates to every signed-in member, because members cannot read `mentorships` and the Big Sister badge on a profile needs the count. It names no new member, outcome or note (those stay behind `my_mentorships` and `set_mentorship_note`). What members were told was checked in the Privacy page (`src/content/privacy.ts`, "Who can see it": other members see "Your profile as you set it ..., the books and awards you add, and what you post in the channels they are in", and "Not your usage statistics, your IP address or your private notes"), the Security page, the help articles and the Big Sisters page, which says "Big sisters earn a Big Sister badge on their profile that grows as they look after more new members." No page says that matches or mentor counts are private to the mentor and staff, so nothing contradicts the function; the badge and its tier are shown to every member by design. The exact count and dates are a little more than the tier shows, which is not a promise broken, only a detail. The Security page's open item for it is removed.

## Notes (no action)

- **N1. "Signed in" means "has an Auth account that is not banned".** The directory, aliases, profile writing and "ask me about" functions check `auth.uid()` or only the grant, not that the caller is an active member. Access for non-members is closed at Auth (users are created banned and only released while a member is active, `src/lib/auth-provisioning.ts`), so a lapsed member loses new sessions, but a JWT already issued stays valid until it expires. The tables behind these reads are already open to `authenticated` (`member_directory`) or hold only what the member shared.
- **N2. `current_member_id()` falls back to `members.email = jwt email`** when no `user_id` is linked. It is as strong as Supabase Auth's email confirmation (the address in the JWT is the confirmed one), and `user_id` wins when both match. Linking a member's `user_id` removes the dependence.
- **N3. New function defaults.** Because new functions in `public` are callable by `anon` and `authenticated` from the start, the safety net is the pgTAP guard, not the database. Changing the default privileges (`ALTER DEFAULT PRIVILEGES ... REVOKE EXECUTE ... FROM anon, authenticated`) would make a function private until granted, but every RLS helper and RPC would then need an explicit grant and a forgotten one shows up as a runtime "permission denied" in a policy. Not done.
