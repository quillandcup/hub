# Threat model and OWASP Top 10 review

> **Status:** living. **Last reviewed:** 2026-11-23. Review: yearly. Kept up to date with the code; if it is wrong, fix it.

Done 2026-11-17 for the "Threat review" item of the [Supabase production security checklist](https://supabase.com/docs/guides/security/production-checklist) (`docs/checklists/SUPABASE_SECURITY_CHECKLIST.md`). It is a review of the code and configuration in this repository, not a penetration test: nothing was attacked, and production was only read. Where a line says "checked" it names what was read; where it says "not checked" nobody has looked yet. Findings that need work are in `docs/TODO.md`, "Threat model follow-ups".

Public repo: no names, emails or ids here (`.claude/rules/public-repo-hygiene.md`).

## What we protect

| Asset | Why it matters |
|---|---|
| Members' writing (projects, goals, progress, books) | The thing members care about most. Only they, and staff acting through the audited paths, should read it. |
| Member personal data (names, emails, billing status, attendance, Slack content) | Personal data; Slack content is service-role only (`.claude/rules/data-architecture.md`). |
| Staff powers (admin pages, sudo "view as member", imports, flags) | Whoever holds them can read or change anything. |
| Service credentials (Supabase service role, Stripe, Slack, Zoom, Kajabi, Resend, Mux, Google) | Each one is a way around row-level security or into a provider account. Rotation: `docs/runbooks/SECRET_ROTATION.md`. |
| Availability of sign-in and the live prickle pages | Members arrive at the same few minutes. |

## Who might attack, and what they have

| Actor | Starting point |
|---|---|
| Anonymous visitor | The public site, `/login`, landing pages, and every `/api/*` route (the proxy treats all of `/api/` as public; each route must authenticate itself). |
| Signed-in member | A valid session. Wants another member's data, staff powers, or to spam others. |
| Someone who gets hold of a member's link | A magic link, a calendar feed URL, an unsubscribe link, a forwarded email. |
| A compromised account (member, staff, or a Supabase or GitHub account) | The largest blast radius; see A07 and the account items in `docs/checklists/SUPABASE_SECURITY_CHECKLIST.md`. |
| A compromised or malicious provider or dependency | Webhook senders, npm packages, GitHub Actions. |

## Entry points and how each is guarded

Every `src/app/api` route file is classified by credential kind in `tests/lib/api-route-auth.test.ts` (2026-11-18: admin 129, member session 22, provider signature or token 7, internal secret 2, signed token 1, secret URL token 1, OAuth state 1, public on purpose 2; a file with two kinds counts in both). A new route without a recognised check fails that test.

| Entry point | Guard | Checked |
|---|---|---|
| Member and admin pages | The proxy redirects signed-out visitors to `/login`; `/admin` paths are checked in the proxy and again by `requirePermission(...)` / `requireActionPermission(...)` (`.claude/rules/admin-route-protection.md`). | Proxy read. |
| Member data in pages | RLS on every public and bronze table (0 without it, prod); member pages read through `getEffectiveIdentity`. | Prod query. |
| Provider webhooks (Slack, Zoom, Mux, Resend, Google Calendar) | Signature or shared-token check; a deployed build rejects every request while the secret is unset (`src/lib/webhook-auth.ts`, constant-time compare). | Each handler contains a verification step; Calendar, Mux and the Zoom/Slack/Resend paths were read only as far as that. |
| Cron and internal routes (`/api/internal/*`) | `Authorization: Bearer` with `CRON_INTERNAL_SECRET`, refused when unset. | `member-reminders` and `prickle-checkins` check the secret; `changelog-digest` and `lesson-comment-notifications` use `requireAdmin` (the cron secret passes it). Classified by the route test. |
| Public routes with their own credential | Calendar feed (secret token in the URL, looked up server-side, 404 when unknown); unsubscribe (signed token, POST only so scanners cannot unsubscribe anyone); landing opt-in (hidden honeypot field, two rate-limit buckets, the form is looked up in the published page, so it cannot post to a form the page does not show); `media/[id]/[preset]` and course images (private bucket, served only to the caller RLS allows, or to anyone only for assets marked public). | Read. |
| Member-callable API routes | `getCurrentUser()` / `getCoursesCaller()`, then checks for the specific object (course access, message readable); several have rate limits (`src/lib/rate-limit.ts`). | Sampled: `courses/watch`, `courses/playback-tokens`, `chat/*`, `track/events`, `client-errors`. |
| Server fetches of addresses people choose (chat link previews, pictures, book covers) | `src/lib/net/safe-fetch.ts`: http(s) only, ports 80/443, every resolved address must be public, connection pinned to the checked address, redirects followed by hand and re-checked, size and time caps. | Read the design; tests exist. Every caller using it was not enumerated. |
| Rich text shown as HTML (lesson bodies, landing blocks) | Three `dangerouslySetInnerHTML` sites for stored HTML (member lesson page, admin lesson preview, landing `RichHtml`) plus a fourth for JSON-LD (`<` escaped); each site's content goes through `sanitize-html` (`src/lib/courses/sanitize.ts`, `src/lib/landing/sanitize.ts`), at write and again at render. Help, changelog and prickle text are markdown through `react-markdown` without raw HTML. | Allow-lists read line by line and tested against 162 payloads on 2026-11-21 (`tests/lib/html-sanitizers-xss.test.ts`): no bypass. On 2026-11-21 a read-only check of production found every lesson image and link absolute (http(s), plus mailto) and no links or images in landing rich text, so both cleaners now keep a link path on this site only when it is a page (never `/api/`) and a lesson image only when it is http(s) or under our two image routes: staff HTML can no longer make a member's browser request an arbitrary path of ours. The structured link props of landing blocks (buttons, link lists) follow the same link rule (2026-11-22; production had no `/api` link in them), so no link anywhere in landing data can point at `/api`. Counts: the table in `docs/trust/SANITIZER_URL_CHECK.md`. |
| Browser protections | CSP (enforced, with a per-request nonce for scripts and styles; also pictures, framing, connection, frame, media and font sources), and the other headers in `SECURITY_HEADERS` (`next.config.ts`, `src/lib/csp.ts`). | Config read. |
| Sessions | Supabase cookies, `SameSite=Lax`, `Secure` in deployed builds, exact host only. Not HttpOnly (the browser client reads the session for chat and uploads), so an injected script could read it; see `src/content/security.ts` and `docs/TODO.md`, "Make the sign-in cookies HttpOnly". | Read. |

## Abuse cases worth planning for

| Abuse | Today | Gap |
|---|---|---|
| Someone floods sign-in emails for a member's address | 60 s per-address limit, 150/hour overall. | The overall cap is shared: a flood from one source can block everyone else's sign-in for an hour. Monitor; CAPTCHA if it happens. |
| A member scrapes other members' data | RLS limits what a session can read. | No per-user rate limit on read routes in general; the `src/content/security.ts` item "Limits on abuse" already says not every route was reviewed. |
| A member uses chat to reach internal addresses | `safe-fetch`. | Callers are enumerated and guarded by a test (A10). |
| A staff account is taken over | Admin checks, audit log. | MFA is required across the whole Supabase, Vercel and GitHub organizations, and each has more than one owner (owner-reported 2026-11-18; the dashboards are not readable from the CLI, so this is recorded, not verified by a check). In the Hub, a staff account that has a TOTP factor cannot open the admin area, call an admin action or an admin API route on a link or code sign-in alone. A staff account with no factor is not yet required to have one (`staffMfaRequiredFrom` is unset), and a lost device is reset by the owner by hand (`docs/trust/STAFF_MFA.md`). Sudo and imports are powerful, so this stays the highest-impact item until the date is set. |
| A leaked calendar feed or unsubscribe URL | Feed token can be replaced with "Generate new link"; unsubscribe can only turn emails off. | Feed URLs can end up in logs of calendar apps and proxies; **Accepted (owner, 2026-11-18):** the token is in the URL path, so Vercel's own request logs record it, and code cannot turn that off; Sentry events are scrubbed (`src/lib/sentry-scrub.ts`). The feed is read-only and scoped to one member's schedule, and a member can replace the link. Not rotated in bulk: that would break every subscribed calendar. Revisit if the feed ever carries more than a schedule, or if Vercel log access widens. |
| A provider webhook is forged | Verified, secrets required in production. | Secrets must not appear in logs (found and fixed once). |

## Scheduled scanners

Besides CodeQL (a required check on pull requests) and Dependabot, these workflows in `.github/workflows/` run on a timer (UTC; each also has `workflow_dispatch`, so "Run workflow" in the Actions tab starts one). **None is a required check and none can block a merge**, for the reason `audit.yml` gives: a finding with no fix available would stop every unrelated PR. **How you find out:** all but Scorecard fail on a finding (scheduled and manual runs; a pull request run of `audit.yml` or `osv-scan.yml` only reports, so no PR is ever held up) and post to the alerts channel through `SLACK_ALERTS_WEBHOOK_URL` (the same webhook as `audit.yml`; not set means nothing is posted, only a red run). Scorecard grades habits rather than finding faults, so it posts nothing: read its Security tab results now and then. A finding is then fixed, rotated or recorded as accepted in `docs/TODO.md`, "External security scanners: what is left".

| Workflow | What it checks | When | Where the findings are |
|---|---|---|---|
| `audit.yml` | `pnpm audit --prod --audit-level=high`: production dependencies against the npm advisory database. | Mondays 06:17; PRs touching `package.json` or the lockfile | Step log; a post to the alerts channel when it fails |
| `osv-scan.yml` | OSV-Scanner on `pnpm-lock.yaml`: the OSV database, which covers more than npm's advisories. Scheduled and manual runs fail on a vulnerability and post to the alerts channel; on a pull request it only reports. A finding with no fix that is accepted on purpose is listed in `config/osv-scanner.toml` with a reason and an expiry date. | Mondays 06:53; PRs touching the lockfile | Alerts channel; Security tab (code scanning) |
| `openssf-scorecard.yml` | OpenSSF Scorecard: the repo's own habits (pinned actions, token permissions, branch protection, review, update tooling, security policy). Publishes the score, which works because the repo is public. | Tuesdays 06:41; pushes to `main` touching `.github/**` or `config/github.yml` | Security tab |
| `gitleaks.yml` | gitleaks over the **whole git history**, because the repo is public and a secret that was ever committed is out even after a later commit removed it. Output is redacted (`--redact`). | Wednesdays 06:29 | Alerts channel; job log (rule, file, commit). Rotate first; rewriting history is the owner's call (`.claude/rules/public-repo-hygiene.md`) |
| `zap-baseline.yml` | OWASP ZAP **passive** baseline against production (`appUrl` in `config/app.ts`): crawls the public pages and watches headers, cookies and leaked information. No attack payloads, signed in as nobody. There are no preview deploys to aim it at. | Thursdays 07:11 | Alerts channel; the `zap-baseline-report` artifact (no GitHub issue is opened) |

An authenticated or active ZAP scan does not belong in the schedule: run those against a local or demo stack, never production. By hand (not automated): SSL Labs and an HTTP header grade (Mozilla Observatory, securityheaders.com) for the production host, and the Supabase Security and Performance advisors for the schema; what is not done yet is in the `docs/TODO.md` entry above.

## How fast findings are fixed

A finding is a vulnerable dependency (Dependabot alert, `pnpm audit`, OSV-Scanner) or a static analysis alert (CodeQL). The time to fix is counted from the day the finding is first reported against the code we run, and the severity is the one the scanner or advisory gives, raised one level when the vulnerable code is reachable from the production app or the advisory is known to be exploited.

| Severity | Fixed or mitigated within |
|---|---|
| Critical | 10 days |
| High | 30 days |
| Medium | 60 days |
| Low | 90 days (the next quarterly pass at the latest) |

- **Fixed** means the dependency is upgraded or removed, or the code is changed. **Mitigated** means the risk is removed without that (a feature switched off, an input blocked) and the real fix is tracked in `docs/TODO.md`.
- **No fix published.** A finding with no fixed version is not left silent: it is recorded with a reason and an expiry no later than its deadline above in `config/osv-scanner.toml`, so the scheduled run fails again on that date and someone looks at it. A finding in a development-only dependency that never reaches the production build can be recorded the same way, saying so.
- **What is enforced, and what is not.** A new CodeQL alert blocks the merge (a required check). Nothing blocks a pull request that adds a vulnerable dependency (`docs/checklists/OSPS_BASELINE.md`, `OSPS-VM-05.03`), and nothing computes a deadline: the table is a target the maintainers hold themselves to. What makes a missed one visible is that the scheduled scans (`audit.yml` for High and above, `osv-scan.yml` for any) fail and post to the alerts channel every week a finding stays open, and that an accepted finding in `config/osv-scanner.toml` expires. A finding past its deadline that is still open goes in `docs/TODO.md` with the reason and a new date.
- **Dependabot security updates** open the pull request as soon as an advisory lands (`auto-merge.yml` merges only patch and minor ones; a major always waits for a person), so for most findings the time to fix is the time to review and merge.
- **Licenses.** We do not scan dependency licenses, so there is no threshold for them yet (`OSPS-VM-05.05`).
- **Who.** The maintainers. The weekly scanner runs and Dependabot alerts are how a finding reaches them.

## Review again when

A new public route, webhook or provider is added; sign-ups open; a staff capability is added (imports, sudo, flags); a new place renders stored HTML or fetches a user-chosen URL; or after any security incident.
