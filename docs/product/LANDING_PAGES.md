# Landing pages (the page builder)

> **Status:** living. **Last reviewed:** 2026-11-23. Review: yearly. Kept up to date with the code; if it is wrong, fix it.

Status: **slice 1 built**: the model, the editor, the blocks, publishing with history, the public route. The opt-in form block (sign-ups into Kajabi) and the import of Kajabi page exports are built too; the rest is in `docs/TODO.md`, "Landing pages (page builder)".

Kajabi has landing pages with a block editor. The Hub has the same, on [Puck](https://puckeditor.com) (`@puckeditor/core`, MIT): a page is Puck's JSON, `{ content: [...], root: { props } }`, and the same React components render in the editor's canvas and on the public page. We chose an open source editor over writing our own: the drag and drop, the outline, undo and redo, the viewport preview and the iframe canvas are Puck's; the blocks, the shell around it, the model and the rules are ours.

Puck 0.24 peers on React 18 or 19 and was checked against this app's Next 16 and React 19: the editor is a client component, and the public page renders through Puck's `rsc` entry (the package's `react-server` export), which has `Render` and no editor code. Nothing about it needed patching. The editor needs a real browser (it uses dnd-kit and `ResizeObserver`); its tests mock Puck, and the blocks are tested on their own.

## Model

- `landing_pages` (`lpg_`, Tier 2): `slug` (unique among live pages), `title`, `status` (`draft` or `published`), `draft_data`, `published_data`, SEO title and description, a social image (a media asset), `first_published_at`, `published_at`, soft delete (`deleted_at`) `page_type` (`website` or `landing`, see "Website and landing pages") and `kind` (`page` or `template`, fixed for the life of the row; a template is a page kept to start others from and is **never public**: `published(slug)`, the public route and the opt-in relay only ever see `kind = 'page'`). `landing_page_versions` (`lpgv_`): one row per publish, **immutable**: no role may update or delete one (not an admin, not the service role), and a restore copies a version into the draft without touching it.
- **Autosave writes `draft_data` only.** Publishing is a separate, explicit step: `publish_landing_page(id)` copies the draft to `published_data` and writes a version in one transaction (a `SECURITY INVOKER` function, so row-level security applies). `restore_landing_page_version(id)` puts a version into the draft and does not publish it. The editor's "Reset to published" button (`<LifecycleButton action="reset">` (`src/components/LifecycleButton.tsx`), shown only while the draft differs from the published copy) copies `published_data` back into the draft through the repository (`resetDraftToPublished`); nothing goes live and no version is written. Taking a page down sets the status back to `draft`; the published copy and the versions stay.
- **Ids are never in a URL.** Page ids are Tier 2 (`docs/decisions/SHORT_IDS_PLAN.md`), so the public address is `/p/<slug>` and the editor is `/admin/pages/<slug>` (an admin URL counts as exposed). `new`, `templates`, `landing` and `website` are reserved slugs (they are admin routes). The ids travel only between our own client and server actions and are checked at the door (`isLandingPageId`).
- **Row-level security: admins and conversion specialists only** (`is_conversion_specialist()` policies, `20270930000000`; the same two on the site template and its versions below). There is no anon policy and no anon grant. A signed-out visitor never touches the table: the public route reads a published page on the server with the service role (`getServiceRepos().landingPages.published(slug)`), and that one method returns a page only when it is published and not deleted. We chose this over a narrow anon policy because the only way to leak a draft is a bug in one method with a test, not a policy that could be widened by a later migration. Community managers have no access (opt-in rule for new roles).
- **Audit: the intent, not the keystrokes.** The row trigger leaves `draft_data`, `updated_at` and `updated_by` out of its `WHEN`, so autosave writes nothing. Create, publish, unpublish, restore (`restored_at` changes), rename, address and SEO changes, and delete are audited as the admin. The two documents are logged as changed, never with their content (the `redact` argument); the versions hold the content. `supabase/tests/database/landing_pages.test.sql` tests both halves.

## Website and landing pages

Borrowed from Kajabi: **website pages** are the interconnected pages of the site (home, about, ...) that will share one header, footer and style, so a change there applies to all of them; **landing pages** are standalone, single-purpose pages (opt-ins, sales and thank-you pages) styled on their own, so an edit affects only that page. Consistency against flexibility.

- `landing_pages.page_type` (`website` or `landing`, default `landing`) is chosen in New page (a choice between the two, with the templates filtered to the kind) and never changed afterwards; the editor's Details show it read only, and a copy keeps it. A template takes the type of the page it was saved from and is offered only when starting that type. It is separate from `kind`, which says page or template.
- The Pages list is one sheet with three tabs, which are paths (`/admin/pages` Website, `/admin/pages/landing`, `/admin/pages/templates`), each with a count and the same search as before. New page opens on the type of the tab you are on.
- Public routing is unchanged: both types are served at `/p/<slug>`. A website page is framed by the site template (below); a landing page keeps its own header and footer root fields, as before.

## Site template

One header and footer for the whole site, shared by every website page, edited once in the **Design** tab of Pages (`/admin/pages/design`; a path tab like the others, so there is still one Pages entry in the nav).

- **Table.** `landing_site_template` (`lpst_`, Tier 2): one row for the site (`singleton`, unique), `draft_data`, `published_data`, `published_at`, `published_by`. Admin and conversion specialist only; no anon grant. A signed-out visitor never touches it: the public route reads the published copy on the server with the service role (`LandingSiteTemplateRepository.published()`, `src/lib/data/landing-site-template.ts`). The audit trigger leaves the draft out of its `WHEN`, so autosave writes nothing; publishing is one Activity Log entry ("published the site design"), and neither document is ever logged.
- **How it is drafted and published.** The site template has its own draft and published copy, like a page, and it is **never published with a page**. The Design view autosaves to the draft; **Publish site design** is the one step that changes what visitors see, on every published website page at once (the view says so beside the button). So a published page never changes under a visitor without a publish step: a page's own publish does not touch the header, and the site's publish does not touch any page's content. "Reset to published" throws the draft away. The public route renders the published copy (a site never published has no header or footer on website pages); the admin preview and the editor canvas show the draft, so you see the result before publishing. Each publish keeps a version, see "Version history" below.
- **Shape.** `src/lib/landing/site-template.ts` (pure, tested): `{ header: { show, align, mobileMenu, items }, footer: { show, text, links, social } }`. Every reader goes through `normalizeSiteTemplate`, which keeps known keys only, clamps choices, caps text and counts, and cleans links with `safeHref`, because the stored JSON is untrusted. Header-only blocks: **Logo** (a media picture with a description, a link), **Menu** (links), **Call to action** (a button), **Social links** (network and link; shown as a text link named for the network, no logo glyphs yet) and **Sign in** (a link or button to `/login`, the member sign-in page). Each block can be shown on every size, only when there is room (wide) or only when narrow. Publishing is refused with a list of what a visitor would meet broken (a button with no link, a logo with no description, ...).
- **Layout on small screens** uses the named container sizes (`@split`), never viewport breakpoints: the header lives inside the page's `@container`, so the editor's phone preview matches a phone. On a narrow page the menu folds into a native `details` "Menu" disclosure (no script), or wraps, as chosen.
- **Pictures are shown whole.** The header logo (and a landing page's own header logo) uses the `logo` media preset, a largest box that keeps the picture's own shape and transparency (`docs/product/MEDIA_LIBRARY.md`), at a fixed height of 48 px with the width following the picture. The **Image** and **Image and text** blocks use `page_image`, also whole. The Image block has a **Fit** choice: *Whole picture* (the default, and what a block saved before the choice means) or *Fill a wide frame*, a 16:9 crop for a photo that should match its neighbours. Crops stay where they are the point: card pictures, a Section or Hero background, event covers.
- **Frame polish.** The frame is a column at least as tall as the screen and the page takes the slack, so on a short page the footer rests at the bottom with no page colour under it; the admin preview puts its note above and lets the page fill the rest. Every header and footer link has the same box (`block`), so the sign-in link lines up with the menu links.
- **Rendering.** `PageFrame` (`src/components/landing/config.tsx`) takes a `frame` (`{ pageType, site, editing }`); `renderConfigFor(frame)` and `editorConfigFor(frame)` build the configs, and `LandingRender` takes `frame`. `src/components/landing/site-frame.tsx` draws the header and footer (server-safe).
- **In the editor** a website page shows the header at the top and the footer at the bottom of the canvas as fixed regions: not draggable, not selectable, inert (their links don't navigate), each marked "Shared by every website page" with a link to Design (a new tab). They are not edited in the right panel: there is one place to edit them, so there is one source of truth. A website page has no header or footer root fields. The editor loads the site draft when it opens; reload after changing Design to see it.
- **Version history.** One bad publish changes every website page, so the site template keeps what a page keeps. `landing_site_template_versions` (`lpstv_`, Tier 2; admin and conversion specialist only, insert-only: no UPDATE or DELETE grant) holds one row per publish: the published JSON, who and when. **Publish site design** is one database function (`publish_landing_site_template`) that makes the draft the published copy and writes the version in the same transaction, so a published copy never lacks its version. Like page versions, they are never pruned; History lists the last 20 (`LandingSiteTemplateRepository.versions`, names through `editorNames`, never a user id in the browser). The migration kept the copy already live as the first version.
  - **History** (Design tab, `LifecycleButton action="history"`) lists versions with who and when. **Bring back** (`restore_landing_site_template_version`, the registry's confirmation) copies a version into the **draft only**: the published copy and the versions don't change, and nothing goes live until the next publish. **Reset to published** (existing) throws the draft away, with its confirmation. The view says "Draft saved, not published" whenever the draft differs from the published copy (a restored version that equals the live one clears it).
  - **Audit.** Autosave stays unaudited. Restore stamps `restored_at` / `restored_from_version_id` and reset stamps `draft_reset_at` on the row, columns the audit trigger watches, so each is one Activity Log entry ("brought back an earlier version of the site design into its draft", "threw away the draft..."); neither document is ever logged. Usage events: `landing_site_published`, `landing_site_draft_reset`, `landing_site_version_restored`.
- **Not built:** a signed-in user menu. It needs a per-visitor render, and public pages are cached and anonymous by design, so the Sign in block does not know whether someone is signed in (`docs/TODO.md`).


## Settings

The editor's left rail has a **Settings** tab beside Add and AI (`src/app/(admin)/admin/pages/[slug]/SettingsPanel.tsx`; in the rail like the others, so the canvas keeps its width).

- **Style guide** (`src/lib/landing/style.ts`): page background (white, cream, blush, mist, or the theme), primary colour (plum, warm brown, teal, charcoal), button style (solid or outline), button text colour (automatic, white or dark), button size and corners, body font (the app's sans, a modern sans, the brand serif, a classic serif), weight and line height. Every token is a name from a short list, never a free colour or font, and is drawn as a class (`lp-primary-teal`, `lp-bg-cream`, ...) defined once in `src/app/globals.css`; the defaults add no class, so a page without a style is unchanged. A page background brings `landing-light` with it, because the cream and the rest are fixed light colours and dark mode would otherwise put light text on them. The primary colour sets the accent tokens and the solid primary buttons; button size and corners act on every button the builder draws (`lp-btn`). See "Buttons" below for how a button takes its look.
- **Favicon**: a square picture from the media library, 32 to 512 pixels on a side, PNG (ICO, SVG and WebP also pass). The picker refuses a wrong shape with the reason; publishing checks the whole picture again (type and size). Public pages put it in the page's `icons` (`generateMetadata`); with none, the app's own icon stays.
- **Where they come from.** The site's style and favicon live in the site template (edited in Design, published with it). A **website page** has none of its own: its panel only says what it inherits, with a link to Design. A **landing page** follows the site by default ("Use site settings", on) for each of the two groups; turning it off stores the page's own as optional root props (`styleOverride`, `faviconOverrideAssetId`; absent means follow the site, an own empty favicon means none), turning it on removes them. Its own header and footer root fields stay, and take their look from the style.
- **One helper decides.** `resolveStyle(siteStyle, override)` and `resolveFaviconAssetId` (`src/lib/landing/style.ts`) are used by the page frame for the editor canvas and the public page alike: defaults, then the site's tokens, then the page's own tokens where it has them. A token the page doesn't set follows the site, so changing the site later changes every page that doesn't override it. The public page uses the site's *published* style; the editor and the preview use the draft.
- **Design tools** (guides: an outline around every block; grid: twelve columns) are drawn over the canvas only, kept per browser in local storage, never in the page's data and never on the public page (`src/components/landing/design-tools.tsx`).
- **Keyboard shortcuts** opens the app's `?` panel (`useShortcutsPanel`, recorded as `via: editor_settings`).
- **Not here: custom code.** It runs third-party scripts and needs the consent decision first (`docs/TODO.md`, "popups, A/B tests, custom code and tracking pixels"). Not built either: a site-wide button width (full or auto; see `docs/TODO.md`, "Landing pages: site-wide button width and per-button text colour").

### Buttons

Every button the builder draws (Button, Buttons, Link list, the sign-up form, the hero's first button, the banner, a card's button, a finish-line card's button, the header's call to action and sign-in button) comes from `buttonClasses` (`src/components/landing/blocks.tsx`). Its **look** is `inherit` (the default, also for a missing or old value), `solid` or `outline`:

- `inherit` takes the site's button style. It is drawn solid (`lp-btn-inherit`, plus `lp-btn-primary` in the primary colour), and the frame's `lp-btn-style-outline` turns it into an outline in the colour it would have as an outline (`lp-btn-c-plum`, `-light`, `-brown`; `src/app/globals.css`). Changing the site's style, or a landing page's own, changes every such button, in the editor canvas and on the public page alike (`resolveStyle`).
- `solid` and `outline` are the button's own choice and win over the site. A button's colour (plum, light, brown) and shape are its own too; plum is the primary colour, so it follows the site's primary. The site's corners and size act on every button, own look or not.
- The text on a solid primary-colour button is `--lp-on-accent`: white, dark ink on the pale fills the brown, teal and charcoal primaries have in dark mode (automatic), or what the style guide's button text colour says. It applies to solid buttons in the primary colour; a light or brown button keeps its own text colour. An outline button's text is the primary colour.
- **Publish check** (`src/lib/landing/button-contrast.ts`): for the buttons that follow the site, text against the primary colour (solid) or the primary colour against the page background (outline), WCAG AA 4.5 to 1, in light and dark mode when the page follows the theme, light only on a chosen background. A failing site style blocks publishing the site design (`siteTemplateIssues`); a landing page with its own style gets a warning (`checkLandingPage(data, siteStyle)`). The colours are written there as numbers; `tests/lib/landing-button-contrast.test.ts` reads `src/app/globals.css` and fails when they drift. A button with its own look is not checked.
- The style guide's fields show a sample button drawn with the chosen tokens (`ButtonPreview`, `src/components/landing/style-fields.tsx`).

## The editor

`/admin/pages/<slug>` (`src/app/(admin)/admin/pages/[slug]/LandingEditor.tsx`) puts Puck in our shell: our header replaces Puck's (back, title, **Saved / Unsaved changes / Saving…**, device buttons, undo and redo from Puck's history, Details, History, Preview, Publish), and the Puck panels follow the theme through CSS variables in `src/app/globals.css`.

- **Panels** (`[slug]/SidePanels.tsx`): the left rail opens on **Outline**, then **Add**, **AI** and **Settings**. Outline (`OutlinePanel.tsx`, replacing Puck's tree under the same `outline` name) is a Kajabi-style drill-down in one panel, and the level is whatever is selected: nothing selected is the **Page** (Header, the sections, Add section, Footer; a website page's header and footer are links to Design, a landing page's open its root fields); a block with slots (found from the config's slot fields, so new containers and item lists appear on their own) shows its blocks per slot, an Add button limited to what the slot allows (a slot with one allowed type adds it straight away, "Add step"), then its own fields under "Settings"; any other block shows its fields. **Back** selects the parent, a canvas click navigates the panel (and switches to the Outline tab, without opening a hidden panel), and the fields are Puck's own `Puck.Fields` rendered in the left panel, so the right panel stays closed and the canvas keeps its width. Rows reorder by dragging the handle (@dnd-kit, `src/components/writing/SortableList`) or the Move to position menu (keyboard), dispatching Puck's `reorder` in the slot's zone. The header's "Pin fields beside the page" opens the right panel again with the path and Back above the fields; the block level then points there. Add replaces Puck's Blocks tab (a plugin with the same `blocks` name wins) with a search box and the `categories` of the config, collapsed except the first; a search opens every group with a match; items are Puck's `Drawer.Item`, so dragging onto the canvas is unchanged. The header toggles are "Editing panel" and "Pin fields beside the page" (`leftSideBarVisible` and `rightSideBarVisible` are Puck's own state). Done through `plugins`, the `fields` and `puck` overrides and the `ui` prop; no Puck internals.
- **Autosave**: 1.2 s after typing stops, the draft is sent to `saveLandingDraft`; a failed save says so and retries every 5 s; Ctrl/⌘ S saves at once; leaving with unsaved changes asks first. "Changes not published yet" shows on a live page whose draft differs.
- **Publish** opens a dialog: it runs the accessibility checks (below), lists what must be fixed or checked, and only then publishes. The server runs the same checks and refuses on errors. Publishing sends the draft the editor shows, so nothing typed a moment before is left out.
- **Versions**: History lists the last 20 versions, each with **who made it** (a display name through `editorNames`, `src/lib/landing/version-people.ts`; "Someone" when unknown; never a user id), when, what kind it is (published, or the draft kept before an import or a replacement) and its **note**. The note is what the admin typed in the Publish dialog's optional "What changed?" (at most 200 characters, `landing_page_versions.note`, written by `publish_landing_page_with_note` in the same step), or what the app wrote for a draft it kept: "Replaced by the template “X”", "Replaced by the page “Y”", "Replaced by a JSON import", "Replaced by a Kajabi import", and "Saved from the page “Y”" for the publish of Save as template (a name or title, never typed page content). The note lives on the version only: it is never in the Activity Log sentence or the audit rows. Bring back replaces the draft (after a confirm), and the editor reopens on it. It never goes live until published again.
- **Details**: title, address (a warning when the page is live), search title and description, the picture shown when shared.
- **Preview** opens `/admin/pages/<slug>/preview`, the draft rendered as a visitor would see it, under a "Preview of the draft" banner and without the staff shell (no sidebar or top bar: it lives in the `src/app/(admin-bare)` route group, same URL and the same `pages.read` guard); drafts never render on the public route.
- Device preview uses Puck's viewports: desktop is 1280 wide with a free height; Tablet and Phone set an exact width and height from a model (`devices.ts`: the portrait CSS screen, full height, so a phone's browser toolbars take roughly 100 to 150px more than the fold shown). The editor remembers the chosen model and the orientation separately: Tablet landscape swaps the same model's width and height. At a device size the canvas is one screen tall (Puck scales it to fit) and the page scrolls inside it; `FoldMarker.tsx` draws a dashed plum line with "Fold: Npx" at the viewport height inside the canvas iframe (Puck's `iframe` override), and a header button hides it. Blocks lay out with container queries (`@container` on the page frame, named sizes), so the phone preview reflows as a phone does.

## Accessibility checks (`src/lib/landing/a11y.ts`)

Errors stop a publish: an empty page, no page title (an `h1`), a picture with no description (unless marked as decoration), a button or card button with no usable link, a countdown with no date, a video from a host that isn't allowed. Warnings are shown and let through: more than one `h1`, a skipped heading level, vague link text ("click here"), text over a picture with no shade, a video with no title. Contrast cannot fail by construction for the blocks: backgrounds come from a short list of theme colours, each with the text colour that is readable on it (`src/components/landing/theme.ts`), and a picture's text colour follows its shade. Free colours are deliberately not offered. The site's button style is checked for contrast too (see "Buttons" above).

## Pictures and public assets

Pictures come from the media library through the same `MediaPicker` (surface `landing_page`) and are referenced by asset id in props named `*AssetId`. A signed-out visitor is served only assets marked `is_public` (`docs/product/MEDIA_LIBRARY.md`), so **publishing marks every asset the page uses (and its social image) public**, through the admin's own client. A live Coming up tile's event cover is marked public when an admin saves the publicly announced event instead (see "Live data", "Event covers, safely"). Unpublishing does not turn it back (the asset may be used elsewhere); a sweep for assets no page shows is in the TODO. Pictures are requested at the existing presets, which crop; see the TODO for presets that keep the shape.

## Safety

- Rich text is TipTap, stored as HTML in a prop named `html`, and cleaned to an allowlist (`src/lib/landing/sanitize.ts`: paragraphs, headings, lists, quotes, emphasis, links; no images, styles, classes, scripts or handlers) on every save and **again before a public render** (`LandingRender`), whatever the database holds. Never raw HTML.
- A prop named `href` or `url` is a link and goes through `safeHref` (http, https, mailto, a path on this site, an anchor; nothing else) on save, on render, and in the block itself.
- Video accepts only YouTube, Vimeo and Mux player links; the iframe address is built from the extracted video id, with `sandbox`, so a pasted link can't point the frame elsewhere (`parseEmbed`).
- Sections can fade in; it is a CSS animation inside `prefers-reduced-motion: no-preference`.
- The public page sends nothing to an analytics provider and records no visitor. The site's consent banner and Google Analytics rules apply as on every page. There is no anonymous usage event yet (TODO).

## Blocks

Section (background colour or picture with a shade, width, space, optional white card, fade in; holds other blocks), Columns (two or three side-by-side areas that each hold blocks, see below), Text (rich), Heading, Button (solid or outline, pill or rectangle, three colours), Buttons (one to three of those side by side in a row that wraps when the container is narrow, left or centred, small or medium gap; built from the same `buttonClasses` and `safeHref`, a button with no usable link shown disabled; the "Links" group), Image, Image and text (reversible), List (emoji or check markers), Testimonials, Accordion (a folding list: a title that opens to its text, optionally open to start with; native `details`), FAQ (the same look, for questions and answers; also told to search engines, see "Accordion and FAQ"), Countdown (an instant stored in UTC, entered as a wall time in `ORG_TIMEZONE`; at zero: a message, nothing, or zeros; fixed-size cells, no layout shift, read as one labelled timer), Card grid (image or emoji icon, title, description, price, button; up to 2, 3 or 4 columns by the room), Link list, Divider, Spacer, Video. Five ready-made blocks (the "Ready-made" group) save assembling the common ones from Section, Heading, Text and Button; they are static, with no data behind them:

- **Hero**: headline (the page title, `h1`, by default; `h2` when the page already has one), a line under it, a main and an optional second button (`primary` and `secondary`, each `{ label, href }`, so `href` is cleaned wherever it sits), an optional picture behind the words (with a shade, like Section) or beside them (needs a description, or "decoration only"), on a theme colour, left or centred, and "Space above and below" (`padding`: none, small, medium, large; unset means large, the original `py-16 @split:py-24`, so pages saved before the option are unchanged).
- **Steps**: two to five numbered steps (title, short text) under an optional heading; stacked on a narrow page, side by side with room. Titles are `h3` under its own heading and `h2` without one, and the checks count them the same way.
- **Stats**: two to four figures with a label, typed by hand (a description list). Live figures from the Hub are the Outcome numbers block (see "Live data" below).
- **Call-to-action banner**: heading, a line and one button on a theme colour (not the page colour); the button flips to the light style on a dark band.
- **Social icons** (the "Links" group): a row of up to eight round icon links (`SocialLink`: a `network`, which is Instagram, Facebook, YouTube, TikTok, X, LinkedIn, Pinterest, Threads, Email or Website, and a `url` through `safeHref`; `mailto:` is allowed for Email, so a bare address is a publish error), left, centred or right, small, medium or large (the row sets the size, since an item cannot see its block). Each link's accessible name is the network's ("Instagram"), the mark is hidden from screen readers, and a link to another site opens in a new tab with `rel="noopener noreferrer"` (a `mailto:` does not). Colour is the section's text colour (`currentColor`), so it reads on every theme background. **The marks are not the networks' official logos**: they are simple outlines drawn for this project from plain shapes (`src/components/landing/social-marks.tsx`, no third-party artwork or licence), listed in `CUSTOM_DRAWINGS` in `tests/lib/icons.test.ts` as brand marks (`icons.md`: lucide has none). To add a network: a key in `social-networks.ts` and its drawing in `social-marks.tsx`. The site header and footer's own social links are not this block.
- **Pricing**: one to three plans (`PricingPlan` items, limit in `item-limits.ts`) side by side, stacked on a narrow container, each as wide as it needs (container query `@pair`, centred when there are fewer). A plan has a name (an `h3`), a price as typed (never parsed or computed), a billing period or note shown after the price in the same line (so it is read as "$97 per month"), a short description, what is included (one line each), a button (label and link through `safeHref`) and an optional badge ("Most popular"). **Featured** gives the plan a heavier border and shadow and a "Featured plan" label for screen readers, so it does not rest on colour; the badge is words. Colours are the theme's. The publish check makes a button with a label and no link an error (like any button), warns about a link with no label, a "click here" label, more than one featured plan and more than three plans. A button with no usable link is not drawn for a visitor, and is shown disabled while editing.

The "Homepage" group (`src/components/landing/homepage-blocks.tsx`, see "Homepage blocks" below): **Announcement strip**, **Schedule panel**, **Outcome numbers**, **Finisher cards**, **Timeline**, **Week strip**, **Finish-line cards**, **Plan phases**, **Journey map** and **Coming up**. The three about what is on (Announcement strip, Schedule panel, Coming up) are the events module's, contributed to the block registry (`src/modules/events/page-blocks/`, [Page blocks](../architecture/PAGE_BLOCKS.md)); the rest are the pages code's own.

**Columns** (`count` 2 or 3, `gap`, `verticalAlign` top or middle; slots `col1`, `col2`, `col3`; palette group "Layout"): one column on a narrow container, side by side from `@split`. It has no background or text colour, so it inherits the Section around it. Slots are declared in `SLOTS` (`src/components/landing/config.tsx`) and as `slot` fields in the editor config; the migrations, `sanitizeLandingData`, `collectAssetIds` and `checkLandingPage` find nested blocks by their shape, so any slot is covered (tested for Columns inside a Section). Switching three columns to two keeps what was in the third: it is not shown and not checked until switched back (its pictures are still made public on publish). Every slot is rendered with `flow-root` (`SLOT_CLASS` in `blocks.tsx`): Puck draws a slot's dashed outline around the slot's own box, and a first Heading's `my-3` used to collapse out of it, so in the editor the heading touched the outline. Not offered to the AI builder (`AI_BLOCKS`); a page that has one keeps it exactly when the AI revises the page.

**Spacing and width** (`src/lib/landing/layout.ts`, fields in `src/components/landing/layout-fields.tsx`, classes in `theme.ts`). The data shape:
- A Section has `paddingDesktop` and `paddingMobile`, each `{ top, bottom, left, right }` in whole px (0 to 320; defaults 48/48/16/16 desktop, 32/32/16/16 mobile; a missing or invalid side takes the default), and `hideOnDesktop` / `hideOnMobile` booleans. The old `padding` string is gone; a stored Section that still has it shows the defaults (no migration: no real page existed). The field has None/Small/Medium/Large quick picks for top and bottom.
- A block inside a Section may have `span` (width on desktop, 1 to 12) and `spanMobile` (1 to 12); unset or invalid means the full 12. The editor shows the "Width on desktop" and "Width on mobile" fields (a row of twelve squares, "N columns", Reset) only for a block whose parent is a Section (`resolveFields` with `parent`).
- Rendering: the Section's slot is a 12-column grid; `config.tsx` wraps every block in a box that carries `col-span-N @split:col-span-M`, and marks blocks `inline` so Puck's own wrapper does not sit between the box and the grid (the box takes `puck.dragRef`). Spacing is written as `--sp-*` custom properties on the section and read by `pt-[var(--sp-t-m)] @split:pt-[var(--sp-t-d)]` and the like: mobile is the base and the named `split` container size (48rem) switches to desktop, so the editor's phone preview matches a phone. Hiding is `hidden @split:block` (mobile) or `@split:hidden` (desktop); in the editor a hidden section is dimmed instead. Margins of neighbouring blocks no longer collapse inside a Section (grid items), so two stacked headings sit slightly further apart than before.
- The AI builder gets the Section's two paddings as numbers and may set `span`/`spanMobile` on blocks inside a Section (clamped); it is never offered the hide switches. The publish check warns about a section hidden on both sizes. The Kajabi importer builds Sections with `presetPadding`.
- Tests: `tests/lib/landing-layout.test.ts`, `tests/components/landing-layout-fields.test.tsx`, `landing-spacing.test.tsx`, plus the AI and public-render tests.

**Space.** Hero and Outcome numbers have "Space above and below" because each is a band of its own; their default (Hero large, Outcome numbers medium) is what they drew before, so no stored page changes. The other Homepage blocks sit inside a Section, whose own "Space above and below" is the control, and the Announcement strip is a one-line bar, so they have none.

**Reordering items.** Blocks drag on the canvas, and so do the items inside the blocks listed under "Blocks with items" below (they are child blocks in a slot). The two blocks that are still array fields (Coming up events and the Journey map's stages and offers) reorder in the right panel by the grip handle on each item (`docs/TODO.md`, "Landing page editor: a calmer layout...")

**Colours and dark mode.** The page follows the theme (the app's setting in the editor, the visitor's system setting on the public page). Blocks do not write `dark:` classes or slate colours: they use semantic tokens (`bg-page`, `bg-card`, `bg-tile`, `text-ink`, `text-ink-muted`, `border-accent`, `text-accent-ink`, `text-warm`), whose light and dark values are defined once in `src/app/globals.css` (`--lp-*`) and named in `config/tailwind.ts`. Change a value there and every page follows. White, cream, blush and mist bands stay light in dark mode: theme.ts marks them `landing-light`, which sets the light values again inside the band. Plum, cream and the other brand bands are fixed colours and do not change with the theme. `tests/lib/landing-theme-tokens.test.ts` fails on a `dark:` variant or a slate colour in a block.

Text colours in all four follow theme.ts; there is no colour picker. The page frame has optional header (logo, links) and footer (text, links) as root fields.

### Homepage blocks

Built for the public homepage (the "Homepage" template). They are **typed by hand in the editor**, and four of them (the Announcement strip, the Schedule panel, Outcome numbers and Coming up) can instead be **live from the Hub**, see "Live data" below. No Finisher is read from the Hub: THE END is not recorded anywhere yet.

- **Announcement strip** (`text`, `buttonLabel`, `href`, `tone` gold, plum or charcoal): a bar above the page, dark text on gold, a dot that pulses only inside `prefers-reduced-motion: no-preference` (`.landing-pulse` in `src/app/globals.css`, shared with the "live" chip). **Schedule panel** (`title`, `zoneLabel`, `rows`: `time`, `title`, `status` text, `state` live, soon or open, `host`): a light panel with its own colours; the starter puts it beside the pitch, in the second of two Columns in a plum Section. **Outcome numbers** (`padding`, `items`: `value`, `label`, `note`): a full-width white band with a gold top stripe; numbers `text-plum-900` and labels `text-ink` are set on the block, never inherited. **Finisher cards** (`items`: `imageAssetId`, `alt`, `name`, `kind`, `dayOne`, `theEnd`, `linkLabel`, `href`; `more`: `label`, `href`): book-cover shaped photos, a placeholder without one. **Timeline** (`heading`, `intro`, `items`: `when`, `title`, `text`; `closing`). **Week strip** (`subtitle`, up to 7 `items`: `label`, `emoji`, `text`, `note`; two columns on a narrow page). **Finish-line cards** (up to 3 `items`: `title`, `program`, `text`, `durationLabel`, `durationPercent`, `buttonLabel`, `href`) and **Plan phases** (`heading`, `items`: `title`, `text`, shaded light to deeper plum). **Journey map** (`stages`, up to 6: `name`, `helps`, `current`, `note`, `link`: `label`, `href`, and `offers`, up to 4 per stage: `status` open, waitlist, soon or dates, `statusLabel`, `title`, `text`, `buttonLabel`, `href`, `featured`; `compare`: `label`, `href`): a stepper (a column on a narrow page, a row with room) where choosing a stage shows that stage's programs under it in **one attached panel** (a left accent rail on a card, not a card per program). Programs are not equal, so the panel **leads with one**: the featured offer large (status chip, title, text, button), and the stage's other offers as a compact "Also for <stage>" list of rows (name, one line, "See it →" when the offer has a safe link). The featured offer is the first one marked `featured`, else the first (`featuredOfferIndex`, `src/lib/landing/journey.ts`), so a page saved before the option shows its first offer large, no migration needed. A stage with one offer has no list. The same offer may be typed under two stages (the starter puts Best Feedback Friends under Drafting and Revising). Only the featured title is a heading (`h3`; the checks count it the same way); every offer with a button label still needs a usable link to publish. A stage with no offers shows its `note` and optional `link` instead. `current` is the stage chosen when the page opens (the first without one). The interaction is the one client part, `src/components/landing/JourneyTabs.tsx` (the panels are built by the server component and passed in). Every stage's panel is in the server's HTML, so crawlers read all of them. Before hydration, and for ever without JavaScript, the stepper is the plain list with the current stage marked and every panel is shown under its stage's name (nothing is hidden that a visitor could not reach); once hydrated it becomes a `tablist` of real buttons with `tab` / `tabpanel` wiring, roving tabindex, Left/Right/Up/Down/Home/End (focus selects, like the app's `Tabs`), only the selected panel shown, with a plain fade only inside `prefers-reduced-motion: no-preference`. Choosing a stage never navigates and records nothing; it is an element-level pattern, not a page-wide shortcut, so it is not in the shortcut registry. In the editor canvas Puck's selection overlay takes the click, so the canvas shows the stage marked current; edit the other stages' offers in the side panel. A page saved with the old single `offer` under the stepper is migrated (step 1 of `LANDING_MIGRATIONS`) by moving it into the offers of the stage marked current (the first named stage if none), keeping `compare`; and **Coming up** (`heading`, `style`, up to 4 `items`: `kind`, `title`, `when`, `availability`, `status`, `linkLabel`, `href`, and for the other styles `date`, `time`, `imageAssetId`, `soldOut`; `waitlist`; see "Live data").
- **Links are `href`.** Only a prop named `href` is cleaned on save, so a block with several links keeps each in an object (`more`, `offer`, `compare`) or an item, each with its own `href`.
- **Heading levels.** The block's own heading is an `h3` (so the page's section heading above it is the `h2`), and titles under it `h4`; `src/lib/landing/a11y.ts` counts them the same way. Errors: a Finisher photo with no description, a button or link with words and no address. Warnings: vague link words. Blocks with items (below) are the exception: an item title is always an `h3` (an item cannot know whether its block has a heading), and the Steps block heading is the `h2`.
- **Gold** is one fixed brand pair in `config/tailwind.ts` (`gold`, `gold-ink`), like cream and blush: it does not change with the theme, and the dark text on it is about 11:1.
- **Not offered to the AI builder**: none is in `AI_BLOCKS`; adding one is a decision (what the model may invent for a Finisher card is the first question).

### Live data

Four Homepage blocks have a `source`: "Typed in by hand" (`manual`) or "Live from the Hub" (`live`). A block **dropped on a page now starts live** where its point is to be live (the strip, the schedule, and Coming up with retreats, virtual retreats and workshops ticked); Outcome numbers items start typed, because claims such as books published are not recorded anywhere. A block **saved without `source` stays typed** (the resolver acts only on an explicit `live`), so no existing page changes; the typed values are always the fallback. The Homepage starter sets the strip, the schedule, Coming up and its hours and words figures live. Blocks stay presentational and never fetch: the server resolves what they show and hands it to them in a render-only prop named `live` (for Outcome numbers, in the props of each figure).

- **Where it is resolved.** `withLiveData(data)` (`src/lib/landing/live-server.ts`) runs in `src/app/p/[slug]/page.tsx` and in the admin preview, just before `LandingRender`. `resolveLiveBlocks` (`src/lib/landing/live-data.ts`) walks the page (slots and zones included) and asks each data loader (the figures' own in `src/lib/landing/live-stats-loader.ts`, the events module's in `src/modules/events/page-blocks/live-loader.ts`; the contract is `PageDataLoader`) to load what its blocks need once (all figures from one pass, the schedule once, in parallel) and returns a **copy** with `live` set. It is never written back: the editor and the save and publish actions only ever hold the stored page, and a `live` prop found in stored data is dropped before the render. The editor's canvas (a client component) fetches nothing: it shows the typed values and says "live shows on the published page" next to the source switch.
- **Failure.** A loader that throws is caught and logged as a short code (`landing_live_stats_failed`, `landing_live_schedule_failed`, `landing_live_coming_up_failed`, with the error's name and nothing else), and its blocks render their typed values: never an error on a public page. Nothing to show is different from a failure: a figure that is zero stays typed; a schedule with nothing coming up shows the panel's "when nothing is coming up" line, or the strip's `whenNone` choice (nothing, or its typed line).
- **Caching.** Reads use the service-role repositories and are wrapped in `unstable_cache` with `revalidate` 60 and the tag `landing-live` (`LIVE_CACHE_SECONDS`), so the public page costs the database at most one aggregate a minute per set of figures, however many visitors there are. The real "now" is applied after the cache, so "In 12 min" is right within the minute.
- **Privacy.** Counts, sums, public titles and times only; never a name, id, link or per-person row, in the page, a log, analytics or Sentry. Members who hide themselves from Who's coming are counted like everyone (an aggregate does not identify anyone).

**Outcome numbers.** Each item (an `OutcomeNumber` block in the block's `items` slot) is typed or bound to a figure from the registry (`src/lib/landing/live-stats.ts`, `LIVE_STATS`): the item has `source`, `stat` (a select listing every registry label), the typed `value` (also what shows if the live figure is missing) and an optional `label` (empty means the figure's own caption). Live items get a small "live" note (a dot that pulses only when motion is allowed) that the block's "Show a small live note" switch turns off. Figures are floored to two significant digits and never overstate (`friendlyFloor`: 891 shows as "890+", 54,700 as "54,000+", under 100 exactly); a figure of zero is not shown.

| Key | Definition | Caption |
|---|---|---|
| `hours_30d` | Hours written together in prickles: each `prickle_attendance` stay that began in the trailing 30 Eastern days, clipped to its prickle (`least(leave, end) - greatest(join, start)`), summed | hours written together in prickles in the last 30 days |
| `prickles_30d` | Distinct prickles that had at least one stay in those 30 days | prickles with writers in them in the last 30 days |
| `writers_7d` | Distinct members with a stay that began in the trailing 7 Eastern days | writers joined a prickle in the last 7 days |
| `words_30d` | `writing_progress_entries` with `measure` words and `mode` delta, not deleted, by Eastern entry date over 30 days. Never `set_total` (a project's running total) | words logged by members in the Hub in the last 30 days |
| `books_published` | `member_books` rows not deleted and not private (a book a member keeps to themselves is not counted for a public page) whose `published_date` is on or before today (Eastern): a count through `BookRepository.countPublishedOnOrBefore`, never a title or an author. All time, no window. A book a member did not add to the Bookshelf is not known, so it is a floor | books published by members |

Windows are Eastern days (`ORG_TIMEZONE`): "30 days" is today and the 29 Eastern days before it, from Eastern midnight, across a daylight saving change. **Adding a figure** is one entry in `LIVE_STATS` (a label for the editor's list, a caption, the data it `needs` (`stays` or `words`, or a new input in `loadLiveStats` with its repository method) and `compute`), plus a case in `tests/lib/landing-live-stats.test.ts`; the editor's list, the resolver and the block pick it up from the registry.

**Schedule panel.** `source` live lists the next upcoming prickles (`hoursAhead`, default 24, at most 144; `maxRows`, default 5, at most 6; `emptyText` when there are none): the time in `ORG_TIMEZONE` (the weekday too when it is not today; the panel names the zone, "Times in ET", unless a zone note was typed), the title cleaned like the Events page (`cleanEventTitle`) and with a calendar's "w/ Name" host marker removed, and a chip only where it tells something: **Live** with a pulsing dot (running, green; the dot pulses only inside `prefers-reduced-motion: no-preference`) and **In N min** (starts within 60 minutes, gold). Every other row has no chip, because the same chip on most rows says nothing; type an `openLabel` (pale teal) only if you want one. What is true of every session goes once in `footer`, a line under the whole list ("Camera optional. Chat optional. Everyone is welcome." in the starter); `rowNote` still puts a line under each row that has no host line, for the rare case it differs. Which prickles appear: all upcoming ones, the same set the members' Upcoming list starts from (running or starting inside the window, not yet ended), whatever their type or flags; `announced_publicly` is not consulted (it means worth listing as an event), and the Event type (an event's schedule) is left out by the repository. Nothing yet narrows the list to drop-in sessions (`docs/TODO.md`). There is **no joiner or attendee count per prickle**: the only number is "N writing now" on a running prickle, shown when N is 2 or more (else "Live"), taken from `loadLiveRoom` (members and guests in the Zoom room, hidden or not; no names leave that call). `hostStyle` is "none" (default) or "experience": `experiencedHostText` (default "An experienced host, sure to make you feel at home") under the row when the host has held 100 or more past prickles (`EXPERIENCED_HOST_PRICKLES`; about half of past prickles have no host recorded, so counts are a floor). **No host names are shown anywhere on the public page**; a first-name style is undecided (`docs/TODO.md`) and not implemented (a "first name" `hostStyle` can be added later: a new value in `scheduleOptions`, the snapshot would carry the name, and the privacy copy would need to agree first). `rowNote` is an optional line (for example "Camera optional" or "First-timers welcome") under every row that has no host line; it is free text, never a name or a count. The time column does not wrap ("Fri 4:00 am"). A live panel's rows replace the typed ones, so a typed `host` line applies only to a typed panel.

**Announcement strip.** `source` live says "A prickle is on now" while a public prickle runs, else "Your next prickle starts in N minutes" for the next one (or "today at 3:30 pm ET", "tomorrow at ..." from an hour out), within 24 hours; with none, nothing (or the typed line, `whenNone`). The button's `href` stays typed: the Hub supplies no join address and no Zoom link.

**Coming up.** `source` live lists the next events (`src/modules/events/page-blocks/live-events.ts`, `loadComingUp`): shown in Events (not hidden) with **`announced_publicly`** true on the event (a marketing flag, "may appear in a Coming up list", the audience chain in `docs/product/CALENDAR_EVENTS.md`; not "secret"), starting after now, soonest first, `max` cards (1 to 4, default 4) and optionally only some `kinds` of event (tick boxes; none ticked is every kind; read by `EventRepository.upcomingAnnounced`). If nothing qualifies, or the load fails, the typed cards show. A card has:
- **Kind pill**: a plain label per event kind (`COMING_UP_KIND_LABELS` in `src/modules/events/page-blocks/live-kinds.ts`: Retreat, Virtual retreat, Workshop, Book launch, Social, Session, Educational; an unknown kind shows "Event"). A new kind of event needs a label there (typed as a `Record`).
- **Title**: the cleaned title (`cleanEventTitle` and a "w/ Name" marker removed, as the Schedule panel does). No host or speaker is added, unlike the member Events page.
- **When**: Eastern days (`ORG_TIMEZONE`): "Dec 5", "Mar 13 to 15", "Mar 30 to Apr 2", with the year when it is not this one. An all-day or multi-day event gives dates only; a timed single-day event adds the time and zone ("Dec 5, 7 – 8 pm EST"), so the zone is named only where a time is shown.
- **Availability**: "N spots left", "1 spot left" or "Sold out" only when the event has a `capacity` **and** a linked Kajabi offer, using `eventSignups` (`src/lib/event-signup.ts`, "Places left and sign-up" in `docs/product/CALENDAR_EVENTS.md`): the same count the member Events page shows (attendees plus active purchases of the event's offers, once per person, read with the service role). An event with no capacity, or with a capacity but no linked offer (places can't be counted reliably from attendees alone), shows nothing. Never who is registered, never a count of registrants.
- **Link**: the member event pages (`/events/<slug>`) need a sign-in, so a card never links to them. A card links to its linked offer's Kajabi checkout page ("Sign up", only an http(s) address, through `safeHref`) while it has places; a sold-out event has no sign-up link (the feature style can show the block's waitlist link instead, below). The block also has one typed `more` link under the events ("See all events", optional; there is no public all-events page yet, `docs/TODO.md`). The typed cards keep their own `linkLabel` and `href`.
- **Styles** (`style`; a block saved without one is `cards`, so nothing already saved changes). **`cards`**: what is described above, a card per event. **`feature`**, for the big events (retreats, virtual retreats, workshops): tall tiles. With a cover the picture is the tile (the same `event_card` preset the member Events page uses) and the kind pill, title, dates and availability sit on a dark shade at the bottom in white; without one the tile is a plain blush or cream with the kind's symbol (`eventArt` in `src/components/EventArt.tsx`) and dark words: never green, plum or brown. The picture is decorative (`alt=""`, the title is on the tile). The block is its own container, so tiles pair up by the block's own width and stack in half a column. **`waitlist`** (`{ label, href }`, one per block, default label "Join the waitlist"): shown on a sold-out tile only when `href` is a safe address, in place of the sign-up link; the editor has no check for it, an empty `href` just hides it. **`list`**, for routine sessions: not cards but plain rows between thin rules, each with a date tile (day number over a short month, a `<time datetime>`), the title, a time line (the time of a timed single-day event, the dates of a several-day one, nothing for an all-day day) and the kind as a quiet tag. Its heading is "Upcoming sessions" when the block never had one (a heading cleared on purpose stays empty), and the `more` link sits under the list. A typed card in these styles takes `date` (YYYY-MM-DD, for the tile), `time` (empty falls back to `when`), `imageAssetId` (a library picture, made public on publish like any landing picture) and `soldOut`. The starter pairs a feature block (retreats and workshops, 2) and a list block (sessions, socials, launches, educational, other, 4) in two Columns on a white band.
- **Event covers, safely.** An event's cover is `community_events.image_id`, a media library asset. A signed-out visitor is served only an asset marked `is_public`, so the loader (`loadComingUp`) returns an event's `imageAssetId` **only when the asset is live, an image and already public**; otherwise the tile is the neutral one, and a failed read is the same as no picture (the page never waits on or breaks for an image). Making the asset public is the admin's act: saving an event that is announced publicly and has a cover (`POST /api/admin/events`, `PATCH /api/admin/events/<id>`) marks the cover public through the admin's own client (`publishEventCover`, `src/lib/media/event-image.ts`), the way publishing a landing page marks its pictures. It is never turned back, and an error there never fails the save. The only id that reaches the page is the one in the image address (`/api/media/<id>/event_card`) every landing picture already has; no event id, count of people or name does. No migration and no change to who can read an asset. An event announced and given a cover before this shipped keeps a private cover until it is saved again or marked public in `/admin/media`.
- Cached like the other live blocks (60 seconds, one entry per set of options); an event that starts while a snapshot is cached is dropped at render. The cards are render-only (`live: { cards }`), never saved. No ids reach the page.

**Hedgie Bookshelf** (the `bookshelf` module, `src/modules/bookshelf/page-blocks/`, Homepage group; `docs/product/WRITER_PROFILES.md`, "The public Hedgie Bookshelf"). Always live: a grid of the covers of the books members keep at the globe, newest published first, each with its title, the name on the book (the book's pen name, else the member's display name, else no author line; never the legal name) and, where there is one, a link to buy it. Fields: `heading`, `intro`, `genre` (only books with a genre containing the text, any case), `max` (books to load, 1 to 500, default 60), `firstShown` (how many show before **Show more books**, default 24: the others are in the page, hidden until pressed, and shown to a reader without scripts), `emptyText` (what a page with no books says; empty draws nothing) and `padding`. The loader (`live-loader.ts`) reads once for the blocks that ask the same, through `BookRepository.publicShelf` (service role, paged past 1000 rows), cached a minute under the `landing-live` tag; a member changing, hiding or removing a book drops that tag at once (`invalidateLiveLandingData`). The cards (`live: { books }`) hold the title, the author, a cover path, a link and the published day, and no id. A cover is drawn only when it is a media library cover at the shelf size (`/api/media/<id>/book_cover_shelf`, which is served to visitors only while a live book at the globe uses it); anything else, or no cover, is a placeholder with the title. A link is kept only when it is `http` or `https`. The cards have alt text ("Cover of <title>") and the first 100 are in the page as `schema.org` `Book` data. The editor shows three sample books so the page can be laid out. To replace the old public list, make a page, put this block on it and publish it at the address that should show the books (`/p/<slug>`, and the root host when the domain work lands). Not offered to the AI builder.

**Not live**: Finisher cards (THE END is not recorded), Timeline, Week strip, Finish-line cards, Plan phases and Journey map stay typed. The blocks with live data are not offered to the AI builder (`AI_BLOCKS` is unchanged).

**Tests.** The figures and rounding (`tests/lib/landing-live-stats.test.ts`: clipped stays, `set_total` and deleted entries ignored, Eastern midnight and daylight saving), Coming up (`landing-live-events.test.ts`: only announced, shown, upcoming events, order, limit, kinds, places left with and without a capacity, full, all-day, multi-day and timed dates across Eastern midnight and the daylight saving change, and the repository's `upcomingAnnounced` contract), the schedule (`landing-live-schedule.test.ts`: non-public types excluded, the host threshold, "writing now" at 2 or more, no names), the resolver (`landing-live-data.test.ts`: only live blocks touched, nothing saved, fallback on failure; it runs the loaders through `tests/helpers/live-loaders.ts`), the registry and the composition with and without the events module (`page-block-registry.test.ts`, `page-block-composition.test.tsx`), the boundary (`page-block-boundary.test.ts`), the server entry and its cache setting (`landing-live-server.test.ts`), the blocks and editor fields (`tests/components/landing-live-blocks.test.tsx`), the public page and preview (`tests/components/pages/landing-pages.test.tsx`), and the repository contracts for `staysJoinedBetween`, `wordsLoggedBetween` and `countHostedBy(before)`.

### Blocks with items

Steps, Stats, Finisher cards, Timeline, Week strip, Finish-line cards, Plan phases, Buttons, List, Testimonials, Accordion, FAQ, Card grid, Link list, Pricing, Social icons, Schedule panel and Outcome numbers hold their repeating items as a **slot of child blocks** (`items`), so the editor drags them on the canvas and edits one by clicking it, like Section content. The data shape is `{ type: "WeekStrip", props: { subtitle, items: [{ type: "WeekDay", props: { id, label, ... } }, ...] } }`; an item has its own type, defaults, label and fields (the Finisher card's photo is the item's own `imageAssetId`):

| Block | Item type | Layout limit |
|---|---|---|
| Steps, Stats | `Step`, `Stat` | 5, 4 |
| Finisher cards, Timeline, Week strip | `FinisherCard`, `TimelineMoment`, `WeekDay` | 6, 12, 7 |
| Finish-line cards, Plan phases | `FinishLineCard`, `PlanPhase` | 3, 4 |
| Buttons | `RowButton` | 3 |
| Pricing | `PricingPlan` | 3 |
| Social icons | `SocialLink` | 8 |
| List, Testimonials, Accordion, FAQ | `ListItem`, `Testimonial`, `AccordionItem`, `FaqQuestion` | none |
| Card grid, Link list | `GridCard`, `LinkItem` | none |
| Schedule panel | `ScheduleRow` | 6 |
| Outcome numbers | `OutcomeNumber` | 4 |

- **One table.** `SLOT_ALLOW` in `src/components/landing/config.tsx` says which block holds which item type; `SLOTS`, `ITEM_BLOCKS` (the "Parts of a block" palette group), the editor's `allow` on the parent's slot and `disallow` on Section and Columns slots, the JSON import (drops other types in the list), the publish check and the AI builder all read it. `ITEM_LIMITS` (`item-limits.ts`) is the most each layout shows; a block with no entry takes any number.
- **Rendering.** The parent draws `<Items as="ol" className="grid ..." />` (the slot, as a list); an item is a list item (`li`, or a `div` in a `dl`, or its own element such as a `figure` or `details` in a plain `div` slot) that takes `dragRef` (Puck's drag handle) and `editing`. Items are `inline` and have no width box. Layout is count-independent (auto-fit columns, CSS counters for step numbers, `nth-child` for the finish-line gradient and plan shades), because the parent cannot see how many items it has, and it cannot hand its own settings to an item. An item with nothing in its main prop draws nothing on the public page but stays visible while editing; an empty list is `empty:hidden` and items past the limit are hidden (`itemList` in `blocks.tsx`), on the public page only. A block with a frame of its own (the Schedule panel, Outcome numbers) hides the whole frame when it has no item (`:has(li)`, `:has(dd)`).
- **Pages saved before this.** A page stored with a block's items as plain lists (every page made before they became child blocks) is converted when it is read: steps 2 and 3 of `LANDING_MIGRATIONS` (`src/lib/landing/migrations.ts`) wrap each list item as a child block of the right type, with an id made from its parent's, keeping its props. Step 3 is the Buttons, List, Testimonials, FAQ, Card grid, Link list, Schedule panel (its `rows` become `items`) and Outcome numbers; a Link list's style and colour go onto each of its links. Without it the editor throws "Cannot read properties of undefined (reading 'id')" from Puck on the first list item that is not a block (`tests/components/landing-puck-editor.test.tsx` opens such a page in the real editor). Changing how a block stores anything is a migration step, not just a code change ("Changing a block's props" above).
- **Adding items.** Drag one from "Parts of a block" in the Add list into the block (`allow` greys out the rest), or duplicate one. A new parent starts with a few items (`BLOCK_DEFAULTS`; Puck gives them ids when it is added). Items are named in the outline by their type ("Week day"), not their content (Puck 0.24 has no per-item label).
- **Keyboard.** Puck's own: the drag handle and arrow keys work for a slot's children as for any block; not yet checked by hand (see `docs/TODO.md`).
- **Publish check.** Warns on a block with no (shown) items, on items past the limit and on an item outside its block; item errors (a Finisher photo with no description, a link with no address) are checked per item and numbered by their place.
- **AI builder.** Offers Steps, Stats, List, FAQ, Link list and Card grid with `items` as `{ type, props }` children (`Step`, `Stat`, `ListItem`, `FaqQuestion`, `LinkItem`, `GridCard`); a bare `{ title, text }` is read as one. The rest are not offered.
- **Settings that moved to the item.** An item cannot see its block, so a setting that used to be the block's for all its items is now each item's: the Link list's style and colour are on each link (`LinkItem`, as a Buttons button always had its own). The Schedule panel's "label on an open session" and "line under every session" apply to the live sessions the panel draws itself; a typed `ScheduleRow` carries its own status and host line.
- **Live blocks.** The live source behaves as before (`docs/product/LANDING_PAGES.md`, "Live data"), with the typed items as the fallback: the **Schedule panel** draws the server's rows itself when `source` is live and there are some, and its `items` slot otherwise. **Outcome numbers**: the typed figures are the child blocks (each with its own `source` and `stat`, so a live one can sit between typed ones and be dragged like them), and the server writes `live` into the props of each live figure (with the block's "show a live note" switch as `live.note`), never into the block.
- **Making another repeating block.** Add the item component and parent to `blocks.tsx` / `homepage-blocks.tsx` as the others do, their defaults in `CORE_DEFAULTS` and two definitions in `coreBlocks` (`src/components/landing/core-blocks.ts`: the parent with `slots: holds("Item")`, `itemLimit` when its layout has one and `itemRule` for the publish check, and the item in the `parts` group), and the item's fields (an `itemsSlot(...)` field on the parent) in `editor-config.tsx`. `tests/components/landing-items.test.tsx` checks the table against all of those. Blocks whose items look different by a setting of the block (Coming up's three styles) or nest a list (Journey map) need more care: see `docs/TODO.md`.

### Adding a block

1. A presentational component in `src/components/landing/blocks.tsx`: no hooks or browser APIs (a client part gets its own file, like `Countdown.tsx`), container-query layout from the named sizes, links through `safeHref`, pictures from `*AssetId` props with the alt text from a prop.
2. Its default props in `CORE_DEFAULTS` and a `core(...)` entry in `coreBlocks` with its label, palette group and position (`src/components/landing/core-blocks.ts`). A block about something another module owns (events, say) is not added here: it goes in that module's contribution ([Page blocks](../architecture/PAGE_BLOCKS.md)).
3. Its fields in `src/components/landing/editor-config.tsx` (every field has a label; `image(...)` is the media picker, `richText(...)` the TipTap field, `dateTime(...)` a zoned date).
4. If it can be wrong in a way a visitor can't work around, a rule in `src/lib/landing/a11y.ts`.
5. Tests: the block in `tests/components/landing-blocks.test.tsx`; the config test already fails for a block with no fields.

### Accordion and FAQ

Two blocks that look alike and differ in meaning. **Accordion** is the generic folding list: items (`AccordionItem`: `title`, plain-text `text`, `open` to start open). **FAQ** is for questions and answers (`FaqQuestion`: `question`, `answer`), and on the **published public page only** (`/p/<slug>`, never the admin preview or the editor's canvas) it also adds one schema.org `FAQPage` as `<script type="application/ld+json">` (`src/lib/landing/faq-schema.ts`, drawn by `LandingRender` when the route passes `structuredData`). It lists the answered questions of every FAQ block on the page, in order, and nothing for an empty FAQ, a question with no answer, or a FAQ inside a section hidden on both desktop and mobile or in a switched-off third column (the publish check warns about unanswered questions). The JSON is escaped (`<` as `\u003c`, `jsonLdScript`), and being a data block rather than a script that runs, it needs no CSP nonce (the writer profile does the same).

- **Pages saved when "FAQ" was the generic list.** Step 4 of `LANDING_MIGRATIONS` renames a stored `Faq` to `Accordion` and its `FaqItem`s to `AccordionItem` (`question` and `answer` become `title` and `text`; the look is the same), wherever the data is read: drafts, published copies, saved versions, a restore, an imported file. A `Faq` that holds `FaqQuestion` blocks is the new block and is never renamed, so running the step on a document without its version marker is safe (only an empty `Faq` is ambiguous, and as an Accordion it loses nothing). The step used a new capability of the migrations: `retype` renames a block, `blocks` is still looked up by the old type.
- To make an imported Accordion an FAQ, add an FAQ block and copy the words across.

### Changing a block's props

Stored pages (draft, published copy, every saved version) keep the props they were saved with, so renaming or reshaping a prop needs a migration step, not just a code change. Append a step to `LANDING_MIGRATIONS` in `src/lib/landing/migrations.ts` (`version` is the next number; `blocks` maps a block name to a function from old props to new; `root` does the same for the page frame; `retype` gives a block a new type name, as step 4 did for the FAQ). Never edit or remove an earlier step, and write each one so running it twice changes nothing more.

- The document carries `schemaVersion` (unmarked data is 0). `normalizeLandingData` runs the steps above the document's version wherever stored data is read, so the editor, the public page, preview, restore and copy all see current props, and the next save writes them back with the new version. Blocks nested in a slot (a Section's `content`) and in zones are migrated too.
- The save and publish actions stamp what the editor sends as current (`stampLandingVersion`), because the editor only ever holds migrated data and Puck may drop the marker.
- Adding a prop with a default needs no step (the block's `defaultProps` cover it); only renames, removals and changes of meaning do.
- Tests: add a case for the step to `tests/lib/landing-migrations.test.ts` (old shape in, new shape out, run twice).

## Build with AI

On **New page**, an optional "Describe the page" box turns the admin's description into a draft (`createLandingPageWithAi`, event `landing_page_ai_built`; `src/lib/landing/ai.ts`). It is our own call to the Claude API, not Puck Cloud's AI (which needs Puck Cloud). The key is `ANTHROPIC_API_KEY`; the host and model are in `config/app.ts` (`anthropic`); without the key the box is disabled.

- **Only the description is sent**: no member data, no existing page, no pictures. This is staff-written marketing copy; the rule that members' writing never touches AI still holds, and nothing a member wrote can reach this call (the Kajabi import, which maps exports deterministically, is unchanged and has no AI).
- **The answer is never trusted.** The model must call one tool, `build_page`, with a list of `{ type, props }`. `cleanGeneratedBlocks` keeps only the blocks in `AI_BLOCKS`, only the props a block has in `BLOCK_DEFAULTS`, checks each value against the default's kind and the option lists, caps lists and nesting, then `sanitizeLandingData` cleans links and rich text like anything an admin types.
- **Blocks the model is not offered**: those needing something it cannot know (Image, Image and text, Countdown, Video, Sign-up form) and Testimonials (it would invent quotes). Pictures are added in the editor. Card grid is offered without pictures, prices or buttons (icon, title, description; `SHAPES` in `src/lib/landing/ai.ts`), and a grid that has pictures is kept as it is on a change. Requests use Sonnet at medium effort with adaptive thinking (`output_config.effort`), and the model also returns a one-line summary shown in the tab; on a change, only problems the change added are listed. Adding a block to the builder does not offer it to the model: add it to `AI_BLOCKS` and `ENUMS` on purpose.
- **Always a draft.** The page is created only if generation worked (no empty page is left on a failure), is never published, and the publish checks still apply: a button the model left without a link stops a publish until filled in. The form says to check every fact and link.
- **The AI tab in the editor** (`[slug]/AiPanel.tsx`, a Puck plugin in the left rail beside Blocks and Outline) has two modes. **Add** sends only the description (`generateLandingBlocks`) and appends the blocks. **Change** (`reviseLandingBlocks`, `reviseLandingPage`) also sends the page's blocks, so the text and settings go to the model: never picture ids, and never anything but the page itself. The model returns the whole revised list; blocks keep their `id`, and `cleanGeneratedBlocks(raw, current)` merges by id, so only the props the model sent change and pictures and other settings stay. Blocks it cannot write (Image, Video, Testimonials...) are marked `locked`: kept exactly or dropped, never rewritten. Both modes put the result in with one `setData` that records history (one undo step) and read the page when the answer arrives, so edits made while waiting are kept. Nothing is saved by the action: autosave takes it from there.
- **Tests** mock the model call (`tests/lib/landing-ai.test.ts`, `landing-page-actions.test.ts`, `tests/components/ai-panel.test.tsx`); nothing in CI calls the API. Not verified: a live call against the real API (needs the key in an environment).

## Starting a page

**New page** has a "Start from" choice: a blank page, or one of the **published templates** of the chosen kind (see "Templates" below). There is no built-in, in-code starter any more: the Homepage, which used to be one, is now a published template (a landing page of kind `template`, `page_type` `landing`), so there is one list and one way to improve it. Choosing a template turns off "Describe the page". **Start over** puts a template on a page that already exists (History, "Start over from a template"; `replaceLandingDraftWithTemplate`, event `landing_template_applied`): after a danger confirm it keeps the current draft as a `before_replace` version (shown as "Your draft before it was replaced"; the JSON import below and a template replace use the same kind, restorable with Bring back like any), then replaces `draft_data` only, so the published copy, title, address, search settings and the other versions are untouched and nothing goes live. It stamps `landing_pages.replaced_at`, which makes it one audit entry without the content (like `imported_at` for an import). It saves what is typed first, so the kept draft is the one on screen, then reloads the editor on the new draft. `landing_page_versions.kind` allows `published`, `before_import` and `before_replace` (shared by the template replace and the JSON import). Tests: `tests/components/landing-templates-ui.test.tsx`, `tests/components/landing-admin.test.tsx` (New page lists no "Built in" group), `tests/lib/landing-template-actions.test.ts`. Tests that need a realistic page use `sampleLandingPage()` in `tests/helpers/landing-sample-page.ts`, not product code.

**Other ways to start**: the chevron beside **New page** (admin Pages) holds three, in this order. **Start from a template** (`StartFromTemplateDialog.tsx`) lists the published templates with their kind, takes a title and address, and calls `createLandingPage` with `template`; the page takes the template's kind, and with no published template the dialog says so and links to the Templates tab. **Import from JSON** (`ImportJsonDialog.tsx`) takes a file or pasted text through the same section as the editor's import (`JsonImportInput.tsx`, shared with `[slug]/JsonTransfer.tsx`: dry run, then the preview), then asks for the kind (the file carries none), title and address. `createLandingPageFromJson` (event `landing_page_created_from_file`) runs the same reading, pruning, picture check and sanitizing as the editor's import (`prepareJsonImport`), and only after that makes the page in one insert, so a file that fails leaves no page; the insert stamps `replaced_at`, which makes the Activity Log say "created the page ... from a JSON file". **Import from Kajabi** is below. Tests: `tests/components/NewPageStartOptions.test.tsx`, `tests/lib/landing-create-from-json-action.test.ts`.

## Export and import

History has "Export and import as JSON" (`[slug]/JsonTransfer.tsx`, `src/lib/landing/json-transfer.ts`), so a page can leave the editor as a file, be read and changed elsewhere (the owner and Claude iterate on it this way: Claude cannot write to production, so the file is the write path), and come back in one step.

- **Export** builds the file in the browser from what the editor holds: the draft as it is on screen, or the published copy. Download is named from the address, the copy and the day in the org's zone (`home-draft-2026-11-20.json`); Copy JSON puts the same text on the clipboard. The file is `{ "format": "hedgie-landing-page", "version": 1, "slug", "title", "kind": "draft" | "published", "exportedAt", "data": { content, root, schemaVersion } }`, pretty-printed, `data` as `normalizeLandingData` returns it. No row ids, user ids or audit data. A page over 2 MB (the cap save and publish use) is refused with a message.
- **Import** takes a file or pasted text, accepts the wrapper or a bare `{ content, root }`, and always previews first: `importLandingDraftJson(pageId, text, { dryRun: true })` runs the whole pipeline and writes nothing, and the real call is the same code. The file is untrusted: over 2 MB, not JSON, another `format` or `version`, no `content` list, or a `schemaVersion` newer than this build is refused in plain words. Otherwise it is migrated (`normalizeLandingData`), reduced to the blocks and props the builder has (`pruneToKnownBlocks`: unknown blocks at any depth, in Sections and Columns, are left out and listed; props a block or the page frame does not have are dropped; a missing or repeated block id is replaced), every `*AssetId` is checked against this library (a picture that is missing or deleted is cleared and counted), then `sanitizeLandingData` and the schema stamp run as on save (rich text allowlist, links through `safeHref`). Nothing is fetched. Props inside a card or list item are not pruned: only the block's own props are.
- **What it never touches**: the published copy, title, address, search settings, other versions, other pages. A file never creates a page, publishes, or changes the address, even though the wrapper names a slug and title (they are shown as where the file came from, nothing more).
- **History**: like "Start over from a template", the draft as it was is kept first as a `before_replace` version and `replaced_at` is stamped (the one audit entry, without content); History calls that kind "Your draft before it was replaced", and Bring back restores it. A file identical to the draft (after the same cleaning) changes nothing and keeps no version. The editor saves what is typed first, then reloads on the new draft.
- **The preview** says how many blocks the file has against the draft, what was left out or removed, what the publish check would raise, and whether it matches the draft; "Replace draft" then asks (danger tone) before anything is written.
- **Tests**: `tests/lib/landing-json-transfer.test.ts` (file, parsing, pruning), `tests/lib/landing-json-import-action.test.ts` (the action), `tests/components/landing-json-transfer-fields.test.tsx` (fails when the editor gains a field the import would drop: add it to `EXTRA_PROPS` or the block's defaults), `tests/components/LandingEditor.test.tsx` (the dialog).

## Templates

A **template** is a landing page of a special **kind** (`landing_pages.kind = 'template'`): the page the owner keeps to start other pages from. It is not a parallel system. It has a **draft that autosaves**, a **published copy**, **versions** at each publish, **Reset to published**, "changes not published yet", **History with Bring back**, **JSON export and import**, and Activity Log entries, all through the same editor, repository and actions as a page. Templates are the only starting points: they are made in the editor and live in the database (the former built-in Homepage starter in code was retired once the Homepage became a template).

- **Never public.** A template's address (`slug`) is only its editor address, `/admin/pages/<slug>`; nothing serves it to a visitor. `published(slug)` (the one read behind the public route `/p/[slug]` and the opt-in relay) returns only `kind = 'page'`, so a published template's address answers like an unknown one and the relay refuses a form on it; both are tested. `kind` never changes after the row is made (a database trigger refuses), so a template can't be turned into a public page or the reverse. The editor says it is a template, shows no public address, and its preview carries a banner. The Pages list excludes templates and the Templates tab (`/admin/pages/templates`, a path-based tab; `templates` is a reserved address) excludes pages.
- **Publishing a template** runs the same checks as a page but only as **warnings** (a template legitimately has placeholders and empty links), never blocks, and does **not** make its pictures public (it is not on the public site): a picture becomes public when a page made from the template is published. It still keeps a version.
- **Using a template** copies its **published copy** (never its draft) into a new page's draft (New page, "Start from", `createLandingPage({ title, slug, template })`), or into an existing page's draft (History, "Start over from a template", `replaceLandingDraftWithTemplate`): the previous draft is kept in History as the same `before_replace` version, only the draft changes, nothing goes live, and the title, address, search settings and published copy are untouched. The document is migrated and cleaned again as it is used (`loadTemplateDraft`). A template that was never published, or was taken down, is not offered (`usableTemplates`, `usableTemplateData`).
- **Save as template** (History, `[slug]/SaveAsTemplate.tsx`, `saveLandingTemplate`, event `landing_template_saved`) copies the page on screen (typed changes included, cleaned like a save, at least one block, under the 2 MB cap): **New template from this page** (the page becomes the template's DRAFT; edit and publish it like any page) or **Replace a template's draft with this page** (asks first; the template's previous draft goes to its History, its published copy doesn't change). **Publish the template now** does the publish in the same step (a new version). The source page is never changed. A new template's address comes from its name (`-2`, `-3` when taken); names are unique among templates.
- **Versions are immutable.** `landing_page_versions` is insert-only for every role (no UPDATE or DELETE grant, not even for the service role; pages are deleted softly so nothing cascades). A restore copies a version into the draft and never touches it; a publish adds one row. `supabase/tests/database/landing_page_kind.test.sql` tests the refusals and that earlier rows stay byte for byte the same.
- **Activity Log.** A template's changes are audit entries of their own type (`landing_page_template`, chosen by the trigger's `WHEN` on `kind`; an update's delta doesn't carry the unchanged `kind`), as the admin, in plain sentences in `src/lib/activity-feed.ts` ("published the template ...", "took the template ... down", "brought back an earlier version of the template ... into its draft", "replaced the draft of the template ..."). Page content and a page's typed search text are redacted from the audit rows.
- **Privacy.** A page may hold real names an admin typed, so a template's content lives in the database and is never committed to the repository, a fixture, a log or an analytics event. Ids are Tier 2: they travel only between our own client and server actions and never appear in a URL.
- **Repository.** `LandingPageRepository` (`src/lib/data/landing-pages.ts`): `list(kind)`, `byId`, `create({ kind })`, `usableTemplates`, `usableTemplateData`, with the in-memory twin and the shared contract test (`tests/helpers/landing-page-contract.ts`). Limits and helpers: `src/lib/landing/templates.ts`.

## Opt-in forms

The Sign-up form block (name, email, optional Instagram handle, button label, a line under the button, a success message or a thank-you page) sends sign-ups to Kajabi. The decision (owner) is that during the migration the mailing list, tags and automations stay in Kajabi, so **the Hub stores no submission**: there is no table, and nothing about the person reaches a log, an analytics event or Sentry.

- **How Kajabi takes it.** Kajabi's public API: `POST /v1/forms/{id}/submit` (JSON:API, bearer token) with `name` and `email` (required) and optional `custom_1` to `custom_3`; Kajabi checks deliverability and does the rest of what the form is set up for (double opt-in, tags, offers, sequences, automations, webhooks). It uses the same client credentials as the Kajabi imports (`KajabiClient.submitForm`, no new variable, no new host). The reference is at `help.kajabi.com/api-reference/forms/submit-form`. Kajabi's other documented way, the one-line JavaScript embed, was not used because it brings Kajabi's own styling and scripts onto our page; it remains the fallback if the API ever stops accepting submissions.
- **The block names a form, not an address.** "Kajabi form" is the form's id (Marketing, Forms), stored in the page data (`kajabiFormId`); no id or host is in code. The Instagram handle goes to the Kajabi custom field the block names (`instagramField`), or the question is left out (the default).
- **The relay** (`POST /api/landing/opt-in`, public): the browser sends the page address, the form id and the fields; the server reads the **published page** and forwards only if that page really has an opt-in block for that form, so the route can't be used to post to any other form on the account. A hidden field is the honeypot (a bot gets a normal success and nothing is sent); two rate limits through `RateLimitRepository` (per visitor address and per form); calm messages. The visitor's address is the rate-limit key and nothing else.
- **`OptInDestination`** (`src/lib/landing/opt-in.ts`: `submit(target, fields)`) is the extension point: `KajabiOptInDestination` is the only implementation, chosen in `src/lib/landing/opt-in-destination.ts`. A Hub destination (or a dual write) plugs in there; the migration steps are in `docs/TODO.md`.
- **Editor and preview** send nothing: the form reads the page address in the browser and is disabled, with a note, anywhere but `/p/<address>`.
- **Verified and not.** Verified from Kajabi's documentation: the endpoint, auth, body and side effects. Not verified: a live submission (never made, so nothing was added to the real account), which custom field the owner's Kajabi has set up (the block defaults to leaving Instagram out), and the exact status for a refused address (Kajabi documents only 401 and 403; the destination treats 400 and 422 as "check your details" and anything else as "try again").

## Importing from Kajabi

Pages has a chevron beside **New page** with **Import from Kajabi**. The admin uploads a Kajabi page export (the zip from a page's Export) and gets an unpublished draft. Kajabi has no content API, but the export is structured, so the conversion is a table, not a model: `src/lib/landing/kajabi-import.ts` (`mapKajabiPage`, pure, tested on made-up fixtures) maps the export's `config/settings_data.json` to Puck JSON, and `src/lib/landing/kajabi-import-service.ts` (`importKajabiExport`) does the rest. There is no AI in it, and none may be added: members' writing must never touch AI, and this keeps the product code free of it. The route is `POST /api/admin/landing-pages/import` (a route, not a server action, because the upload outgrows an action's body limit; it uses `requireAdminAction` and `withAction` all the same, event `landing_page_imported`, with `detail` `inspect` for a read and `needs_choice` for a match that must be chosen). The dialog is `ImportKajabiDialog.tsx` (the file list) and `ImportKajabiRow.tsx` (one export).

- **Mapping.** A section becomes a Section (background colour to the nearest we offer, width from the most common block width, a boxed card when a text or form block has its own background, a background picture with a dark shade; a section with nothing importable in it is dropped and said). Text blocks: h1 to h4 become Heading blocks, a rule a Divider, the rest cleaned rich text. Call-to-action blocks become Buttons (colour to the nearest of plum, light and brown; Kajabi paths like `/resource_redirect/...` are resolved against `kajabiSiteUrl` in `config/app.ts`, which keeps working while Kajabi stays). Form blocks become the Sign-up form. The header logo is the first picture of the page; the footer's copyright line is the footer. A block hidden in Kajabi is not imported but is listed with its link. The other block types, each a branch in `kajabi-import.ts` with a test in `landing-kajabi-import-blocks.test.ts` (the settings of each were read from real exports; the tests use made-up ones):
  - **Feature** is a Split (picture beside its words, picture on the left), or just its words when its picture is hidden, then its button if it has one.
  - **Card** blocks that follow one another (hidden ones in between skipped) are one **Card grid**: the card's first heading is the title, the rest of its words are plain lines (list items with a bullet; bold, italics and links are not kept, and the report says so), its picture, and its button when the card shows one. The card's own colours, border and shadow are not carried over. A card that links as a whole needs a button label added in the editor to show the link.
  - **Pricing** columns in a row are **Pricing** blocks (three plans at most each, so a longer row is several): the plan's name, the price text exactly as written, its heading and any plain paragraphs as the description, the list under the price as what is included, and the button with the export's link. Nothing is invented: Kajabi has no billing-period field, so that line stays empty; no plan is marked featured; a field the export lacks stays empty and is reported. The report lists what was approximated (colours, borders and shadows are not carried over; a picture on a column is left out because the block has none; bold, italics and links in the text are not kept). A second button follows the block as a button. **Offer** blocks name a Kajabi offer by id only (its title, price and checkout link are looked up when the page runs, and are not in the export), so they are not imported; the report says so with the id and the button's label.
  - **Accordion** items in a row are one **Accordion** (the heading is the title; what opens is plain lines, none open to start with). Kajabi's accordion is a generic folding list, so it is not made an FAQ: the FAQ block tells search engines its items are questions, which the export does not say.
  - **Countdown** is a Countdown with no date: the export names a Kajabi event, not when it is. The report says the date must be set (until then the block is not shown to visitors). It hides itself at the end if Kajabi removed its section, else shows zeros; what Kajabi does when it ends is reported, not imported.
  - **Video** is an empty Video block and a to-do with the Kajabi video id: a Kajabi-hosted video has no address in the export, and the Hub plays YouTube, Vimeo and Mux.
  - **Link list** in a page section is an empty Link list (the export names the Kajabi menu by id, not its links) with a to-do; in the footer it is left out and said.
  - **Social icons** in a page section are a **Social icons** block: one icon link per network the export gives an address for and the block has (Instagram, Facebook, YouTube, TikTok, X for Kajabi's Twitter, LinkedIn, Pinterest), in the export's order, with its alignment and size. A network the block has no mark for (Spotify, podcasts and the like) is left out and named in the report; a link that can't be used is kept empty with a to-do. Kajabi's icon colours and backgrounds are not carried over (the theme's are used), and links open in a new tab. In the header or footer they are left out and said.
  - **Embedded code** is imported only when it is plain markup (it then goes through the rich text rules, so it becomes text). Anything that runs or loads something (a script, an iframe, a style, an object, a form, an event handler, a `javascript:` link) is never imported; the report says once how many blocks were left out and from which hosts they load.
  - **Blog** blocks are left out: the blog stays on Kajabi.
- **What the export lacks.** A page title (the admin types it), the Kajabi form's name and fields (only its id, shown in the report; the form is chosen by name in the editor and nothing is hard-coded), whether the form asks for an Instagram handle, fonts, exact spacing, "Powered by" and anything a block does at runtime. These show up as "To do in the editor" or "Approximated" on the results screen.
- **Not handled yet.** Left out and named in the report: the blog, embedded code that runs a script or embeds another site (in the owner's pages these were Shopify product embeds: the products need cards with buttons), offers (only an id in the export), a Kajabi-hosted video's picture (the Video block has no poster), header and footer social icons and footer link lists, carousels, popups (the theme's exit and two-step popups) and any other block type. A page that is not exported cannot be imported; there is no scraping. The list and what to do next are in `docs/TODO.md`, "Landing pages: import the existing Kajabi pages".
- **The zip is untrusted** (`src/lib/landing/kajabi-zip.ts`): read in memory, never written to disk or run; at most 4 MB uploaded (Vercel's request limit is 4.5 MB), 1000 entries, 2 MB of settings, 8 MB per image, 24 MB unpacked in all, counted as each entry inflates (a zip bomb stops at the limit); a name with `..`, a leading `/`, a backslash or a drive letter refuses the whole archive; entries other than the settings and `assets/` images are never inflated, so a symlink or a script in the archive is inert. Pictures named in the export come from the archive or, for an upload path, from the Kajabi picture host (`kajabiPhotoHosts`) through the pinned fetch and nowhere else; each goes through the media library's image checks. All text and HTML pass `src/lib/landing/sanitize.ts`.
- **A page's identity.** The export has no page id or title (its file name carries a number that differs per export), and the ids it does carry for a section or a block belong to the Kajabi template or to the page it was cloned from: pages made from one template or by duplicating a page share their first section and earliest block (found on real exports, which is why the first key, `kajabi:<first section>:<earliest block>`, made different pages replace one another). So `landing_pages.import_key` is now a fingerprint of the page's **layout**: a hash of the ordered sections of the page (id and kind) and, in each, the ordered blocks (id and kind), never the text, the settings, the header or the footer (`layoutFingerprint` in `kajabi-import.ts`). The key is `kajabi2:<hash>`. What follows from that: a re-export after edits to the wording is the same layout and is found again; a re-export after a block was added, removed, moved or changed to another kind is a different layout and is a new page unless the admin picks the page to replace; pages cloned from each other and differing only in their words share a layout, so **a match is only ever an offer**.
- **Choosing.** Each file is read first (`mode=inspect`, nothing is written): the dialog shows what the export starts with (its first heading and first lines, since the export has no title and the zip names say nothing), suggests a title from the heading, and lists the pages with the same layout. Nothing is preselected when there is a match. The choices are: replace the draft of a page with the same layout, import as a new page, or replace the draft of another imported page (a pick list of every page made by an import: how a page whose layout changed is updated). A replace says the draft's edits will be replaced and that the old draft is kept in the page's Version history; the live page never changes. The title is needed only for a new page; a replaced page keeps its title, address and SEO. The route never replaces without an explicit `replacePageId`: with neither that nor `asNew=true`, a match answers `choose` and nothing is written. Several zips can be added at once; each is its own row with its own title and choice.
- **Keys of numbered twins and old pages.** A new page whose layout a page already has gets `kajabi2:<hash>#2` (then `#3`, ...), because a key is unique per live page; a later export is offered every page with that layout. A page replaced by choice takes the export's key if it did not already have one for that layout, so its next export is found. Pages imported before this change hold a key of the first format (`kajabi:...`): it is never matched again (so it can never give a silent or wrong match), those pages stay in the pick list of replaceable pages, and replacing one rewrites its key to the new format. Nothing is migrated or deleted: the column and its unique index are unchanged (expand only), and an old key is just a value that nothing looks up. A page not made by an import (no key) is never replaceable by an import.
- **Unpublished edits are protected.** If the draft was edited after the last import (`updated_at` later than `imported_at`), or differs from the live page, or the title typed isn't the page's, the import writes nothing and asks ("this will replace your unpublished changes"). On a yes, the old draft is first kept in the page's history as a `before_import` version (`landing_page_versions.kind`), shown in Version history as "Your draft before an import" and restorable with Bring back like any version. `imported_at` changes on each import, so each is one audit entry without the content (autosave stays unaudited).
- **Tests.** The mapper on synthetic fixtures (`tests/lib/landing-kajabi-import.test.ts`), the zip limits (`landing-kajabi-zip.test.ts`), the identity on fixtures that reproduce the shared-ids collisions (`landing-kajabi-import.test.ts`), the service with the in-memory repositories (new page, a match that must be chosen, replace with the published copy and versions untouched, a numbered twin, a page with an old key, what may be replaced, inspect, before-import version and restore: `landing-kajabi-import-service.test.ts`), the route, the dialog, the repository contract both ways and pgTAP for the audit and the key.
