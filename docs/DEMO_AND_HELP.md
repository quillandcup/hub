# Reproducible Demo and Help Docs

One mechanism, two outputs: a fictional demo community seeded into a local stack, and Playwright scenes that drive the app and capture screenshots and clips.

1. **Newsletter / showcase** (short term): screenshots and short videos of what's being built, for the RayhausCapital newsletter.
2. **Member help site** (longer term): app-specific help articles (how to join a prickle, check in, host, find a BFF) whose screenshots are regenerated from the same scenes, so they don't go stale as the UI changes.

Status: the harness, two scenes, the `/help` route and the first article ("How to join a prickle") exist (`docs/TODO.md`, "Reproducible demo and help docs").

## Layout (proposed)

```
demo/
  seed/            fictional community, built from Bronze + Local inputs
  scenes/          one Playwright spec per help article or feature
  playwright.config.ts
  out/             captured screenshots and videos (gitignored)
help/         the articles (markdown), one per topic, images by scene name
```

Commands, run from the repo root:

1. `pnpm demo:stack up`: a separate local Supabase stack (project `hub-demo`, ports shifted by 2000: API 56321, DB 56322, mail 56324), built from this branch's migrations with no `seed.sql`, so it always matches the schema and never touches the shared dev database. Its config is generated from `supabase/config.toml` (`demo/stack.ts`); URLs and the standard local keys go to the gitignored `demo/.env.demo`. `down` stops it, `reset` deletes its data.
2. `pnpm demo:app`: the app on port 3100 against that stack (dev server). For production-mode runs, which is what CI checks, `pnpm demo:build` then `pnpm demo:serve`: they build into `.next-demo`, so the pre-commit build (which rewrites `.next`) can't pull files out from under a running server. (Next adds `.next-demo` to `tsconfig.json`'s `include` when it builds there; that edit is local, so leave it out of a commit.)
3. `pnpm demo:seed`: the fictional community (`demo/personas.ts`), then the app's own `/api/process/calendar`. Safe to run again.
4. `pnpm demo:publish [--verify | --prod]`: uploads the desktop light screenshots the articles use into the current set, or with `--verify` only checks they were all captured (see Decisions). `pnpm demo:stack migrate` applies migrations added since `up`.
5. `pnpm demo:capture [--project=desktop-light]`: runs every scene in `demo/scenes/` across the matrix and writes `demo/out/<scene>/<project>/NN-step.png`. `DEMO_VIDEO=1` records video.

Notes from the first run: the phone project is Chromium at the iPhone's size and user agent (WebKit isn't installed; add it for Safari-accurate checks); the browser's time zone and locale are pinned to the org's, because members see times in their own zone and the host's would leak in; the Next.js dev badge is hidden in screenshots.

## Seed data

- **Fictional only.** The repo is public (`public-repo-hygiene.md`): invented names, `@example.com` emails, no real Slack, Zoom or Kajabi ids.
- **Seed the inputs, not the results.** Write Bronze (calendar events, Zoom attendees, Kajabi members) and Local rows, then run the real `/api/process/*` routes to build Silver. The demo then exercises the same pipeline production does, and a change to Silver logic can't leave the demo showing something the app wouldn't produce.
- **Relative dates.** Server code reads the real clock (`lib/clock.ts`), so the seed is generated relative to "today in `ORG_TIMEZONE`" (a prickle tomorrow at 9am, last week's attendance, a 12-week streak) instead of frozen dates. Captures are reproducible in content, not in calendar dates.
- **Cast.** A handful of personas that map to articles: a new member in their trial, a regular with a streak, a prickle host, a big sister, an admin. Ten more invented members fill the room without signing in, and a deterministic Zoom attendance history (`demo/attendance.ts`: who comes by their own rate, joins a few minutes in, sometimes leaves early or steps out and back) goes through the real attendance processing, so the schedule shows typical crowds and hosts have show-up and on-time rates.
- **Safety.** The script refuses to run unless the Supabase URL is local, and never touches production (`verify-against-prod.md`).
- **Typed rows (TODO).** There are no generated database types, so seed rows are plain objects and break at runtime when a column changes. Generate types (`supabase gen types typescript --local`) and type the seed with them; until then the capture run is the check that the seed still fits.

## Scenes

- Signing in: create the demo users with the service role (as in the local sign-in recipe) and set the session in the browser context once in a Playwright setup project, instead of going through Mailpit for every run. Sudo ("Sudo As…") gives member views from the admin account where that is simpler.
- Fixed viewport (1280x800 desktop, plus a phone size where a mobile layout matters), light theme, animations off, `page.clock` for client-side time, masked or avoided elements that vary (relative times, avatars from external hosts).
- A small `shot(page, name, { highlight })` helper names files `NN-name.png` and can outline the control the article talks about.
- A scene is a spec file; a failing selector is the signal that an article is out of date.

## Help articles

- Static markdown in `help/`, covering the topics members already get in Kajabi's "Hedgie Help!" section that the Hub has screens for: joining a prickle, planning your month, becoming a host, starting a PUP, running a prickle (which includes what to do if you can't host). The BFF program, suggesting a webinar or coaching topic and submitting a daily coaching video are processes outside the Hub (external forms), so they stay in Kajabi until the Hub has the feature (`docs/TODO.md`, "Kajabi help topics left in Kajabi").
- Kajabi stays the source of the existing lessons; none of their text is copied into the repo. Read the relevant lesson there when drafting its Hub version, for tone and for the non-app parts (prickle types, etiquette, hosting norms). Its steps predate the Hub: joining is described through Slack's `#prickle-times` posts, a shared Zoom link and password, and a monthly "Prickle Times" spreadsheet, so every app-specific step is rewritten against the real screens. Of the ten "Hedgie Help!" lessons, two are drafts (what to expect in the BFF program, suggesting a webinar or coaching topic; the second is empty), and the daily coaching video lesson is a short video page.
- Publishing is a later decision (a `/help` route in the app, a static site such as Trackbear's help site, or Kajabi itself). Markdown plus images is portable to all three.
- Images are fictional by construction, but still review them before committing: a screenshot is the likeliest place for real data to leak.

## Scenes are also browser tests

Each scene is a key user journey (join a prickle, check in, host, find a BFF), so it doubles as an end-to-end test. One scene definition, two modes:

- **verify**: runs the journey with assertions across the whole matrix below; fails on a broken flow, a missing control or a failed accessibility check.
- **capture**: runs the same journey for the chosen project only and writes the screenshots and video.

A stale article and a broken flow are then the same failure.

**Matrix** (Playwright projects): phone, tablet portrait, tablet landscape, desktop, each in light and dark. Widths include sizes just either side of the shell breakpoints (`CLAUDE.md`, "Responsive Layout"), not only device presets. Dark mode is `next-themes` with Tailwind's `darkMode: "class"`, so a scene sets the theme explicitly (stored preference) as well as emulating `prefers-color-scheme` for the "system" setting. Cheap per-page checks run on every combination: axe contrast and a11y scan, no horizontal overflow, no console errors. Screenshots of the verify run can be compared against a baseline later; the first pass is assertions only.

**Fidelity of the demo users.** The service role only creates the accounts and rows. The browser then signs in as each demo user through the real auth flow, so every page query runs as that user under RLS, and `requireAdminPage` and the sudo rules apply as they do in production. The service role key never reaches the browser. Demo users are created in the states real people are in (trial member, active, on hiatus, cancelled, big sister, host, admin, signed-in non-member), with `user_profiles`, `members` and membership history written the way the app's own sign-up and processing write them. A scene signs in as the persona the article is about, and a permissions scene checks that a member can't reach `/admin` (`/no-access`) and sees only their own data.

## Page checks (every scene, every size, light and dark)

Each `shot()` also checks the page it just captured (`demo/checks.ts`), so a scene is an accessibility, overflow and console test at all eight size and theme combinations without extra code:

- **a11y and contrast**: axe at WCAG 2.0/2.1 A and AA. Colour contrast is the check that catches a missing dark-mode colour: it runs against the real theme of each run.
- **overflow**: the page scrolls sideways, or an element sticks out past the screen edge, outside a container that really scrolls sideways (`overflow: auto` or `scroll`, with something to scroll). A container that clips with `hidden` or `clip` doesn't count: it cuts content off with no way to reach it, which is how the week calendars lost Thursday to Saturday on phones. Contents of a fixed panel (a slide-in drawer) are left to the dialog check.
- **edge**: a dialog, menu, listbox, tooltip or popover is cut off by the screen, is taller than it with no scrolling of its own, or sits within 8 px of a side without being a full-width sheet. This is what catches a modal clipped on a phone.
- **covered**: no control is still under a fixed or sticky bar (or any other element) after it has been scrolled to the middle of the screen. Content passing under a footer while it scrolls is normal; the last item under a footer, the first under a header (they can't be centred), or a bar tall enough to cover the middle is a control a person can never reach.
- **console**: an error logged, or an uncaught exception.

**Scrolling.** The member app is a full-height shell whose `main` scrolls; the window never does. So before checking, every scrolling area is scrolled through, top to bottom in screen-sized steps and back (`scrollThroughPage`): that lays out everything below the fold, which axe needs to report it consistently, and it makes lazy-loaded content appear. A whole-page capture (`shot(page, testInfo, "name", { fullPage: true })`, used for the weekly schedule and the host request form) grows the viewport to fit what the page scrolls inside itself, up to 7000 px, because Playwright's own `fullPage` only knows the window and would add nothing here. The default capture stays what is on the screen, as a member sees it.

A scene can also assert behaviour, not just look: `calendar-views` scrolls each day of the week calendars into view and expects it on screen, and that the sticky time column sits flush with the left edge of what scrolls (a sticky `left: 0` sticks at the scroller's content edge, so padding on a scroller leaves a gap that the admin calendar once had), which is what failed on a phone before the fix. (The cause: the calendar card was both the `@container` box, whose width ignores its contents, and `overflow-clip`, so the 492 px grid overflowed it and the clip hid the overflow from the scroller outside; the fix keeps the `@container` box bare and puts the card inside with a minimum width.)

`demo/selftest/checks.spec.ts` builds small pages that each trip one check (and a clean one that trips none), so a detector that quietly stopped working can't pass for an app with no problems.

**A ratchet, not a wall.** `demo/baseline.json` lists the findings that are known and tolerated, per size and theme and per step. It is empty now (the 245 the first run found are fixed), so any finding fails a run, with the rule, the element and the numbers. If a deliberate or not-yet-fixable one has to be allowed, it is added there in a reviewed diff. A finding known at any size in the same theme counts as known, because axe is not consistent about elements below the fold on a short screen; a new element or rule still fails. Identities leave out row positions and record ids, so a list that is one longer today or a re-seeded database doesn't count as new. To regenerate the file: `DEMO_CHECKS=report pnpm demo:capture --grep-invert @published && pnpm demo:baseline`. `DEMO_CHECKS=report` writes the findings without failing, and `off` skips the checks.

## Overview videos

`pnpm demo:video` records two member overview videos from the demo community into `demo/out/video/` (gitignored; WebM and, with ffmpeg installed, MP4, both with the narration): `overview-short` (about 30 seconds: one beat each for commitments, streaks, a writing project, chat posting and the end card) and `overview-long` (about 2.5 minutes: the dashboard scrolled down to what's coming up, adding a Prickle to the member's calendar, syncing the whole schedule, what that looks like in Google Calendar, attendance history as list, month and week calendars, streaks, a writing project with a progress entry logged end to end, chat with threads, posting and search, members, notifications reached through the user menu and Settings, and Hedgie Help). They are scripts, so a UI change means re-running, not re-editing. Run `pnpm demo:seed` first: the long cut logs a progress entry and adds a Prickle to the calendar, and the seed puts the member's projects, commitments and calendar items back as they were.

- **`demo/video/director.ts`** draws everything into the page with one injected script: a cursor that glides to what it clicks, a ripple on each click, a caption bar, and full-screen title cards (the recording opens on the card's background, never a blank page). Scenes call `say`, `click`, `point`, `scroll`, `card`, `goto`; each click clears the caption and scrolls the new view to its top (the app's own `main` scroller keeps its position across navigation).
- **Run against a production build** so nothing compiles on camera: `pnpm demo:build`, then `pnpm demo:serve -p 3101` (the scenes default to `http://localhost:3101`; `DEMO_APP_URL` overrides). Pages are visited once in an unrecorded context first, so the recording shows the app responding, not loading for the first time. `DIRECTOR_LOG=1` prints each step, which is how to find the one a changed page broke.
- **Never `waitUntil: "networkidle"`**: the member pages poll, so it doesn't settle and the run hangs until the timeout.
- **Only what the demo community can show honestly.** Captions say what is on screen (Hosting shows "Settle in first" for a three-week member, so the caption says that). Screens with nothing to show are left out: the Bookshelf (no published book) and the Wheel of Wonder (nobody online). Chat is seeded by `demo/chat-seed.ts` (four app-only channels, threads, reactions, some unread) with the `chat` feature on and `chat_posting` off: the demo has no Slack, so a post would answer "isn't connected", and the composer is hidden instead.
- **The cast is women writers, in a bookstagram voice** (`demo/personas.ts`, bios in `demo/seed.ts`, chat in `demo/chat-seed.ts`): casual, emoji, WIP and word-count talk, because most members come from Instagram. Renaming the cast leaves the old members behind, so the seed removes demo (`@example.com`) members who are no longer in it.
- **Chat posting without Slack.** The demo channels are bridged with made-up Slack ids (`CDEMO...`) and the demo member has a token-less Slack connection record, so the composer works. Outside production the app saves a post and leaves it pending; the recording marks it sent (`demo/video/slack-stand-in.ts`), which is the state Slack's answer leaves. The recording starts as a returning member whose last open channel is `#announcements` (the `chat_last_channel` cookie), so `/chat` opens on a conversation, not the empty list. Posts from an earlier recording are removed first.
- **Nothing about this machine goes on camera.** The director rewrites any IPv4 address on screen to a documentation address and the demo browser's `node` user agent to "Chrome on macOS" (Settings → Account lists sessions with both).
- **Google Calendar stills** (`demo/video/google-calendar.ts`). The demo's feed is localhost, which Google can't subscribe to, so the long cut shows what Google does with it, from two screenshots made by hand in `demo/out/video/google-calendar/` (`week.jpg`, `event.jpg`, 1400x845 browser screenshots; gitignored because they come from a real account; the video skips the segment without them). To make them: fetch the member's feed (`/api/calendar/feed/<token>.ics`, token from `calendar_feed_tokens`), import the `.ics` into a throwaway Google calendar (Settings → Import & export, choosing that calendar, not the default one), show only that calendar ("Display this only"), screenshot the week of the events, open one and screenshot again, blank everything but the grid and the popover, then put the calendar view back as it was and delete the throwaway calendar. The popover's calendar owner and `localhost` link are replaced with demo text in the video.
- **Narration** (`demo/video/script.ts`, `voiceover.ts`; storyboard and script in `docs/OVERVIEW_VIDEO_SCRIPT.md`): each beat is `d.narrate(line, actions)`. The line is spoken on this machine (nothing is sent to a service), the line is the caption, and the screen waits for whichever is longer, the voice or the actions. All lines are spoken before recording starts and kept by a hash of engine, voice, rate and text, so only an edited line is spoken again. `finish()` mixes the clips in at the moment each began and normalizes the loudness to about -16 LUFS. **Voice**: Kokoro, an open neural model (`af_heart`, an American woman, by default; try `af_bella`, `af_nova`, `af_sarah`, `af_nicole`, `af_kore`, `af_sky` with `DEMO_VOICE=af_bella pnpm demo:video`, `DEMO_VOICE_RATE` is speed, 1 is normal). Without it set up the narration falls back to macOS's `say` (Samantha), which sounds plainly synthetic (`DEMO_TTS=say` forces it). **One-time Kokoro setup** (about 120 MB to 450 MB, in `~/.cache/hedgie-demo-tts`, outside the repo; `DEMO_KOKORO_DIR` changes the place): `brew install python@3.12`; `python3.12 -m venv ~/.cache/hedgie-demo-tts/venv`; `~/.cache/hedgie-demo-tts/venv/bin/pip install kokoro-onnx soundfile`; then into `~/.cache/hedgie-demo-tts/models/` download `kokoro-v1.0.onnx` (326 MB, the full-precision model, which sounds cleaner; the 92 MB `kokoro-v1.0.int8.onnx` also works and is used when the full one is missing) and `voices-v1.0.bin` (28 MB) from the `model-files-v1.0` release of github.com/thewh1teagle/kokoro-onnx. 54 voices ship in that file; the American women are `af_heart`, `af_bella`, `af_nicole`, `af_sarah`, `af_sky`, `af_nova`, `af_kore`, `af_alloy`, `af_aoede`, `af_jessica` and `af_river`, the British women `bf_emma`, `bf_alice`, `bf_isabella` and `bf_lily`. The speech model can read a word the wrong way (it said "lives" as a noun where the verb was meant), so script lines avoid words that can be read two ways. `demo/video/kokoro_tts.py` is the small script that speaks one line.
- **ffmpeg** (`brew install ffmpeg`): `finish()` cuts the blank seconds before the first page loaded and writes the WebM and an H.264 MP4 (email and social want MP4). Without it the WebM keeps its blank start and there is no MP4, with a warning. To read a recording, `ffmpeg -i x.mp4 -vf "fps=0.2,scale=480:-1" f%02d.png` writes a small frame every five seconds, and `tile=4x4` makes a contact sheet.
- Not in CI (it isn't under `demo/scenes/`): recording takes minutes and the output isn't committed.

## Integration mockups

Not everything happens in the browser. `demo/scenes/notification-mockups.spec.ts` draws what members receive when the Hub reaches out, for every notification kind (so a new kind appears in it by itself), from the real message code with the demo community's data:

- **Slack**: the blocks as the Slack channel assembles them (`slackBlocks()`, including footer links), rendered locally by [slack-blocks-to-jsx](https://github.com/themashcodee/slack-blocks-to-jsx) (MIT; every block type our messages use, with a light and a dark theme) in a desktop direct-message frame and a phone frame (Slack's phone app: status bar, conversation header, message box; the screen grows to show a long message in full). **The phone frame is an approximation:** the blocks are the real ones, but how they lay out is the renderer's CSS at phone width, not Slack's own, so how Slack's iPhone app arranges a row of buttons (wrap, stack or scroll) is NOT verified by it. Compare with a real screenshot (Admin → Test Notifications, sent to your phone) before relying on it, for example to judge how an answer scale looks, with the bot's name and colour read from `slack-app-manifest.yml`. No third-party service: Block Kit Builder would mean sending the message to Slack.
- **Email**: the React Email template as `renderNotificationEmail()` makes it, with the unsubscribe link a real send adds, inside an email client frame with the real sender.
- **Browser push** (web push): the payload `pushPayload()` builds, on a laptop, an Android phone and an iPhone. Web push reaches desktop Chrome, Edge, Firefox and Safari and Android Chrome; on iPhone only once the Hub is added to the Home Screen (iOS 16.4 and later), which the iPhone frame says.
- **In-app**: the bell and banner are part of the app itself, so the other scenes already show it.

Messages come from `sampleMessages(supabase, kind, now, { test: false })` (`lib/notification-test.ts`), the admin test send's builder without its "[Test]" marking. Only the frames are drawn (`demo/mockups/frames.tsx`): the content is the app's, the surroundings plausible rather than pixel-identical to each client. The page checks are off for these pages, since they aren't the app's own. They are captured at every size and theme like any scene.


## Decisions

- **Help site**: `/help/<topic-slug>` inside the app, gated by sign-in (the proxy checks first; the article pages themselves are built ahead of time and carry normal caching headers, because the content is the same for every member; anything per-member is `private` or `no-store`, and Vercel won't cache a response that varies on `Cookie`). Slugs are stable and named by topic (`join-a-prickle`), not by title, so a reworded title never changes a link; a renamed slug keeps a redirect. Contact is the `SUPPORT_EMAIL` address (`lib/config.ts`), not typed into the page. Not a `help.` or `support.` subdomain: gated content shares the app's session, and a subdomain would need DNS, a rewrite and a cross-subdomain cookie for no benefit. `support.` stays free for a ticketing tool later, and can alias `/help` meanwhile. No attempt to mimic a vendor's URL scheme.
- **Public pages**: a small set for members who can't sign in (login trouble, how to reach support), with no member data. Any public page gets `noindex` and `robots.txt` rules for crawlers, which are requests, not enforcement. Which pages are public is still open.
- **Screenshots**: not committed, and paired with the build that shows them. They live in the private `help-images` Storage bucket (no policies), one folder per **set**, named by the first 12 characters of the main commit it was captured at. A deploy of commit M shows the newest set whose commit is an ancestor of M (`pickSet` in `scripts/help-images-version.ts`): the deploy job works it out from the bucket and git history and exports it as `HELP_IMAGES_VERSION`, `next.config.ts` bakes it into the build, and `/help/images/<scene>/<file>` serves `<id>/<scene>/<file>` after a sign-in check. So commits between two captures show the earlier set, and an older deploy keeps the set it was built with, so a rollback shows matching images. A new set reaches production only when a build picks it up, which is why the capture workflow also redeploys. Articles refer to images as `![alt](img:<scene>/<file>.png)`.
- **CI**: capture is not part of the merge pipeline (it used to be, and added about 8 minutes to every main run). The scheduled `Help screenshots` workflow (`.github/workflows/help-screenshots.yml`, nightly and on demand with an optional `force`) works on the commit in production (the `production` tag), which already passed CI. It skips itself when the source the screens depend on (`HELP_IMAGE_INPUTS`) is unchanged since the newest set; otherwise it starts its own local stack, resets it to empty (no `seed.sql`, so the only people on screen are the demo's), seeds the demo community, runs every scene at every size in light and dark with the page checks, verifies every article screenshot was captured, publishes the set to production (additive; sets older than 30 days are deleted, except the newest of them) and redeploys that same commit through `deploy.yml` (the reusable deploy job `ci.yml` also uses; no tests, no migrations) so a build picks the set up. The redeploy is skipped if production moved on in the meantime, so it can't roll back a newer deploy; the next run covers that case. It fails when a scene fails, a page check finds a new problem, or an article shows a screenshot no scene captured; GitHub emails that, and nothing blocks a merge, so a broken scene is found the next morning, not on the PR. It reads `NEXT_PUBLIC_SUPABASE_URL` (a GitHub variable) and `SUPABASE_SERVICE_ROLE_KEY` (a GitHub secret), synced with `pnpm env:sync:github --only=NEXT_PUBLIC_SUPABASE_URL,SUPABASE_SERVICE_ROLE_KEY`. Run it by hand after a big UI change (Actions → Help screenshots → Run workflow, with `force` if the screens' source didn't change). There is no PR preview of the images; run `pnpm demo:capture` locally.
- **By hand**: `pnpm demo:publish` (the demo stack, the "local" set), `--verify` (no upload), `--prod` (production, for a person to run; the scheduled workflow does it). Dark and phone variants of article images are not published yet.
- **Slack mockups**: local renderer (evaluate `slack-blocks-to-jsx` first), no third-party service.
- **Entry point**: a question mark in a circle in the top bar, beside the notification bell (`components/HelpMenu.tsx`), not a sidebar entry; it opens a menu with Hedgie Help and Send feedback (the feedback form, which no longer has a floating button); the page is titled "Hedgie Help" ("How things work in the Hedgie House"). It is also findable in the search palette. Shown in the member and admin areas.
- **Where the files live**: member-facing articles in a top-level `help/` directory (images next to them by scene name, or published artifacts), developer docs stay in `docs/`. The route that renders them is `app/(member)/help/`, which reads `help/<slug>.md` at build time (`generateStaticParams`, `react-markdown` and `remark-gfm`, both already dependencies). Because code reads `help/` at build time, it must not count as documentation in `scripts/docs-only.ts`: otherwise a PR that only edits an article skips the build and the deploy, and the change never reaches members. Take it out of the allowlist and update `tests/lib/docs-only.test.ts` in the PR that adds the route (`docs-only-changes.md`).
