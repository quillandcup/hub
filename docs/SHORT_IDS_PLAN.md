# Plan: Short prefixed text IDs instead of UUIDs

Status: **planning only, no code written.** Pick this up from "Next steps".

## Goal

Replace every UUID identifier we own with a short, prefixed, random text ID such as
`cnt_7Kx2mQ9dFh3N`, so URLs and logs are readable and self-describing. Done now because
the app hasn't launched: only a couple of early-access users, so old links and
subscriptions can break. Existing data must be preserved (Slack data has aged out of its
90-day lookback, so a wipe-and-reimport is not an option).

## Decisions already made

- **Text primary keys generated in Postgres**, not Sqids over integers. Sqids is an
  app-side encoding, so SQL, pg_cron, pgTAP, logs and the dashboard would see different
  values than the app. Text keys mean the stored value is the URL value.
- **Format:** `<prefix>_<12 random base58 chars>` (~70 bits). Generated by a SQL function
  `new_id(prefix text)` used as the column default, replacing `gen_random_uuid()`.
  Collisions are backstopped by the primary key (the app can retry).
- **Convert everything we own**, including all bronze tables. No stragglers left as tech
  debt. Big bronze tables (`slack_messages`, `zoom_attendees`, `kajabi_*`) may need batching.
- **Stay UUID:** anything Supabase owns, namely `auth.users.id`, `user_profiles.id`, and
  every column that references `auth.users` (`user_id`, `created_by`, `updated_by`,
  `awarded_by`, `locked_by`, `slack_identities.user_id`,
  `user_feature_previews.user_id`, ...). External ids (Slack, Zoom, Kajabi, Stripe) are
  already text and don't change. Each column must be checked: a member reference converts,
  an auth reference stays.
- **No legacy mapping kept.** Old UUID links, bookmarks, Slack DMs and email links may
  break. Only the early-access users are affected: tell them in one line (brief
  maintenance window; calendar-feed subscribers must re-subscribe because feed event
  `UID`s change; see `lib/calendar-feed.ts`). `SLACK_TEST_MODE=true` in prod, emails are
  new and opt-in, so nothing external depends on old ids.
- The signed email-unsubscribe tokens embed the member id (`lib/email-unsubscribe.ts`);
  old tokens will stop verifying. Accepted this once. The rule "never rotate" still holds
  going forward.
- The two stuck "Sending to Slack..." hub-to-Slack test chat messages in prod are deleted
  as part of the migration (a one-off statement), together with any outbox rows for them.
  `chat_posting.sql` compares `chat_messages.id::text` to an `app_message_id` in Slack
  message metadata, so old ids in `bronze.slack_messages.raw_payload` metadata must be
  mapped or the rows removed.

## Prefixes

Agreed: `cnt_` contacts (the `members` table; it holds leads, active, hiatus and cancelled
people, hence "contact"; renaming the table itself is a separate TODO in `docs/TODO.md`),
`prkl_` prickles, `prty_` prickle types, `prj_` writing projects, `evt_` events,
`msg_` chat messages, `chn_` chat channels, `seg_` segments, `prg_` programs,
`bdg_` badge types.

Proposed, still to be confirmed (4-letter prefixes are fine; Stripe uses `price_`):
`cmt_` prickle commitments, `bok_` member books, `flg_` feature flags, `coh_` program
cohorts, `sch_` prickle schedules, `cev_` calendar events. Every other table with its own
uuid id (about 70 in total) needs a prefix too: generate the full list from the inventory
and put it at the top of the migration for review.

## Inventory (from the local DB, ~7 migrations behind the branch)

Inbound foreign-key counts: members 50, prickles 8, prickle_types 6, writing_projects 5,
events 5, chat_messages 3, segments 2, chat_channels 2, programs 2, badge_types 2,
bronze.calendar_events 2, plus single-FK parents (prickle_commitments, member_books,
feature_flags, program_cohorts, prickle_schedules).

The local DB lacks the later migrations (e.g. `push_subscriptions`, anything after
roughly 20261007). Rebuild the inventory from a scratch DB migrated from this branch.

Things a plain FK rewrite will miss:

1. **Views / materialized views** depending on the columns: `member_directory`,
   `member_engagement`, `member_metrics`, `prickle_popularity`, and the `bronze` views
   such as `slack_messages_meta`, `slack_channel_membership_periods`. Drop and recreate
   around the type change. Also RLS policies and SQL functions with `uuid` parameters;
   generate the dependency list from `pg_depend`. Read the LATEST `CREATE OR REPLACE`
   of any function before editing it.
2. **Ids without an FK:** `audit_log` (`member_id`, `acting_as_member_id`, plus the row id
   it audits), `access_events`, `member_activities.acting_as_member_id`. Rewrite member
   ones, keep the auth ones.
3. **Self-references:** `chat_messages.thread_root_id`,
   `prickle_schedules.carried_forward_from`.
4. **Ids stored in data:** jsonb/text columns, `in_app_notifications.url` / `ref`,
   `chat_posting` metadata, `prickle_checkin_dm_log`, calendar feed items, notification
   dedup rows, push/outbox tables. Scan every text/jsonb column for the old uuids of
   migrated tables before and after, and fail the migration if any remain.
5. **Triggers** that audit by table (`audit_member_actions`) and anything keyed on
   `id::text`.
6. **Column named `host` on `prickles`:** confirm whether it references a member or an
   auth user before converting.

## Migration approach (forward migration, data preserved)

One new migration, numbered after checking every worktree for collisions (collisions are
silently skipped; see the migration-version-collisions memory).

1. Create `new_id(prefix)` (pgcrypto `gen_random_bytes` or `gen_random_uuid` as entropy
   source; map bytes onto the base58 alphabet; consider rejecting bytes >= 232 to avoid
   modulo bias).
2. For each table: add `new_id text`, backfill with `new_id('<prefix>')`, and record
   `(table, old_uuid, new_id)` in a **temporary** mapping table (dropped at the end).
3. Generate the FK rewrite from `pg_constraint` (not by hand), in dependency order, joining
   through the mapping. Rewrite the non-FK locations above the same way.
4. Drop dependent views/policies/functions, drop old PK and FK constraints, rename new
   columns to `id` / `<x>_id`, re-add PK and FK constraints (same `ON DELETE` actions),
   set defaults to `new_id('<prefix>')`, recreate everything dropped.
5. Delete the two prod test chat messages and related rows.
6. Verify inside the transaction: per-table row counts equal before and after, zero
   orphan FKs, zero remaining old uuids in jsonb/text, then drop the mapping.

Check row counts and the migration role's statement timeout first (the repo notes an 8s
limit for some Slack statements). If one transaction is too slow, batch the backfill of
the big bronze tables and keep the constraint swap in a single final step. Deploy the app
change and the migration together (CI pushes migrations before the Vercel deploy on main).
