# Plan: Short prefixed text IDs instead of UUIDs

Status: **phase 1 (the 17 Tier 1 tables) is live in production** since 2026-10-23 03:43 UTC
(`20261215000000_short_ids_tier1.sql`, PR #196). The 109 Storage objects were moved the same
night and the queue table is dropped (`20261217000000_drop_storage_path_moves.sql`). Phase 2
(the Tier 2 tables in `public`) and Bronze are not started; see "Phases" and "Lessons from the
phase 1 run" below.

## Goal

Replace every UUID identifier we own with a short, prefixed, random text ID such as
`mbr_7Kx2mQ9dFh3N`, so URLs and logs are readable and self-describing. Done now because
the app hasn't launched: only a couple of early-access users, so old links and
subscriptions can break. Existing data must be preserved (Slack data has aged out of its
90-day lookback, so a wipe-and-reimport is not an option).

## Decisions already made

- **Text primary keys generated in Postgres**, not Sqids over integers. Sqids is an
  app-side encoding, so SQL, pg_cron, pgTAP, logs and the dashboard would see different
  values than the app. Text keys mean the stored value is the URL value.
- **Format:** `<prefix>_<12 random base58 chars>` (~70 bits). Generated by a SQL function
  `new_id(prefix text)` used as the column default, replacing `gen_random_uuid()`.
  Collisions are backstopped by the primary key (the app can retry).
- **Convert every table we own, in phases.** Tier 1 (ids users can see) first, then Tier 2
  in `public`. **Bronze is deferred** (decided 2026-10-20): it is never shown to users, so
  it can break or migrate later without anyone noticing. The migration script is driven by a
  table list, so Bronze is a later, separate run. Until then the Bronze tables are a listed
  exception to the pgTAP "no uuid-typed id columns" check.
- **Stay UUID:** anything Supabase owns, namely `auth.users.id`, `user_profiles.id`, and
  every column that references `auth.users` (`user_id`, `created_by`, `updated_by`,
  `awarded_by`, `locked_by`, `slack_identities.user_id`,
  `user_feature_previews.user_id`, ...). External ids (Slack, Zoom, Kajabi, Stripe) are
  already text and don't change. Each column must be checked: a member reference converts,
  an auth reference stays.
- **Old links break; no legacy mapping** (decided 2026-10-20). `SLACK_TEST_MODE=false` now,
  but members have barely received any Slack messages, so old `/prickles/<uuid>` links in
  DMs and notifications are not worth a compatibility layer. Exposure is small (945 members,
  14 with accounts, 9 calendar feed tokens, 2 push subscriptions, 1 course); tell them in one
  line (brief maintenance window; calendar-feed subscribers must re-subscribe because feed
  event `UID`s change, see `lib/calendar-feed.ts`).
- The signed email-unsubscribe tokens embed the member id (`lib/email-unsubscribe.ts`);
  old tokens will stop verifying. Accepted this once. The rule "never rotate" still holds
  going forward.
- The two stuck "Sending to Slack..." hub-to-Slack test chat messages in prod are deleted
  as part of the migration (a one-off statement), together with any outbox rows for them.
  `chat_posting.sql` compares `chat_messages.id::text` to an `app_message_id` in Slack
  message metadata, so old ids in `bronze.slack_messages.raw_payload` metadata must be
  mapped or the rows removed.

## Prefixes

Prefixes only need to be meaningful where a person sees the id: URLs, Slack messages,
emails, support threads. Everything else needs a prefix that is *consistent and
traceable* (an orphan id in a log tells you which table it came from), not pretty. So two tiers
(Slack prefixes a few dozen user-visible kinds with one letter; Stripe has 100+ and the long
tail is cryptic; nobody minds either).

**Tier 1: hand-chosen, readable (17, plus `media_assets`, born Tier 1 with the media library: `media_`, in `/api/media/<id>/<preset>`).** Needs owner sign-off. These are the ids a person can see or copy: in page URLs and admin pages, and in the image and download links (`photo_` in `/api/events/<event>/photos/<photo>`, `file_` in `/courses/<slug>/lessons/<lesson>/files/<file>`).

### Storage buckets (new in this audit)

Object names in Storage are paths, and some embed our ids. Renaming an object means a copy
plus delete through the Storage API (updating `storage.objects.name` in SQL does not move
the file), so the safest rule is: **leave existing objects where they are** and let the row's
`storage_path` stay authoritative. Only RLS that matches on the path needs care.

| Bucket | Path built from | RLS matches path? | Handling |
|---|---|---|---|
| `book-covers` (public) | `<member id>/<random>.ext` | **Yes**: first folder must equal `current_member_id()::text` | After conversion the member's new id no longer matches existing folders, so members could not replace or delete old covers (1 object in prod). Move those objects with the Storage API, or accept for a one-off and re-upload |
| `event-photos` | `<event id>/<item id>` | No (role-based) | Leave in place; `event_photos.storage_path` is authoritative |
| `course-files` | `<course id>/<lesson id>/<file id>-<name>` | No | Leave in place (8 objects in prod); new uploads use new ids |
| `feedback-screenshots` | `<auth user id>/<id>.png` | Yes, on `auth.uid()` | Unaffected: auth ids stay uuid |
| `slack-files` | Slack ids | No | Unaffected |

**Decided 2026-10-20: move the objects.** The Tier 1 migration rewrites the path columns
(`event_photos.storage_path`, `course_lesson_files.storage_path`, the `book-covers` URLs in
`writing_projects.cover_url` and `member_books.cover_url`) and queues each rename in
`public.storage_path_moves` (service role only). A one-off script moved each object through the
Storage API right after the migration was pushed and deleted the queue row as it went: 109
objects in production (71 event photos, 37 course files, 1 book cover), 109 moved, 0 failed.
Until it ran, those files 404 under their new paths. The table is dropped by a later migration
(`20261217000000_drop_storage_path_moves.sql`) and the script and its tests were removed; they
are in git history (PR #196) if phase 2 needs the same pattern.

`video_text_tracks.storage_path` follows the same rule. `videos.mux_asset_id` /
`mux_playback_id` are external ids and don't change.

## Ids we don't generate

`new_id(prefix)` is for the primary key of a row the **server** creates. Everything else that
looks like an identifier falls into one of these groups. All of them are stored as text or
uuid; what differs is *who chooses the value*. Checked against the scratch stack on 2026-10-20.

| Who chooses it | Examples | Treatment |
|---|---|---|
| **A person, meant to be meaningful** (admin, developer, importer config) | Slugs: `events.slug`, `programs.slug`, `courses.slug` (all `UNIQUE`). Keys: `feature_flags.feature_key`, `user_feature_previews.feature_key`, `feature_flag_segments.feature_key`, `badge_types.key` | Unchanged. Slugs are what member-facing pages use (`/events/[slug]`, `/courses/[slug]`), next to the id: the primary key still converts, the slug is a second handle, not a replacement. `feature_flag_segments` also has a `segment_id` that converts |
| **Another system** | `source_key` on `courses`, `course_modules`, `course_lessons`, `course_lesson_files`, `videos` (Kajabi); `videos.mux_asset_id` / `mux_playback_id`; `external_id` on `writing_*`; every Slack, Zoom, Kajabi and Stripe id | Never converted, never generated by `new_id`. They are the natural key the importers upsert on |
| **Our own code in the browser** | `analytics_events.message_id` and `session_id` (`crypto.randomUUID()`, `lib/analytics/client.ts`); `video_watch_segments.session_id` is the same kind (not written by any code yet, so confirm when it is) | Stay uuid. We generate them, but in the browser, because a retried batch must re-send the same value for the insert to be idempotent. They are idempotency and correlation keys in their own columns, not primary keys, and not shown to anyone (`analytics_events` itself is keyed by a `bigint` counter) |
| **Our code, as a secret** | `calendar_feed_tokens.token`, the signed email-unsubscribe token, `slack_sign_in_tokens`, push subscription endpoints | Not ids, not touched. They sit in URLs by design; the member id inside the unsubscribe token changes, so old emails' links stop verifying (already accepted) |
| **Code, derived from other values** | `dismissed_duplicate_groups.group_key`, `admin_work_queue_completions.occurrence_key`, `rate_limit_counters.bucket` | Unchanged; check that none embeds a converted id (the `occurrence_key` contents are still an open item) |
| **The database, as a counter** | `access_events.id`, `audit_log.id` (`bigint GENERATED ALWAYS AS IDENTITY`) | Unchanged: already short, server-generated, internal |

Also check our own server code: it sometimes mints a primary key itself instead of using the
column default (`app/api/feedback/route.ts` does `const id = randomUUID()` for the `feedback`
row and its screenshot path). Those become `new_id`-style calls; the migration's grep for
`gen_random_uuid()` should also cover `randomUUID()` in `app/` and `lib/`.

**Courses are a mix on purpose:** the course page uses the slug (`/courses/[slug]`), the
module, lesson and file pages use ids (`/courses/<slug>/modules/<module>`,
`.../lessons/<lesson>`, `.../files/<file>`), and the admin page uses the id
(`/admin/courses/[id]`). That is why `courses`, `course_modules`, `course_lessons` and
`course_lesson_files` are Tier 1: their ids are visible. A slug being the member-facing handle
does not make the id private. `events` and `programs` are the same.

**Rules**
- A row's primary key is always produced by the server (the column default, or `new_id` called
  from server code). No person, importer payload or request body supplies one. Values from
  the browser are allowed only as idempotency or correlation keys in their own column, with a
  unique constraint where idempotency needs it (`analytics_events (user_id, message_id)`),
  never as the primary key.
- A value a person chose (slug, key) is not an id and is not rewritten, but it is a link:
  changing a slug breaks old links the same way this migration breaks old ids. Slugs are not
  mapped or redirected by this change.
- Code that takes an id from a request and compares it to a column should validate the shape
  (`<prefix>_<12 chars>`), not use `.uuid()`; see "App and test changes".

## Rehearsal, cutover and failure modes

### Rehearse on a copy first

1. Dump production (`supabase db dump --linked`, schema plus data, read-only on prod) into a
   fresh local stack like the scratch one used for the inventory. The dump holds real member
   data: keep it outside the repo, never commit it, delete it afterwards.
2. Apply the phase's migration there and record the wall-clock time per statement. Production
   is **slower** than a laptop (see the benchmark below), so multiply local times by the
   measured ratio (plan with 10x) instead of treating the local number as an upper bound.
3. Run the whole check list on the copy: row counts equal, zero orphan foreign keys, zero old
   uuids left in text/jsonb, pgTAP, then the unit and db suites and a manual click-through of
   the Tier 1 pages (member, prickle, event, course, lesson).
4. Repeat until the copy is clean, then rehearse the failure path: kill the migration midway
   and confirm nothing changed.

### How much slower is production than the laptop?

Measured 2026-10-20 with a one-off script (`bench.sql`, not committed): inside Postgres, on
temp tables (so it leaves nothing behind; it ends in a deliberate `RAISE EXCEPTION` that
rolls everything back and returns the timings), it times a CPU loop, inserts 2 x 250k rows
with a foreign key, backfills a `new_id` column on 250k rows, rewrites a referencing column
on 250k rows through a join, and swaps the primary and foreign key. The comparison is
database against database; a Vercel cron would only time the app, not the database.

| Step | Local (M-series laptop, Docker) | Production (3 runs) | Ratio |
|---|--:|--:|--:|
| CPU (3M md5) | 1.1 s | 4.4 to 4.5 s | about 4x |
| Insert 2 x 250k rows | 1.2 s | 6.6 to 9.7 s | about 5 to 8x |
| Backfill `new_id` on 250k rows | 1.3 s | 7.1 to 8.2 s | about 5 to 6x |
| Rewrite a referencing column, 250k rows | 1.5 s | 14.9 to 19.1 s | about 10 to 13x |
| Swap primary and foreign key | 0.18 s | 1.3 to 1.5 s | about 8x |

So production is roughly **4 to 13 times slower** than the laptop, and the heavier the write
work the bigger the gap. Limits: temp tables are not WAL-logged, so real tables (which write
WAL and feed replicas and backups) will be slower again; and prod may be sharing CPU with
live traffic. If the rehearsal shows the migration is anywhere near a minute locally,
re-benchmark with real tables on a throwaway project before choosing the window.

### Expected downtime

Each migration file runs in one transaction, and Postgres DDL is transactional, so the schema
is either entirely old or entirely new. Inside it the migration takes `ACCESS EXCLUSIVE` locks
on every table it alters, so reads and writes to those tables wait for the whole transaction.
Prod is about 250k rows in total, so the work is about the size of one benchmark pass. Scaled
by the ratios above that is roughly **30 seconds to 2 minutes per phase** on production, to be
replaced by (rehearsal time x 10). Waiting queries from the app fail once `lock_timeout` (8s
for `authenticator`) is hit, so treat the window as an outage, not a slowdown: pick a quiet
hour, post the one-line notice, and keep it clear of the scheduled writers below.

### Writers during the window (nothing needs deleting)

Do not remove any webhook. What writes to the database, and what to do about each:

| Writer | During the lock | Handling |
|---|---|---|
| Slack, Zoom, Google Calendar and Mux webhooks (`app/api/webhooks/*`) | The handler's queries wait, then fail; the sender sees a 5xx | Do nothing: Slack and Zoom retry failed deliveries (confirm Mux and Google Calendar before the cutover), and the "nothing through webhooks alone" rule means the nightly reconciliation (`/api/reconcile/*`) re-imports anything missed. Optional: a maintenance switch in `proxy.ts` returning `503` with `Retry-After` for `/api/webhooks/*` makes the retry explicit |
| `pg_cron`: `send-prickle-checkins` (every 5 min), `send-member-reminders` (hourly) | A run during the lock fails or waits | Disable both just before (`SELECT cron.alter_job(jobid, active := false)`) and re-enable after; or start the window just after a tick |
| Vercel crons, nightly reconcile (02:00 to 03:15 UTC) | Same | Start the window after 03:30 UTC (or skip that night) |
| Members and admins using the app | Pages and actions error | The announced window; optional maintenance page |

### If the migration partially succeeds

Within one migration file it cannot: any error rolls the whole file back and production stays
on the old schema and old code. The one real "partial" state is **between phases**, since each
phase is its own migration. A later phase failing leaves the earlier phases applied, which is
fine only because each phase's app code ships with that phase; never apply a phase's migration
without its code. Two parts live outside the transaction and are not atomic: Storage object
moves through the Storage API (the `book-covers` objects) and the Vercel deploy. Run those
after the migration and make them re-runnable.

### If the migration works but the deploy fails

The old deployment keeps serving (Vercel does not replace it until the new one is ready), now
against the new schema. That mostly works, since the app talks to Postgres in strings, but it is
degraded: routes that validate with `.uuid()` reject every new id (so links to converted pages
fail), and code that mints a primary key itself (`randomUUID()` in `app/api/feedback`) stores an
old-format value. So **migrate first, deploy right after** (the CI order) is correct, but the
gap must be short and the deploy must not be able to fail late.

To get there for this change, do not rely on the normal push-to-main sequence:
- Build the new code as a preview deployment first, and run the unit and db suites against the
  rehearsed copy with it. A broken build is found before anything touches prod.
- Cut over by hand: disable the two `pg_cron` jobs, take a backup (Supabase point-in-time recovery marker, plus
  a `pg_dump` of the affected tables), run the migration, **promote the already-built
  deployment** (seconds, with nothing left to fail), verify, re-enable the jobs.
- Rolling back after the cutover means restoring the backup and promoting the previous
  deployment, losing any writes since. The mapping table is dropped at the end of the
  migration, so there is no reverse migration; keep the pre-cutover backup until the next
  phase.

## Phases

Converting a table rewrites the columns that reference it, in the same migration, so a mixed
schema is valid at every step. Tier 2 ids are never shown to a user, so converting them
later breaks nothing a person can see. What a later phase *can* still touch is internal:
`audit_log.entity_id` / `changes` for the tables in that phase, jsonb and text copies of
their ids, and anything keyed on the id. Each phase runs the same table-driven script and its
own checks (row counts equal, no orphans, no old uuids left for the tables it converted).

| Phase | Tables | Why this order |
|---|---|---|
| 1 | The 17 Tier 1 tables and every column that references them (about 50 `member_id`-style columns in Tier 2 tables) | Everything a user can see or copy. The `.ics` feed `UID`s are built from member, prickle and prickle-type ids (`lib/calendar-feed.ts`), all Tier 1, so subscribers re-subscribe once |
| 2 | Remaining Tier 2 tables in `public` | Internal only; mostly leaf tables, so each is a primary-key swap plus a default change |
| 3 | Bronze (18 tables) | Never shown to users; can wait or be skipped |

If a Tier 2 table later starts appearing in a URL or message, promote it to Tier 1 with a
hand-chosen prefix: one small migration for that table.

## Migration approach (forward migration, data preserved)

One new migration, numbered after checking every worktree for collisions (collisions are
silently skipped; see the migration-version-collisions memory).

1. Create `new_id(prefix)` (pgcrypto `gen_random_bytes` or `gen_random_uuid` as entropy
   source; map bytes onto the base58 alphabet; consider rejecting bytes >= 232 to avoid
   modulo bias).
2. For each table: add `new_id text`, backfill with `new_id('<prefix>')`, and record
   `(table, old_uuid, new_id)` in a **temporary** mapping table (dropped at the end).
3. Generate the FK rewrite from `pg_constraint` (not by hand), in dependency order, joining
   through the mapping. Rewrite the non-FK locations above the same way.
4. Drop dependent views/policies/functions, drop old PK and FK constraints, rename new
   columns to `id` / `<x>_id`, re-add PK and FK constraints (same `ON DELETE` actions),
   set defaults to `new_id('<prefix>')`, recreate everything dropped.
5. Delete the two prod test chat messages and related rows.
6. Verify inside the transaction: per-table row counts equal before and after, zero
   orphan FKs, zero remaining old uuids in jsonb/text, then drop the mapping.

Check row counts and the migration role's statement timeout first (the repo notes an 8s
limit for some Slack statements). If one transaction is too slow, batch the backfill of
the big bronze tables and keep the constraint swap in a single final step. Deploy the app
change and the migration together (CI pushes migrations before the Vercel deploy on main).

## Lessons from the phase 1 run

Things the rehearsals did not catch or that cost a round trip; do them again for phase 2.

- **Reload PostgREST's schema cache by hand.** The migration sets `session_replication_role =
  replica` so rewriting every id writes no audit rows and fires no triggers. Event triggers do
  not fire in replica mode either, so the trigger that tells PostgREST to reload after DDL stayed
  silent: production kept the old function signatures (`p_member_id uuid`) and every RPC with a
  member id failed ("function does not exist") until `NOTIFY pgrst, 'reload schema'` was run by
  hand. CI missed it because its PostgREST starts after the migrations. End the next migration
  with that NOTIFY.
- **Rehearse with the real app, not only SQL.** Loading a production data copy into a stack
  with the final schema, applying the migration, then running the app against it and opening a
  member page would have shown the stale cache. A sign-in for a scratch stack: create a user
  with the auth admin API, add a `user_profiles` admin row, sign in with a password, and send
  the session as the `sb-<host>-auth-token` cookie (`base64-` + base64url of the session JSON).
- **Regenerate generated SQL from the final schema, and fix the generator, not the output.**
  The function rewrites were generated from the live definitions; a hand fix to one function
  (a `::uuid` cast on a Tier 2 column) came back the next time the section was regenerated.
- **Test the seed with triggers on.** `supabase/seed.sql` runs after the migrations with
  triggers active, so a function the migration broke can fail only there. A local check that
  runs the migration and the seed in one transaction hides it, because the migration's
  `SET LOCAL session_replication_role` is still in force; `RESET` it first.
- **Main moves under you.** Over three days about 20 migrations landed, mostly chat. Each one
  can add a trigger or function that names a converted column, and each needs the generated
  function section and the pgTAP fixtures refreshed. Freeze schema-changing merges between the
  last rehearsal and the run.
- **Plain id columns without a foreign key** (`audit_log.member_id` and similar) can hold ids of
  rows that were deleted; those stay as they were, and the in-migration check only insists that
  ids still present in the map were converted.
- **Backups:** PITR was off until the night of the run; turn it on before a migration like this.

## Rule: Tier 2 ids are never exposed

**A Tier 2 table's id must never reach a user.** That means no page URL, no link in a Slack
message, email, notification or calendar feed, no id a person can copy out of an image or
download link, and no id in an export or download (CSV, reports) or in an API consumed by anything other than
our own client (a public or partner API, an outbound webhook). Admins count as users: an admin
page URL is exposure, since URLs get pasted into Slack and support threads. Tier 2 ids stay
internal (joins, logs, and the `fetch` calls and request bodies between our own client and
server, even in admin code). Today every `app/api` route is of that internal kind; the first
public or partner API is the moment to re-check what it returns.

**If a feature needs to expose one, elevate the table to Tier 1 first**: pick a readable
prefix (Prefixes section), add it to the Tier 1 table, and convert it before the feature
ships. Once the scheme has landed that is a small migration (`new_id` default, rewrite of the
id and its references, the same checks as a phase). Before it has landed, add the table to
Phase 1. The exposed form is what matters, not the column: if you would show the id, use
Tier 1, or show something else (a slug, a token) instead.

Reviewing a PR: if it adds a route param, a link, a notification `url` / `ref` or a response
field built from a Tier 2 id, ask for the elevation.
