# Landing pages (the page builder)

Status: **slice 1 built**: the model, the editor, the blocks, publishing with history, the public route. The opt-in form block (sign-ups into Kajabi) and the import of Kajabi page exports are built too; the rest is in `docs/TODO.md`, "Landing pages (page builder)".

Kajabi has landing pages with a block editor. The Hub has the same, on [Puck](https://puckeditor.com) (`@puckeditor/core`, MIT): a page is Puck's JSON, `{ content: [...], root: { props } }`, and the same React components render in the editor's canvas and on the public page. We chose an open source editor over writing our own: the drag and drop, the outline, undo and redo, the viewport preview and the iframe canvas are Puck's; the blocks, the shell around it, the model and the rules are ours.

Puck 0.24 peers on React 18 or 19 and was checked against this app's Next 16 and React 19: the editor is a client component, and the public page renders through Puck's `rsc` entry (the package's `react-server` export), which has `Render` and no editor code. Nothing about it needed patching. The editor needs a real browser (it uses dnd-kit and `ResizeObserver`); its tests mock Puck, and the blocks are tested on their own.

## Model

- `landing_pages` (`lpg_`, Tier 2): `slug` (unique among live pages), `title`, `status` (`draft` or `published`), `draft_data`, `published_data`, SEO title and description, a social image (a media asset), `first_published_at`, `published_at`, soft delete (`deleted_at`). `landing_page_versions` (`lpgv_`): one row per publish, insert-only.
- **Autosave writes `draft_data` only.** Publishing is a separate, explicit step: `publish_landing_page(id)` copies the draft to `published_data` and writes a version in one transaction (a `SECURITY INVOKER` function, so row-level security applies). `restore_landing_page_version(id)` puts a version into the draft and does not publish it. The editor's "Reset to published" button (`<LifecycleButton action="reset">` (`components/LifecycleButton.tsx`), shown only while the draft differs from the published copy) copies `published_data` back into the draft through the repository (`resetDraftToPublished`); nothing goes live and no version is written. Taking a page down sets the status back to `draft`; the published copy and the versions stay.
- **Ids are never in a URL.** Page ids are Tier 2 (`docs/SHORT_IDS_PLAN.md`), so the public address is `/p/<slug>` and the editor is `/admin/pages/<slug>` (an admin URL counts as exposed). `new` is a reserved slug. The ids travel only between our own client and server actions and are checked at the door (`isLandingPageId`).
- **Row-level security: admins only.** There is no anon policy and no anon grant. A signed-out visitor never touches the table: the public route reads a published page on the server with the service role (`getServiceRepos().landingPages.published(slug)`), and that one method returns a page only when it is published and not deleted. We chose this over a narrow anon policy because the only way to leak a draft is a bug in one method with a test, not a policy that could be widened by a later migration. Community managers have no access (opt-in rule for new roles).
- **Audit: the intent, not the keystrokes.** The row trigger leaves `draft_data`, `updated_at` and `updated_by` out of its `WHEN`, so autosave writes nothing. Create, publish, unpublish, restore (`restored_at` changes), rename, address and SEO changes, and delete are audited as the admin. The two documents are logged as changed, never with their content (the `redact` argument); the versions hold the content. `supabase/tests/database/landing_pages.test.sql` tests both halves.

## The editor

`/admin/pages/<slug>` (`app/(admin)/admin/pages/[slug]/LandingEditor.tsx`) puts Puck in our shell: our header replaces Puck's (back, title, **Saved / Unsaved changes / Saving…**, device buttons, undo and redo from Puck's history, Details, History, Preview, Publish), and the Puck panels follow the theme through CSS variables in `app/globals.css`.

- **Autosave**: 1.2 s after typing stops, the draft is sent to `saveLandingDraft`; a failed save says so and retries every 5 s; Ctrl/⌘ S saves at once; leaving with unsaved changes asks first. "Changes not published yet" shows on a live page whose draft differs.
- **Publish** opens a dialog: it runs the accessibility checks (below), lists what must be fixed or checked, and only then publishes. The server runs the same checks and refuses on errors. Publishing sends the draft the editor shows, so nothing typed a moment before is left out.
- **Versions**: History lists the last 20 publishes; Bring back replaces the draft (after a confirm), and the editor reopens on it. It never goes live until published again.
- **Details**: title, address (a warning when the page is live), search title and description, the picture shown when shared.
- **Preview** opens `/admin/pages/<slug>/preview`, the draft rendered as a visitor would see it; drafts never render on the public route.
- Device preview uses Puck's viewports (desktop 1280, tablet 768, phone 390). Blocks lay out with container queries (`@container` on the page frame, named sizes), so the phone preview reflows as a phone does.

## Accessibility checks (`lib/landing/a11y.ts`)

Errors stop a publish: an empty page, no page title (an `h1`), a picture with no description (unless marked as decoration), a button or card button with no usable link, a countdown with no date, a video from a host that isn't allowed. Warnings are shown and let through: more than one `h1`, a skipped heading level, vague link text ("click here"), text over a picture with no shade, a video with no title. Contrast cannot fail by construction: backgrounds come from a short list of theme colours, each with the text colour that is readable on it (`components/landing/theme.ts`), and a picture's text colour follows its shade. Free colours are deliberately not offered.

## Pictures and public assets

Pictures come from the media library through the same `MediaPicker` (surface `landing_page`) and are referenced by asset id in props named `*AssetId`. A signed-out visitor is served only assets marked `is_public` (`docs/MEDIA_LIBRARY.md`), so **publishing marks every asset the page uses (and its social image) public**, through the admin's own client. Unpublishing does not turn it back (the asset may be used elsewhere); a sweep for assets no page shows is in the TODO. Pictures are requested at the existing presets, which crop; see the TODO for presets that keep the shape.

## Safety

- Rich text is TipTap, stored as HTML in a prop named `html`, and cleaned to an allowlist (`lib/landing/sanitize.ts`: paragraphs, headings, lists, quotes, emphasis, links; no images, styles, classes, scripts or handlers) on every save and **again before a public render** (`LandingRender`), whatever the database holds. Never raw HTML.
- A prop named `href` or `url` is a link and goes through `safeHref` (http, https, mailto, a path on this site, an anchor; nothing else) on save, on render, and in the block itself.
- Video accepts only YouTube, Vimeo and Mux player links; the iframe address is built from the extracted video id, with `sandbox`, so a pasted link can't point the frame elsewhere (`parseEmbed`).
- Sections can fade in; it is a CSS animation inside `prefers-reduced-motion: no-preference`.
- The public page sends nothing to an analytics provider and records no visitor. The site's consent banner and Google Analytics rules apply as on every page. There is no anonymous usage event yet (TODO).

## Blocks

Section (background colour or picture with a shade, width, space, optional white card, fade in; holds other blocks), Columns (two or three side-by-side areas that each hold blocks, see below), Text (rich), Heading, Button (solid or outline, pill or rectangle, three colours), Buttons (one to three of those side by side in a row that wraps when the container is narrow, left or centred, small or medium gap; built from the same `buttonClasses` and `safeHref`, a button with no usable link shown disabled; the "Links" group), Image, Image and text (reversible), List (emoji or check markers), Testimonials, FAQ (native `details`), Countdown (an instant stored in UTC, entered as a wall time in `ORG_TIMEZONE`; at zero: a message, nothing, or zeros; fixed-size cells, no layout shift, read as one labelled timer), Card grid (image or emoji icon, title, description, price, button; up to 2, 3 or 4 columns by the room), Link list, Divider, Spacer, Video. Four ready-made blocks (the "Ready-made" group) save assembling the common ones from Section, Heading, Text and Button; they are static, with no data behind them:

- **Hero**: headline (the page title, `h1`, by default; `h2` when the page already has one), a line under it, a main and an optional second button (`primary` and `secondary`, each `{ label, href }`, so `href` is cleaned wherever it sits), an optional picture behind the words (with a shade, like Section) or beside them (needs a description, or "decoration only"), on a theme colour, left or centred, and "Space above and below" (`padding`: none, small, medium, large; unset means large, the original `py-16 @split:py-24`, so pages saved before the option are unchanged).
- **Steps**: two to five numbered steps (title, short text) under an optional heading; stacked on a narrow page, side by side with room. Titles are `h3` under its own heading and `h2` without one, and the checks count them the same way.
- **Stats**: two to four figures with a label, typed by hand (a description list). Live figures from the Hub are the Outcome numbers block (see "Live data" below).
- **Call-to-action banner**: heading, a line and one button on a theme colour (not the page colour); the button flips to the light style on a dark band.

The "Homepage" group (`components/landing/homepage-blocks.tsx`, see "Homepage blocks" below): **Announcement strip**, **Schedule panel**, **Outcome numbers**, **Finisher cards**, **Timeline**, **Week strip**, **Finish-line cards**, **Plan phases**, **Journey map** and **Coming up**.

**Columns** (`count` 2 or 3, `gap`, `verticalAlign` top or middle; slots `col1`, `col2`, `col3`; palette group "Layout"): one column on a narrow container, side by side from `@split`. It has no background or text colour, so it inherits the Section around it. Slots are declared in `SLOTS` (`components/landing/config.tsx`) and as `slot` fields in the editor config; the migrations, `sanitizeLandingData`, `collectAssetIds` and `checkLandingPage` find nested blocks by their shape, so any slot is covered (tested for Columns inside a Section). Switching three columns to two keeps what was in the third: it is not shown and not checked until switched back (its pictures are still made public on publish). Every slot is rendered with `flow-root` (`SLOT_CLASS` in `blocks.tsx`): Puck draws a slot's dashed outline around the slot's own box, and a first Heading's `my-3` used to collapse out of it, so in the editor the heading touched the outline. Not offered to the AI builder (`AI_BLOCKS`); a page that has one keeps it exactly when the AI revises the page.

**Space.** Hero and Outcome numbers have "Space above and below" because each is a band of its own; their default (Hero large, Outcome numbers medium) is what they drew before, so no stored page changes. The other Homepage blocks sit inside a Section, whose own "Space above and below" is the control, and the Announcement strip is a one-line bar, so they have none.

**Reordering items.** Blocks drag on the canvas; the items inside a block (a week's days, a schedule's sessions, Finisher cards) are array fields and reorder in the right panel by the grip handle on each item (their `getItemSummary` names them). The Homepage blocks' array fields are standard Puck array fields with a summary and no `disableDragging`-style option, so they all reorder there.

**Colours and dark mode.** The page follows the theme (the app's setting in the editor, the visitor's system setting on the public page). Blocks do not write `dark:` classes or slate colours: they use semantic tokens (`bg-page`, `bg-card`, `bg-tile`, `text-ink`, `text-ink-muted`, `border-accent`, `text-accent-ink`, `text-warm`), whose light and dark values are defined once in `app/globals.css` (`--lp-*`) and named in `tailwind.config.ts`. Change a value there and every page follows. White, cream, blush and mist bands stay light in dark mode: theme.ts marks them `landing-light`, which sets the light values again inside the band. Plum, cream and the other brand bands are fixed colours and do not change with the theme. `tests/lib/landing-theme-tokens.test.ts` fails on a `dark:` variant or a slate colour in a block.

Text colours in all four follow theme.ts; there is no colour picker. The page frame has optional header (logo, links) and footer (text, links) as root fields.

### Homepage blocks

Built for the public homepage (the "Homepage" starter). They are **typed by hand in the editor**, and three of them (the Announcement strip, the Schedule panel and Outcome numbers) can instead be **live from the Hub**, see "Live data" below. No Finisher is read from the Hub: THE END is not recorded anywhere yet.

- **Announcement strip** (`text`, `buttonLabel`, `href`, `tone` gold, plum or charcoal): a bar above the page, dark text on gold, a dot that pulses only inside `prefers-reduced-motion: no-preference` (`.landing-pulse` in `app/globals.css`, shared with the "live" chip). **Schedule panel** (`title`, `zoneLabel`, `rows`: `time`, `title`, `status` text, `state` live, soon or open, `host`): a light panel with its own colours; the starter puts it beside the pitch, in the second of two Columns in a plum Section. **Outcome numbers** (`padding`, `items`: `value`, `label`, `note`): a full-width white band with a gold top stripe; numbers `text-plum-900` and labels `text-ink` are set on the block, never inherited. **Finisher cards** (`items`: `imageAssetId`, `alt`, `name`, `kind`, `dayOne`, `theEnd`, `linkLabel`, `href`; `more`: `label`, `href`): book-cover shaped photos, a placeholder without one. **Timeline** (`heading`, `intro`, `items`: `when`, `title`, `text`; `closing`). **Week strip** (`subtitle`, up to 7 `items`: `label`, `emoji`, `text`, `note`; two columns on a narrow page). **Finish-line cards** (up to 3 `items`: `title`, `program`, `text`, `durationLabel`, `durationPercent`, `buttonLabel`, `href`) and **Plan phases** (`heading`, `items`: `title`, `text`, shaded light to deeper plum). **Journey map** (`stages`: `name`, `helps`, `current`; `offer`: `status` open, waitlist, soon or dates, `statusLabel`, `title`, `text`, `buttonLabel`, `href`; `compare`: `label`, `href`; a column on a narrow page) and **Coming up** (`heading`, up to 4 `items`: `kind`, `title`, `when`, `availability`, `status`, `linkLabel`, `href`).
- **Links are `href`.** Only a prop named `href` is cleaned on save, so a block with several links keeps each in an object (`more`, `offer`, `compare`) or an item, each with its own `href`.
- **Heading levels.** The block's own heading is an `h3` (so the page's section heading above it is the `h2`), and titles under it `h4`; `lib/landing/a11y.ts` counts them the same way. Errors: a Finisher photo with no description, a button or link with words and no address. Warnings: vague link words.
- **Gold** is one fixed brand pair in `tailwind.config.ts` (`gold`, `gold-ink`), like cream and blush: it does not change with the theme, and the dark text on it is about 11:1.
- **Not offered to the AI builder**: none is in `AI_BLOCKS`; adding one is a decision (what the model may invent for a Finisher card is the first question).

### Live data

Three Homepage blocks have a `source`: "Typed in by hand" (`manual`, the default, so no existing page changes) or "Live from the Hub" (`live`). Blocks stay presentational and never fetch: the server resolves what they show and hands it to them in a render-only prop named `live`.

- **Where it is resolved.** `withLiveData(data)` (`lib/landing/live-server.ts`) runs in `app/p/[slug]/page.tsx` and in the admin preview, just before `LandingRender`. `resolveLiveBlocks` (`lib/landing/live-data.ts`) walks the page (slots and zones included), finds the live blocks, loads what they need once (all figures from one pass, the schedule once, in parallel) and returns a **copy** with `live` set. It is never written back: the editor and the save and publish actions only ever hold the stored page, and a `live` prop found in stored data is dropped before the render. The editor's canvas (a client component) fetches nothing: it shows the typed values and says "live shows on the published page" next to the source switch.
- **Failure.** A loader that throws is caught and logged as a short code (`landing_live_stats_failed`, `landing_live_schedule_failed`, with the error's name and nothing else), and its blocks render their typed values: never an error on a public page. Nothing to show is different from a failure: a figure that is zero stays typed; a schedule with nothing coming up shows the panel's "when nothing is coming up" line, or the strip's `whenNone` choice (nothing, or its typed line).
- **Caching.** Reads use the service-role repositories and are wrapped in `unstable_cache` with `revalidate` 60 and the tag `landing-live` (`LIVE_CACHE_SECONDS`), so the public page costs the database at most one aggregate a minute per set of figures, however many visitors there are. The real "now" is applied after the cache, so "In 12 min" is right within the minute.
- **Privacy.** Counts, sums, public titles and times only; never a name, id, link or per-person row, in the page, a log, analytics or Sentry. Members who hide themselves from Who's coming are counted like everyone (an aggregate does not identify anyone).

**Outcome numbers.** Each item is typed or bound to a figure from the registry (`lib/landing/live-stats.ts`, `LIVE_STATS`): the item has `source`, `stat` (a select listing every registry label), the typed `value` (also what shows if the live figure is missing) and an optional `label` (empty means the figure's own caption). Live items get a small "live" note (a dot that pulses only when motion is allowed) that the block's "Show a small live note" switch turns off. Figures are floored to two significant digits and never overstate (`friendlyFloor`: 891 shows as "890+", 54,700 as "54,000+", under 100 exactly); a figure of zero is not shown.

| Key | Definition | Caption |
|---|---|---|
| `hours_30d` | Hours written together in prickles: each `prickle_attendance` stay that began in the trailing 30 Eastern days, clipped to its prickle (`least(leave, end) - greatest(join, start)`), summed | hours written together in prickles in the last 30 days |
| `prickles_30d` | Distinct prickles that had at least one stay in those 30 days | prickles with writers in them in the last 30 days |
| `writers_7d` | Distinct members with a stay that began in the trailing 7 Eastern days | writers joined a prickle in the last 7 days |
| `words_30d` | `writing_progress_entries` with `measure` words and `mode` delta, not deleted, by Eastern entry date over 30 days. Never `set_total` (a project's running total) | words logged by members in the Hub in the last 30 days |

Windows are Eastern days (`ORG_TIMEZONE`): "30 days" is today and the 29 Eastern days before it, from Eastern midnight, across a daylight saving change. **Adding a figure** is one entry in `LIVE_STATS` (a label for the editor's list, a caption, the data it `needs` (`stays` or `words`, or a new input in `loadLiveStats` with its repository method) and `compute`), plus a case in `tests/lib/landing-live-stats.test.ts`; the editor's list, the resolver and the block pick it up from the registry.

**Schedule panel.** `source` live lists the next public prickles (`hoursAhead`, default 24, at most 144; `maxRows`, default 5, at most 6; `emptyText` when there are none): the time in `ORG_TIMEZONE` (the weekday too when it is not today; the panel names the zone, "Times in ET", unless a zone note was typed), the title cleaned like the Events page (`cleanEventTitle`) and with a calendar's "w/ Name" host marker removed, and a status: **Live** (running), **In N min** (starts within 60 minutes), or none (open). Which prickles are public: the **type** must be announced publicly (`prickle_types.announced_publicly`, the audience chain in `docs/CALENDAR_EVENTS.md`); a prickle with no type or any other type never appears, and the Event type (an event's schedule, which has its own flag) is left out by the repository. There is **no joiner or attendee count per prickle**: the only number is "N writing now" on a running prickle, shown when N is 2 or more (else "Live"), taken from `loadLiveRoom` (members and guests in the Zoom room, hidden or not; no names leave that call). `hostStyle` is "none" (default) or "experience": "An experienced host" when the host has held 100 or more past prickles (`EXPERIENCED_HOST_PRICKLES`; about half of past prickles have no host recorded, so counts are a floor). **No host names are shown anywhere on the public page**; a first-name style is undecided (`docs/TODO.md`) and not implemented. A live panel's rows replace the typed ones, so a typed `host` line applies only to a typed panel.

**Announcement strip.** `source` live says "A prickle is on now" while a public prickle runs, else "Your next prickle starts in N minutes" for the next one (or "today at 3:30 pm ET", "tomorrow at ..." from an hour out), within 24 hours; with none, nothing (or the typed line, `whenNone`). The button's `href` stays typed: the Hub supplies no join address and no Zoom link.

**Not live**: Finisher cards (THE END is not recorded), Coming up, Timeline, Week strip, Finish-line cards, Plan phases and Journey map stay typed. The blocks with live data are not offered to the AI builder (`AI_BLOCKS` is unchanged).

**Tests.** The figures and rounding (`tests/lib/landing-live-stats.test.ts`: clipped stays, `set_total` and deleted entries ignored, Eastern midnight and daylight saving), the schedule (`landing-live-schedule.test.ts`: non-public types excluded, the host threshold, "writing now" at 2 or more, no names), the resolver (`landing-live-data.test.ts`: only live blocks touched, nothing saved, fallback on failure), the server entry and its cache setting (`landing-live-server.test.ts`), the blocks and editor fields (`tests/components/landing-live-blocks.test.tsx`), the public page and preview (`tests/components/pages/landing-pages.test.tsx`), and the repository contracts for `staysJoinedBetween`, `wordsLoggedBetween` and `countHostedBy(before)`.

### Adding a block

1. A presentational component in `components/landing/blocks.tsx`: no hooks or browser APIs (a client part gets its own file, like `Countdown.tsx`), container-query layout from the named sizes, links through `safeHref`, pictures from `*AssetId` props with the alt text from a prop.
2. Its default props in `BLOCK_DEFAULTS`, its label in `BLOCK_LABELS`, its renderer in `RENDERERS` and a category in `renderConfig` (`components/landing/config.tsx`).
3. Its fields in `components/landing/editor-config.tsx` (every field has a label; `image(...)` is the media picker, `richText(...)` the TipTap field, `dateTime(...)` a zoned date).
4. If it can be wrong in a way a visitor can't work around, a rule in `lib/landing/a11y.ts`.
5. Tests: the block in `tests/components/landing-blocks.test.tsx`; the config test already fails for a block with no fields.

### Changing a block's props

Stored pages (draft, published copy, every saved version) keep the props they were saved with, so renaming or reshaping a prop needs a migration step, not just a code change. Append a step to `LANDING_MIGRATIONS` in `lib/landing/migrations.ts` (`version` is the next number; `blocks` maps a block name to a function from old props to new; `root` does the same for the page frame). Never edit or remove an earlier step, and write each one so running it twice changes nothing more.

- The document carries `schemaVersion` (unmarked data is 0). `normalizeLandingData` runs the steps above the document's version wherever stored data is read, so the editor, the public page, preview, restore and copy all see current props, and the next save writes them back with the new version. Blocks nested in a slot (a Section's `content`) and in zones are migrated too.
- The save and publish actions stamp what the editor sends as current (`stampLandingVersion`), because the editor only ever holds migrated data and Puck may drop the marker.
- Adding a prop with a default needs no step (the block's `defaultProps` cover it); only renames, removals and changes of meaning do.
- Tests: add a case for the step to `tests/lib/landing-migrations.test.ts` (old shape in, new shape out, run twice).

## Build with AI

On **New page**, an optional "Describe the page" box turns the admin's description into a draft (`createLandingPageWithAi`, event `landing_page_ai_built`; `lib/landing/ai.ts`). It is our own call to the Claude API, not Puck Cloud's AI (which needs Puck Cloud). The key is `ANTHROPIC_API_KEY`; the host and model are in `app.config.ts` (`anthropic`); without the key the box is disabled.

- **Only the description is sent**: no member data, no existing page, no pictures. This is staff-written marketing copy; the rule that members' writing never touches AI still holds, and nothing a member wrote can reach this call (the Kajabi import, which maps exports deterministically, is unchanged and has no AI).
- **The answer is never trusted.** The model must call one tool, `build_page`, with a list of `{ type, props }`. `cleanGeneratedBlocks` keeps only the blocks in `AI_BLOCKS`, only the props a block has in `BLOCK_DEFAULTS`, checks each value against the default's kind and the option lists, caps lists and nesting, then `sanitizeLandingData` cleans links and rich text like anything an admin types.
- **Blocks the model is not offered**: those needing something it cannot know (Image, Image and text, Countdown, Video, Sign-up form) and Testimonials (it would invent quotes). Pictures are added in the editor. Card grid is offered without pictures, prices or buttons (icon, title, description; `SHAPES` in `lib/landing/ai.ts`), and a grid that has pictures is kept as it is on a change. Requests use Sonnet at medium effort with adaptive thinking (`output_config.effort`), and the model also returns a one-line summary shown in the tab; on a change, only problems the change added are listed. Adding a block to the builder does not offer it to the model: add it to `AI_BLOCKS` and `ENUMS` on purpose.
- **Always a draft.** The page is created only if generation worked (no empty page is left on a failure), is never published, and the publish checks still apply: a button the model left without a link stops a publish until filled in. The form says to check every fact and link.
- **The AI tab in the editor** (`[slug]/AiPanel.tsx`, a Puck plugin in the left rail beside Blocks and Outline) has two modes. **Add** sends only the description (`generateLandingBlocks`) and appends the blocks. **Change** (`reviseLandingBlocks`, `reviseLandingPage`) also sends the page's blocks, so the text and settings go to the model: never picture ids, and never anything but the page itself. The model returns the whole revised list; blocks keep their `id`, and `cleanGeneratedBlocks(raw, current)` merges by id, so only the props the model sent change and pictures and other settings stay. Blocks it cannot write (Image, Video, Testimonials...) are marked `locked`: kept exactly or dropped, never rewritten. Both modes put the result in with one `setData` that records history (one undo step) and read the page when the answer arrives, so edits made while waiting are kept. Nothing is saved by the action: autosave takes it from there.
- **Tests** mock the model call (`tests/lib/landing-ai.test.ts`, `landing-page-actions.test.ts`, `tests/components/ai-panel.test.tsx`); nothing in CI calls the API. Not verified: a live call against the real API (needs the key in an environment).

## Starters

**New page** has a "Start from" choice: a blank page, or a ready-made draft from `lib/landing/starters.ts` (`LANDING_STARTERS`, `starterData(key)`). A starter is the same Puck JSON the editor saves, written once (the first, "Homepage", is the reviewed design built from the Homepage blocks: strip, an opening plum band (a Section with two Columns: the h1, line and a row of two buttons (a Buttons block) on the left, the schedule panel on the right, so no Hero block), outcome numbers, Finishers, a day in the house, the first week, finish lines, journey map, coming up and a sign-up) and copied into a new draft by `createLandingPage({ title, slug, starter })`; from then on it is an ordinary page. It is never published, holds no picture and no link that isn't a path on this site, and leaves what only a person knows (button links, the Kajabi form id of the sign-up, names and dates in [brackets]) empty, so the publish check asks for it. Choosing a starter turns off "Describe the page". **Replace with starter** puts a starter on a page that already exists (History, "Start over from a starter"; `replaceLandingDraftWithStarter`, event `landing_page_starter_applied`): after a danger confirm it keeps the current draft as a `before_starter` version (shown as "Your draft before starting over", restorable with Bring back like any), then replaces `draft_data` only, so the published copy, title, address, search settings and the other versions are untouched and nothing goes live. It stamps `landing_pages.starter_applied_at`, which makes it one audit entry without the content (like `imported_at` for an import). It saves what is typed first, so the kept draft is the one on screen, then reloads the editor on the new draft. It is its own kind, not an import: `landing_page_versions.kind` allows `published`, `before_import` and `before_starter`. `tests/lib/landing-starters.test.ts` fails on a block or prop the builder lacks, a duplicate id, a picture, HTML the sanitizer would change, or a second `h1`. To add one: a content function and an entry in `LANDING_STARTERS`.

## Opt-in forms

The Sign-up form block (name, email, optional Instagram handle, button label, a line under the button, a success message or a thank-you page) sends sign-ups to Kajabi. The decision (owner) is that during the migration the mailing list, tags and automations stay in Kajabi, so **the Hub stores no submission**: there is no table, and nothing about the person reaches a log, an analytics event or Sentry.

- **How Kajabi takes it.** Kajabi's public API: `POST /v1/forms/{id}/submit` (JSON:API, bearer token) with `name` and `email` (required) and optional `custom_1` to `custom_3`; Kajabi checks deliverability and does the rest of what the form is set up for (double opt-in, tags, offers, sequences, automations, webhooks). It uses the same client credentials as the Kajabi imports (`KajabiClient.submitForm`, no new variable, no new host). The reference is at `help.kajabi.com/api-reference/forms/submit-form`. Kajabi's other documented way, the one-line JavaScript embed, was not used because it brings Kajabi's own styling and scripts onto our page; it remains the fallback if the API ever stops accepting submissions.
- **The block names a form, not an address.** "Kajabi form" is the form's id (Marketing, Forms), stored in the page data (`kajabiFormId`); no id or host is in code. The Instagram handle goes to the Kajabi custom field the block names (`instagramField`), or the question is left out (the default).
- **The relay** (`POST /api/landing/opt-in`, public): the browser sends the page address, the form id and the fields; the server reads the **published page** and forwards only if that page really has an opt-in block for that form, so the route can't be used to post to any other form on the account. A hidden field is the honeypot (a bot gets a normal success and nothing is sent); two rate limits through `RateLimitRepository` (per visitor address and per form); calm messages. The visitor's address is the rate-limit key and nothing else.
- **`OptInDestination`** (`lib/landing/opt-in.ts`: `submit(target, fields)`) is the extension point: `KajabiOptInDestination` is the only implementation, chosen in `lib/landing/opt-in-destination.ts`. A Hub destination (or a dual write) plugs in there; the migration steps are in `docs/TODO.md`.
- **Editor and preview** send nothing: the form reads the page address in the browser and is disabled, with a note, anywhere but `/p/<address>`.
- **Verified and not.** Verified from Kajabi's documentation: the endpoint, auth, body and side effects. Not verified: a live submission (never made, so nothing was added to the real account), which custom field the owner's Kajabi has set up (the block defaults to leaving Instagram out), and the exact status for a refused address (Kajabi documents only 401 and 403; the destination treats 400 and 422 as "check your details" and anything else as "try again").

## Importing from Kajabi

Pages has a chevron beside **New page** with **Import from Kajabi**. The admin uploads a Kajabi page export (the zip from a page's Export) and gets an unpublished draft. Kajabi has no content API, but the export is structured, so the conversion is a table, not a model: `lib/landing/kajabi-import.ts` (`mapKajabiPage`, pure, tested on made-up fixtures) maps the export's `config/settings_data.json` to Puck JSON, and `lib/landing/kajabi-import-service.ts` (`importKajabiExport`) does the rest. There is no AI in it, and none may be added: members' writing must never touch AI, and this keeps the product code free of it. The route is `POST /api/admin/landing-pages/import` (a route, not a server action, because the upload outgrows an action's body limit; it uses `requireAdminAction` and `withAction` all the same, event `landing_page_imported`).

- **Mapping.** A section becomes a Section (background colour to the nearest we offer, width from the most common block width, a boxed card when a text or form block has its own background, a background picture with a dark shade). Text blocks: h1 to h4 become Heading blocks, a rule a Divider, the rest cleaned rich text. Call-to-action blocks become Buttons (colour to the nearest of plum, light and brown; Kajabi paths like `/resource_redirect/...` are resolved against `kajabiSiteUrl` in `app.config.ts`, which keeps working while Kajabi stays). Form blocks become the Sign-up form. The header logo is the first picture of the page; the footer's copyright line is the footer. A block hidden in Kajabi is not imported but is listed with its link.
- **What the export lacks.** A page title (the admin types it), the Kajabi form's name and fields (only its id, shown in the report; the form is chosen by name in the editor and nothing is hard-coded), whether the form asks for an Instagram handle, fonts, exact spacing, "Powered by" and anything a block does at runtime. These show up as "To do in the editor" or "Approximated" on the results screen.
- **Not handled yet.** Block types with no counterpart are left out and named: countdown, card, link list, video, offer, pricing, feature, social icons, embedded code, carousels, and the theme's popups (`docs/TODO.md`, "Landing pages: import the existing Kajabi pages"). A page that is not exported cannot be imported; there is no scraping.
- **The zip is untrusted** (`lib/landing/kajabi-zip.ts`): read in memory, never written to disk or run; at most 4 MB uploaded (Vercel's request limit is 4.5 MB), 1000 entries, 2 MB of settings, 8 MB per image, 24 MB unpacked in all, counted as each entry inflates (a zip bomb stops at the limit); a name with `..`, a leading `/`, a backslash or a drive letter refuses the whole archive; entries other than the settings and `assets/` images are never inflated, so a symlink or a script in the archive is inert. Pictures named in the export come from the archive or, for an upload path, from the Kajabi picture host (`kajabiPhotoHosts`) through the pinned fetch and nowhere else; each goes through the media library's image checks. All text and HTML pass `lib/landing/sanitize.ts`.
- **Idempotent.** The export has no page id or title (its file name carries a number that differs per export), so `landing_pages.import_key` is made from ids it does carry: `kajabi:<first section>:<earliest block id>` (block ids are creation timestamps and stay when a page is edited). Importing the same page again finds the page by that key and replaces only the **draft**: never the published copy, versions, title, address or SEO, so a live page stays as it is until someone publishes. The results screen says "Created a draft" or "Updated the draft". A page cloned in Kajabi keeps its blocks' ids and so shares a key with the original; that is why the admin is asked to confirm when the title typed differs from the page found.
- **Unpublished edits are protected.** If the draft was edited after the last import (`updated_at` later than `imported_at`), or differs from the live page, or the title typed isn't the page's, the import writes nothing and asks ("this will replace your unpublished changes"). On a yes, the old draft is first kept in the page's history as a `before_import` version (`landing_page_versions.kind`), shown in Version history as "Your draft before an import" and restorable with Bring back like any version. `imported_at` changes on each import, so each is one audit entry without the content (autosave stays unaudited).
- **Tests.** The mapper on synthetic fixtures (`tests/lib/landing-kajabi-import.test.ts`), the zip limits (`landing-kajabi-zip.test.ts`), the service with the in-memory repositories (create, update, published copy and versions untouched, confirmation, before-import version and restore: `landing-kajabi-import-service.test.ts`), the route, the dialog, the repository contract both ways and pgTAP for the audit and the key.
