# Data Access Layer: Repository Catalog

> **Status:** living. **Last reviewed:** 2026-11-20. Review: yearly. Kept up to date with the code; if it is wrong, fix it.

The rule and the conventions are in `.claude/rules/data-access-layer.md` (loaded when you touch `lib/data/`, API routes or actions). This is the catalog it points to: every table or API that has a repository in `lib/data/`, with the rules specific to each. A table with a repository is queried only through it. The page builder's `landing_pages` and `landing_page_versions` are on `LandingPageRepository` (`lib/data/landing-pages.ts`: admin-only; the signed-out `published(slug)` read runs with the service role and returns only a published, undeleted page; autosave is `saveDraft`, which is not audited; publish and restore are one database function each; see `docs/product/LANDING_PAGES.md`). The site template shared by website pages (`landing_site_template`, one row) is `LandingSiteTemplateRepository` (`lib/data/landing-site-template.ts`: admin only; `published()` is the signed-out read and runs with the service role; the draft is `saveDraft`, which is not audited; see "Site template" in `docs/product/LANDING_PAGES.md`). A template is a page of kind `template` on the same repository (`list(kind)`, `usableTemplates`, `usableTemplateData`; see "Templates" in `docs/product/LANDING_PAGES.md`). Writer profiles (`writer_profiles` and `writer_profile_handles`) are on `WriterProfileRepository` (`lib/data/writer-profiles.ts`: a member reads and changes their own page through their own repositories, and cannot write the handle; the handle is `setHandle`, one database function with the service role; everything a visitor reads (`publicByHandle`, `previewOfMember`, `publicHandles`, `publicCount`) runs with the service role and returns `PublicWriterProfile`, which holds only the fields meant to be public, built in one place; the contract test runs against the in-memory twin and Supabase; see `docs/product/WRITER_PROFILES.md`). `tests/lib/data-access-layer.test.ts` fails on a new direct query and lists the files still to move.

the status tables `member_hiatus_history`, `member_status_overrides`, `member_join_date_overrides` and `member_profile_overrides` (`lib/data/member-status-overrides.ts`, `MemberStatusRepository`: hiatus windows, gift/special overrides, legacy join dates and the profile fields members edit; the status derivation and the members processing read them through it), the Bronze Kajabi and Stripe billing data (`kajabi_contacts`, `kajabi_customers`, `kajabi_purchases`, `kajabi_offers`, `stripe_customers`, `stripe_products`, `stripe_subscriptions`, `stripe_invoices`, `stripe_charges`; `lib/data/billing.ts`, `BillingRepository`: reads, and the imports' writes plus `kajabi_members` and `subscription_history`; only `lib/courses/process.ts` still reads purchases and customers through `fetchAllBronzeRows`, which the guard test does not see), `prickle_attendance` (`lib/data/attendance.ts`), `prickles` and `prickle_types` (`lib/data/prickles.ts`), the Bronze Zoom tables `zoom_attendees`, `zoom_meetings` and `zoom_chat_messages` (in-meeting chat from the webhook: the text and the raw payload are service role only, admins read `zoom_chat_messages_meta`: sender, recipient, time) and the `ignored_zoom_names` list (`lib/data/zoom.ts`), `members` (`lib/data/members.ts`: identity scans, full-record lists, lookups by id, auth user and email, profile columns, search; reads and writes; only `/api/health` is still direct, on the guard test's allowlist, because it checks the database itself), and the Bronze Slack tables: `SlackWorkspaceRepository` (`lib/data/slack-workspace.ts`: channels and group DMs, who is in them and the join/leave history, custom emoji, the ignored Slack users, `restricted_slack_channels`) and `SlackMessageRepository` (`lib/data/slack-messages.ts`: messages, reactions and files; admins read messages through the content-free `slack_messages_meta` view, and the text, files and raw payload only through a service-role client), and members' bookshelves `member_books` (`lib/data/books.ts`, `BookRepository`: shelf, profile and My Books lists, add, edit and soft delete, counts for the Published Author badge, search, and the move of older covers into the media library; every query is moved; a book is one card with up to one edition per format in `member_books.editions` (link and price each, rules in `lib/book-editions.ts` and `valid_book_editions`)), what members do around prickles apart from attending, `prickle_commitments` with `prickle_commitment_slots`, `prickle_checkins` and the dismissed offers `prickle_checkin_dismissals` and `prickle_checkout_dismissals` (`lib/data/prickle-activity.ts`, `PrickleActivityRepository`: commitments with their slots and type names joined in, the create/complete/cancel writes, check-in reads and saves, and one dismissal API taking the half, `"checkin"` or `"checkout"`, so the two stay symmetric; every query is moved), the calendar feed and the Google calendar sync lease: `calendar_feed_tokens` (the secret token in a member's feed URL: never in a log or error message) and `calendar_feed_items` (`lib/data/calendar-feed.ts`, `CalendarFeedRepository`: token lookup, create and replace, the first-fetch mark, a member's items with type, prickle and event joined in, add/remove, and the roster's "who added this prickle or slot"), and `calendar_sync_state` (`lib/data/calendar-sync-state.ts`, `CalendarSyncStateRepository`: the claim/release/watermark protocol, each step one conditional UPDATE; `lib/google-calendar/sync-state.ts` wraps it) and `calendar_watch_channels` (the same repository: the Google push channels the daily renewal keeps alive), every query moved, segments and feature flags: `SegmentRepository` (`lib/data/segments.ts`: `segments` and `segment_members`, member links paginated past 1000) and `FeatureFlagRepository` (`lib/data/feature-flags.ts`: `feature_flags`, `feature_flag_segments`, and the previews users turn on for themselves, `user_feature_previews`; `lib/features.server.ts` decides who has a flag from these reads), Slack sign-in: `SlackSignInRepository` (`lib/data/slack-sign-in.ts`: `slack_identities` and `slack_sign_in_tokens`, service role only; hashes only, never a token or code; `consumeToken` is the one conditional UPDATE that makes a credential single-use), and the usage events `analytics_events` (`lib/data/analytics-events.ts`, `AnalyticsEventRepository`: only `lib/analytics/`, the tracking route and `/privacy` call it, after validating against the tracking plan, every query moved, and the Kajabi course Bronze tables `kajabi_courses`, `kajabi_course_modules`, `kajabi_course_lessons`, `kajabi_lesson_files`, `kajabi_course_offers`, `kajabi_product_progress`, `kajabi_lesson_progress` (`lib/data/kajabi-courses.ts`: structure import, lesson content, hero, both progress snapshots), and the Silver curriculum and Local course tables: `CourseRepository` (`lib/data/courses.ts`: `courses`, `course_modules`, `course_lessons`, `course_lesson_files`, `videos`; Kajabi rows are upserted on their source key with orphans removed, Hub rows are written by the course editor, a refused write throws `CourseWriteError` carrying the database code) and `CourseProgressRepository` (`lib/data/course-progress.ts`: `lesson_progress`, `course_access` as rebuilt by processing, `course_access_grants`, the append-only `video_watch_segments`); every query is moved except the retention job's `video_watch_segments`, see `docs/TODO.md`, and the people and profile long tail, every query moved: `StaffRepository` (`lib/data/staff.ts`: `staff`, and the member link the members processing keeps), `MentorshipRepository` (`lib/data/mentorship.ts`: `mentorships` and `big_sister_volunteers`; admin-only matches, a refused second live match for an arrival is the result `already_matched` rather than a thrown error, and the `mentorship_counts()`, `my_mentorships()` and `set_mentorship_note()` functions as typed methods that answer for the signed-in caller), `MemberProfileRepository` (`lib/data/member-profile.ts`: `member_ask_me_about`, the author-only `member_notes` (keep the caller's RLS client; never read or write them as another member), `member_roster_opt_outs`, `member_onboarding` and `member_slack_connections` without the token secrets), `AwardRepository` (`lib/data/awards.ts`: `member_awards`, soft delete and search), `OutreachRepository` (`lib/data/outreach.ts`: `outreach_leads` and `outreach_touches`; the leads' members come from `MemberRepository.withKajabiTag`) and `AdminWorkQueueRepository` (`lib/data/admin-work.ts`: `admin_work_queue_completions`, `dismissed_duplicate_groups` and `feedback`; the work queue's members come from `MemberRepository.tenureOf`). The Zoom accounts (`zoom_accounts`, `zoom_meeting_decisions`) are on `ZoomRepository` too, and its attendee, presence, chat and host reads return only the meetings the account default and the admin's decisions keep (`docs/architecture/ZOOM_ACCOUNTS.md`: a secondary account is excluded until its meetings are kept). The Zoom hygiene tables are on `ZoomRepository` too (`ambiguous_zoom_names`, the per-prickle `ignored_zoom_appearances`, the webhook's `bronze.zoom_participant_events`, and the prickle room's `prickle_join_settings`), and the rest of the prickle side is on the repositories above: hosts' vibe tags `prickle_host_vibes` on `PrickleRepository`, the month locks `prickle_schedule_locks` on `PrickleScheduleRepository`, the check-in/check-out DM claims `prickle_checkin_dm_log` on `PrickleActivityRepository` (`claimDm` is the dedup: true only for the first claim of a prickle, member and kind), `member_metrics` and `member_engagement` (only a merge deletes them) on `MemberRepository`, and three small repositories: `WheelOfWonderRepository` (`lib/data/wheel-of-wonder.ts`: `wheel_of_wonder_matches`), `AccessEventRepository` (`lib/data/access-events.ts`: the `access_events` page-view log) and `NotificationLogRepository` (`lib/data/notification-log.ts`: `notification_log`, the one log of what the app sent a member or a shared place such as a Slack channel, keyed by recipient, kind and dedup key: claim before sending, release when nothing was delivered; a new automated sender uses it instead of a log table of its own, see `docs/runbooks/CHANGELOG_PROCESS.md` for the first user). and `chat_message_videos` on `ChatVideoRepository` (`lib/data/chat-videos.ts`: the course lesson whose video a chat message shares, one per message; the playback route reads it as the viewer so row-level security applies the channel rule, and the share action writes it with the service role after its own checks; see `docs/product/SLACK_BRIDGED_CHAT.md`, "Lesson videos in messages"). Hedgie Care's `care_engagements` (the community manager's reach-outs, one row per period) are on `CareRepository` (`lib/data/care.ts`: renewing is the `renew_care_engagement` function, one transaction; the status is derived in `lib/care.ts`, never stored; see `docs/product/HEDGIE_CARE.md`), the DMs staff track for it, `care_tracked_dms`, on `CareTrackedDmRepository` (`lib/data/care-dms.ts`: a staff user's own opt-in list, visible only to them, not audited; the derivation of who spoke last reads Slack's Bronze metadata only, through `SlackMessageRepository.lastWritesIn`, never message text), and `member_interactions` (who interacted with whom in chat; the measured results read it) on `MemberInteractionRepository` (`lib/data/member-interactions.ts`). Lesson comments and their reports, `lesson_comments` and `lesson_comment_reports`, are on `CourseCommentRepository` (`lib/data/course-comments.ts`: a lesson's thread for a viewer (tombstones for hidden, held visible only to author and staff), the unanswered, reported and held lists, create, edit, soft delete, report, and staff `moderate`, which calls the audited database function; see `docs/product/COURSES.md`, "Lesson comments"). The Finisher record, `member_milestones`, is on `MilestoneRepository` (`lib/data/milestones.ts`: a member's own milestones, the staff list and counts, the set-based per-book backfill from published books (`propose_milestones_for_books`, per work: a book and its project are one), hand-added proposals for a work, taking one back, the member's answer, and the member adding their own (already confirmed) or taking that back; the member's client sees only their rows and an admin's can only propose or take back proposals; see `docs/product/FINISHERS.md`).
