# Permissions: what staff roles may do

> **Status:** living. **Last reviewed:** 2026-11-22. Review: yearly. Kept up to date with the code; if it is wrong, fix it.

Access to the staff area is decided by **permissions**, not by "admin or not". A permission is an operation defined in code, a role is a named bundle of permissions, and every check goes through one function. This is the model for the Hub today and the shape meant to be reused in other apps.

- **Permissions are code.** `PERMISSIONS` in `src/lib/permissions.ts`, each named `<area>.<action>` (or `<area>.<thing>.<action>`) with a one-line description: `pages.edit`, `members.read`, `analytics.cohorts.read`. They are not rows in a table, so a permission can't exist without a guard in the code that uses it, and a code review sees every change to who may do what.
- **Roles are bundles, and a person can hold several.** `ROLE_PERMISSIONS` maps each staff role to its list. A person holds a set of roles (`user_roles`, see "A person can hold several roles" below) and may do the union of what they allow. The roles are: `admin` (everything), `assistant` (the admin's list, derived from it so the two stay in step; see "The assistant" below), `community_manager` and `conversion_specialist`. Anyone else (`member`, no profile) holds nothing. Opt-in is the rule: a new permission is in no bundle but the admin's until someone adds it to another on purpose.
- **One check.** `can(actor, permission)` (`src/lib/permissions.ts`; the actor is anything with a `role` and/or `roles`: it is true when any role held holds the permission) is the only question anyone asks. The guards call it:
  - pages: `await requirePermission("pages.read")` (`src/lib/admin-auth.ts`; redirects);
  - server actions: `const auth = await requireActionPermission("pages.edit"); if (!auth.ok) return { error: auth.error };`;
  - route handlers: `const auth = await requireApiPermission(request, "pages.edit")` (`src/lib/supabase/api-auth.ts`; `user` null is 401, `forbidden` is 403; the cron secret and the test service-role key still bypass it);
  - the proxy and the sidebar: `mayOpenAdminPath(roles, path)` (`src/lib/admin-paths.ts`), from the table of which permission each admin page needs (any role held may open it). The proxy reads the roles from the token's `app_roles` claim and is only the pre-filter; the guards read the roles from the database (see `.claude/rules/admin-route-protection.md`).
- **The database is the other half.** A permission decides what the application offers and runs. What a signed-in user's own client may read or write is still decided by row-level security: a role that can see a page also needs policies on the tables it reads (`is_community_manager()` and `is_conversion_specialist()` next to `is_admin()`; nothing ever widens `is_admin()`). Where the application reads with the service role after its own check, the permission is the only gate, so it is named for exactly that read (`care.member_activity.read`).

## The roles today

The page **Roles** (`/admin/roles`, permission `roles.read`: admin and assistant) lists every permission and every role with what it holds, marks the reserved permissions and the assistant's withheld one, and filters by permission text or role. It is read-only and generated from the registry (`buildPermissionMatrix` in `src/lib/permission-matrix.ts`), so it can't go stale; the one-line role descriptions come from `ROLE_DESCRIPTIONS` and the reason for a withheld permission from `ASSISTANT_WITHHELD_REASONS`, both in `src/lib/permissions.ts`. A new role needs a description there as well.

| Role | Holds |
|---|---|
| `admin` | every permission |
| `assistant` | the admin's, except `care.member_activity.read` (see below) |
| `community_manager` | the Calendar View, the member list and a member's page (with only their own activity in the Activity tab), At-Risk, a prickle's page, Hedgie Care (read and write), Community Stats, Slack Engagement, Resubscriptions |
| `conversion_specialist` | landing pages (read, edit, publish, not delete), outreach, browsing the media library, email, scheduled email and announcements (no surface yet), conversion and retention cohorts in aggregate (no surface yet) |

The conversion specialist has none of the members area (list, member pages, notes, contact data, merges, overrides, sudo), nothing of the changelog and no export. The full table of every role and permission is `tests/lib/permissions.test.ts`; it is written out permission by permission, and a new permission does not typecheck until the table decides it.

**The assistant.** The assistant mirrors the admin: its list is the admin's with only the permissions in `ASSISTANT_WITHHELD` taken out. Today that is `care.member_activity.read`, because the privacy page promises that the text of a member's tracked DMs and their activity in Hedgie Care are seen by admins and community managers, never an assistant. Row-level security still treats only `role = 'admin'` as `is_admin()`, so an assistant passes the application's guards but reads what its own client is allowed to: nothing of the admin tables, until `is_admin()` is extended on purpose (`docs/TODO.md`, "Back the assistant role in the database").

**Preview as a role.** A real admin (anyone holding admin) can look at the staff area as another staff role, one at a time: user menu, "Preview as...", which opens a dialog with a role dropdown and a "Start preview" button (`src/components/PreviewAsModal.tsx`). The dropdown lists `PREVIEWABLE_ROLES`, which is every staff role below the admin, taken from `STAFF_ROLES` with its label from `ROLE_LABELS`, so a new role appears without a UI change. The banner names the role and "Exit preview" leaves; starting lands on the role's `staffHome`. The effective role is the previewed one for the page guards, the action guards and the sidebar, so what the role may not open or do is refused. It is UI and routing only: data is still read with the admin's access. A new role needs a label in `ROLE_LABELS` and, if it doesn't start on the dashboard, a `staffHome`; nothing else.

## Why there are three guards

`requirePermission`, `requireActionPermission` and `requireApiPermission` ask the same question and differ only in how they fail, because a page, a server action and a route handler each have to fail in their own way: a page redirects (to `/login`, `/no-access`, the role's home or the second sign-in step), an action returns `{ ok: false, error }` so it keeps its result shape, and a route answers HTTP 401 or 403. The question itself, who the person is, what role they hold (an admin previewing is that role, never for routes), whether they hold the permission and whether the second sign-in step blocks them, is one function, `decideStaff` in `src/lib/staff-guard.ts` (it takes the roles held); each guard only finds the person (a cookie session, or for routes the cron secret and test key as well) and turns the answer into its failure. A fourth entry point should add a failure adapter, not a copy of the decision.

## A person can hold several roles

Staff teams are small and people span roles (a conversion specialist who also helps with community management), so a user holds a **set** of roles and what they may do is the **union**. The admin implies everything; what is withheld from the assistant (`ASSISTANT_WITHHELD`) stays withheld unless another role they hold grants it (an assistant who is also a community manager holds `care.member_activity.read`, as the privacy page allows community managers to).

- **Storage.** `user_roles` (a user, a role, who gave it and when; one row per role, unique per user) holds a person's staff roles; a member holds none. Everything reads that table and only that table: the repository (`profiles.rolesOf`), the guards, the proxy's token claim, the access token hook and every SQL function (a profile has no `role` in its type, and `tests/lib/user-profiles-role-readers.test.ts` and `supabase/tests/database/user_roles_readers.test.sql` fail on a new read of the old column). `user_profiles.role` still exists and is still **written**, for a rollback to older code: it holds the **primary role**, the highest priority held (admin, assistant, community manager, conversion specialist, or `member` for none; the order of `STAFF_ROLES` in code and `staff_role_rank()` in SQL, a test compares them), kept in step by triggers, and `set_user_roles(user, roles)` replaces a person's set in one call, as the person who calls it. It is dropped in the next step (`docs/TODO.md`, "Let a user hold several roles: the contract step").
- **In code.** `rolesOf(actor)`, `staffRolesIn(roles)` and `primaryRole(roles)` in `src/lib/permissions.ts`; a guard returns `roles` (those in effect) and `role` (the primary of them), and `realRoles`/`realRole` for who the person is. `can(user, permission)` reads both. `staffHome` is the primary role's home. `profiles.rolesOf(userId)` and `setRoles(userId, roles)` are the repository calls (`src/lib/data/profiles.ts`); read roles there, not from the column.
- **In the database.** `is_admin()`, `is_community_manager()` and `is_conversion_specialist()` are exists-checks over `user_roles` (through `user_has_any_role()`, closed to clients, which still counts the old column as a second source until it is dropped), so a single-role user can do exactly what they could and `is_admin()` is still only the admin role; a person with two roles gets both sets of policies. RLS on `user_roles`: a user reads their own rows, admins read and write all.
- **The token.** The access token hook adds `app_roles` (every staff role held, highest first) and keeps `app_role` (the primary). The proxy and `mayOpenAdminPath` use the union; the claim is still only an optimistic pre-filter and real authorization reads the database.
- **Assigning.** The Users page (`system.users.manage`) edits a person's set with checkboxes; each role given or taken away is an Activity Log entry as the person who did it ("gave ada@example.test the role Community Manager"). Preview as a role stays single-role.
- **Who may change whose roles.** No privilege escalation: an actor gives or takes away only roles **strictly below their own highest role**, and only on people strictly below it; an admin may manage any. So an assistant manages community manager and conversion specialist only, and nobody below admin can change a person who holds admin or assistant. Nobody removes their **own** admin role (another admin does it), and the **last admin** can't be removed. Anyone else (community manager, conversion specialist, member) changes no roles. The service role (scripts, tests) and a session with no user (migrations, jobs) are exempt, and deleting an account takes its roles with it by the same rules in the Users route. It is enforced in the database by `enforce_user_role_changes()` on `user_roles` (so `set_user_roles()`, a direct write and the old column all obey it, and the policies on the table allow only admins to write at all), in the route with the reason (`roleChangeRefusal`, `src/lib/permissions.ts`, one copy of the rules in code) and on the Users page, which disables what the person can't do (`changeableRoles`) and hides Delete for what they can't remove. The Roles page states the rules.
- **Not done yet (the last contract step)**: dropping `user_profiles.role`, its check, the sync triggers and `user_has_any_role()`'s second source (`docs/TODO.md`, "Let a user hold several roles: the contract step").

## Adding a permission

A new kind of resource or operation defines its permissions in the same PR: names `<resource>.<verb>` (`read`, `list`, `create`, `edit`, `publish`, `delete`, `import`, `export`, `bulk`, `manage`; none implies another), a decision for every role, the guard, policies, an Activity Log entry for each mutating one, and tests. The rule, with the reasoning for collections, live updates and pipelines, is `.claude/rules/permissions-for-resources.md`.

1. Add it to `PERMISSIONS` with a description. Name it for the operation, not for a page.
2. Use it: `requirePermission` on the page (and the path in `ADMIN_PAGE_PERMISSIONS` in `src/lib/admin-paths.ts`, which the proxy and the sidebar read), `requireActionPermission` in each action, `requireApiPermission` in each route, and `can(...)` for a control inside a page. If nothing uses it yet, list it in `RESERVED_PERMISSIONS` and say "no surface yet" in its description; the guard test fails on a stale reserved entry.
3. Decide each role: add it to the bundles that should hold it (`ROLE_PERMISSIONS`) and write the decision in the table in `tests/lib/permissions.test.ts`. The admin has it automatically.
4. If the role's own client reads or writes tables for it, add the row-level security policies in a migration (`is_<role>()` beside `is_admin()`, SELECT only unless the role writes) and a pgTAP test for what it can and can't read. Never widen `is_admin()`.

`tests/lib/permission-guards.test.ts` scans the source: every admin page, server action and staff route calls a guard with a permission that exists; a page's guard is the one the path table says; every permission is used by a guard or a check, or is reserved.

## Adding a role

A value in the `user_roles.role` and `user_profiles.role` check constraints (an expand-only migration, with `is_<role>()` over `user_has_any_role()` and its policies), a place in the priority order (`STAFF_ROLES` and `staff_role_rank()`), an entry in `ROLE_PERMISSIONS`, a `staffHome` if it doesn't start on the dashboard, a description in `ROLE_DESCRIPTIONS` (the Roles page), a label in the Users page and (if it should be previewable) in `PREVIEWABLE_ROLES`. Audit and the staff definition (`audit_row_change()`, `staff_member_ids()`) count the role as staff in the same migration.

## Plans (not built)

Written down so a later change knows where this is going; none of it exists.

- **Grants as data.** Permissions stay in code (so every one has a guard), but which role holds which could move to rows (a role, a permission, and who granted it and when), so staff can be given one permission without a deploy, with an audit entry. `can()` would read the grants, with the bundles in code as the defaults.
- **Scopes.** A grant limited to a subset (one team's pages, one program's members). The check becomes `can(actor, permission, resource)`; the call sites that pass a resource today (a page's slug, a member id) are where it would start.
- **Other apps.** The registry, the roles map and `can()` are the part that doesn't depend on the Hub: the guards (`admin-auth.ts`, `api-auth.ts`) and the path table are the glue to copy.
