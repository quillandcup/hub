# The event log (design)

**Status: proposal, for review. Nothing here is built except what is marked "exists".** It consolidates the Hub's scattered behavioral logs into one low-level event log, with the other logs, dashboards and the activity feed becoming *views* over it.

## Decisions so far

These came out of discussion and are the constraints this design works within.

1. **One low-level event log; everything else is a view over it.** The member activity feed, sessions, analytics, funnels and the per-feature dashboards are queries over events, not separate stores.
2. **No audience column.** Developers, product managers and the business get different *views*, not a `level` field on every row. (How a view knows which events it includes is in [Views](#views).)
3. **Correlation ID, generated by the client**, ties a click, the server work it causes, and the database changes together, including the database trigger.
4. **Keep everything legally permissible; prefer soft deletes.** Business events are recorded unconditionally only where they are the service's own record; usage analysis rests on legitimate interest with a right to object; browser tracking stays consent-gated. Business events are kept until a member asks, never dropped or anonymised automatically; browser tracking is kept for 13 months and then lives on only as anonymous rollups; raw IPs go after 90 days. See [Retention, erasure and soft delete](#retention-erasure-and-soft-delete).
5. **One table by default.** Use RLS, column grants and views for restrictions rather than splitting tables.
6. **Segment-style Noun Verb event names**, extended with a user-side `failed` and a server-side `error`. See [Naming](#naming).

## Why

Today "who did what, when" is spread over five stores that overlap and disagree about retention:

| Store | What it is | Written by | Notes |
|---|---|---|---|
| `audit_log` | field-level changes to records | database triggers (any write path) | immutable-ish; no FK to users, history outlives them |
| `member_activities` | the CRM timeline | Slack/attendance reprocessing (Silver); best-effort inserts for logins, writing progress, outreach | read by engagement scoring |
| `access_events` | every signed-in request, plus browser page views; user agent, GA id, IP and place | the proxy and `/api/track/page-view` | feeds the activity feed's "session" rows and login activity |
| `analytics_events` (**exists**) | clicks, impressions, search, server outcomes (`action_completed`), notifications sent/opened | the browser, server actions, `createNotifier` | erased with the account |
| `video_watch_segments` | watched/viewed ranges per video | the lesson player | other work is building heatmaps on it |

Page views are logged twice (`access_events`, `analytics_events`), a click and its outcome can't be joined except by guessing from time, and each store has its own idea of who may read it and how long it lives.

What the unified log should make possible, with no new store each time:

- *Developer / UX:* "did they open the filter in the search palette, and use it?"
- *Product:* "they pressed Enter and the form rejected it: which field, how often?"
- *Business:* "a project was created", "a check-in was saved", "a notification went out".
- *Low-level data on demand:* login events, video watch stats, one visit's whole story in order.

## The model

One append-only table, `events` (the existing `analytics_events`, generalised; a compatibility view keeps today's functions working during the move).

| Column | Meaning |
|---|---|
| `id`, `occurred_at`, `received_at` | identity and time (client clock corrected for skew, as today) |
| `name` | the event, Noun Verb in snake_case: `project_created` |
| `correlation_id` | the interaction this belongs to (see [Correlation](#correlation)) |
| `session_id` | the visit (null for events with no visit: system sends, webhooks) |
| `actor_user_id`, `actor_kind` | who did it: `member`, `staff`, `system`; an admin in sudo is the actor with `acting_as_member_id` set, as in the audit log |
| `subject_member_id`, `entity_type`, `entity_id` | *what it concerns*: the person (when there is one) and the record. First-class columns, not free properties, so "everything about this project" and "this member's timeline" are indexed queries |
| `source` | `client`, `server`, `system`, `trigger` |
| `properties` | allowlisted properties from the event's declaration (see [The catalog](#the-catalog)): never names, emails or typed text |
| `context` | route template, viewport, app version; **not** the network details |
| `deleted_at` | soft delete: hides the row from every view; it is a mechanism within a category, not a category (see [Mechanism](#mechanism)). A scrub also sets `scrubbed_at` and `scrub_reason` |

No foreign key to users: like `audit_log`, an event can outlive the account (anonymised, see below). The network and device details that `access_events` keeps today (IP address, place, user agent, GA client id) stay in this same table in columns with tighter grants (see [Access](#access)), not in a second table.

### Naming

Segment's recommended style, Noun Verb, in the past tense, for something that happened: `project_created`, `prickle_checkin_saved`, `notification_sent`. Stored in snake_case (as the registry already is) and shown as "Project Created" in the UI by a formatter. Two extensions, as asked:

- **`<noun>_<verb>_failed`: the user's side.** The request was well formed and was refused: validation, permission, a precondition. `project_create_failed { reason: validation | permission | precondition, fields? }`. A product manager's event. It is also what "pressed Enter and the form rejected it" looks like, including when the check ran in the browser before any server call.
- **`<noun>_<verb>_error`: the server's side.** Something unexpected broke: `project_create_error`. An engineer's event (with a pointer to Sentry).

So one attempt produces exactly one of `project_created`, `project_create_failed`, `project_create_error`, plus the interaction events that led to it (`element_clicked`, `form_validation_failed`...), all sharing a correlation id. The 41 server actions wired in #210 are nearly all already Noun Verb (`project_created`, `commitment_cancelled`...); each becomes a triple declared in one place. `action_completed { action, ok }` is replaced by these.

### The catalog

Today the tracking plan is a TypeScript registry (`lib/analytics/events.ts`): which events exist and which properties they may carry. The design keeps that and adds, per event: a description, which **views** it belongs to, its **basis** (`contract`, `legitimate_interest` or `consent`, below), whether a member can **object** to it, whether it is **soft-deleted or anonymised** on erasure, and its **retention window**. A migration-time check keeps the TypeScript registry and a small `event_catalog` table in step, so SQL views and the privacy rules read the same facts the code does.

## Correlation

One id ties the chain: **click -> browser events -> server action -> server events -> database changes**.

- **Generated by the browser** on each interaction (click, submit, keypress that submits, navigation) as a UUID. It is attached to the browser's own events, and written to a short-lived first-party cookie (`hub_cid`) synchronously in the click handler, so the request that follows carries it. (Server actions can't add custom headers from the client, so a cookie is the carrier; the visit cookie `hub_sid` from #210 already works this way.)
- **Read by the server** in `lib/supabase/server.ts`, which already forwards the sudo header to the database: it forwards `X-Correlation-Id` the same way (validated as a UUID; if absent, the server generates one, so server-originated work like cron and webhooks gets one at its entry point).
- **Reaches the database trigger.** PostgREST exposes request headers to triggers as `request.headers`: this is exactly how `current_acting_as_member_id()` reads `X-Acting-As` today. A sibling `current_correlation_id()` reads `x-correlation-id`, and `audit_row_change()` stamps a new `audit_log.correlation_id` column. Events recorded by the server use the same value. So from `project_created` you can jump to the exact field-level changes in the audit log, and from an audit row back to the click that caused it.
- **Limits, stated plainly.** Writes from the SQL editor, a migration or a cron job with no request have no header: null (cron jobs that go through the app get a server-generated id). It is **untrusted**, since the client chooses it: it is only ever used to *correlate*, never to authorise, and joins are always on `(actor_user_id, correlation_id)` so one member can only confuse their own chain. A very fast double click can overwrite the cookie before the first request reads it; precise per-call correlation would mean passing the id as an argument to every action, which is invasive, so the cookie is accepted as best-effort.
- **No consent, no click link, still a record.** The correlation cookie is set only when interaction tracking is allowed. Without it the server generates an id, so business events and audit rows still correlate with each other; they just don't link back to a click.

## Views

The log is the store; these are queries. Audience is a property of the *view*, not of every row. A view includes events through the catalog (above), not through naming tricks, so adding an event means declaring which views carry it.

| View | Audience | Includes |
|---|---|---|
| **Business facts** | business | the past-tense success events: `project_created`, `notification_sent`... |
| **Product friction** | product management | the `_failed` events, `form_validation_failed`, empty states seen, abandoned flows |
| **Engineering** | developers / UX | `_error` events, clicks, impressions, search and filter use, timings |
| **Activity feed** (`/admin/activity`) | staff | business facts and sessions, merged with `audit_log` rows, keyset-paginated as today |
| **Sessions** | staff | `page_viewed` grouped into visits, with the page trail: replaces the sessionizing over `access_events` |
| **Member timeline** | staff | everything with this `subject_member_id` |
| **Funnels / Explore / Least-clicked** | everyone | what exists today, reading the same table |
| **Record history** | staff | `audit_log` for a record, linked to the events with the same correlation id |

`member_activities` stops being a store for the *append-only* sources (logins, writing progress, outreach, commitments): it becomes a projection of business events, reprocessable like the Slack and attendance rows already are, replacing the "best-effort insert alongside the primary action" pattern. Slack and prickle attendance keep their own reprocessing pipelines.

### What stays separate, and why

`audit_log` is not merged into the event log. It is the data-change journal: database triggers capture the old and new value of every changed field for any write path (API routes, cron, the SQL editor), it **folds** repeated changes made by one transaction into a single row (first old value, last new value, dropped if they net out: a sync that flips a status and flips it back writes nothing), and it powers the per-record change-history dialog. An application-level event log would do all three worse. The two are **linked** by the correlation id instead, which gets the "one story" without losing what the audit log is good at.

`video_watch_segments` stays for now: it is interval data with its own aggregation (heatmaps, engagement), and other work is building on it. Its watch ranges can be exposed through a view next to the events (or, later, re-expressed as `video_segment_watched` events); not in the first phases.

## Retention and erasure

**This is engineering's reading of the regulators' published guidance, not legal advice.** The numbers below are proposals backed by the sources in [Sources](#sources-and-what-was-not-verified); counsel should confirm them before they are published to members.

### What the guidance actually requires

- **No fixed period; you must justify one.** The ICO: the UK GDPR "does not set specific time limits for different types of data"; "it is up to you to justify this, based on your purposes", with a retention policy that sets "standard retention periods wherever possible", and erase *or anonymise* when identification is no longer needed (pseudonymised data usually still counts as identifiable). The same applies under the EU GDPR's storage-limitation principle.
- **Regulator benchmarks that exist** (recommendations, not statutory limits):
  - CNIL on access/audit logs: **six months to one year**; up to **three years** for internal-control logging only if the longer period is documented as necessary and proportionate.
  - CNIL on audience measurement that is exempt from consent: tracker lifetime about **13 months** (not extended on each visit), collected data kept at most **25 months**.
  - ICO on the UK's statistical-purposes exception: individual-level data kept "only as long as you need it" to aggregate it (daily aggregation as a starting point), and the exception "does not allow you to monitor or track individual visitors", for example by "connecting a visitor ID to their site activity". Our interaction events are per-member, so they sit *outside* that exception and rely on consent, which is how they already work.
- **Erasure (GDPR Art. 17)** must happen without undue delay when data is no longer necessary for its purposes, consent is withdrawn, or an objection is upheld; the exceptions include legal obligations, legal claims, and archiving or statistical purposes where erasure would seriously impair them.
- **California.** The statutory test for the CCPA/CPRA (annual revenue over about $26.6M, or data on 100,000+ consumers or households, or 50%+ of revenue from selling or sharing data) probably does not reach this organisation. The principle is still worth following: say how long each category is kept (or the criteria), and keep it no longer than reasonably necessary for the disclosed purpose. About 90% of the membership is in the US.

### Lawful basis per event type (replaces "consent vs operational")

Each event type in the catalog carries a **basis** and an **objectable** flag:

| Basis | What it covers | Consent needed? | Can a member opt out? |
|---|---|---|---|
| `contract` | the product's own record of what happened *in the service the member signed up for*: what `audit_log`, `member_activities`, in-app notifications and the check-in/commitment tables already record (a project created, a commitment cancelled, a notification sent, a login) | No | No: it is the service's data, and it is also what the member sees and relies on. Erasure and access still apply (below) |
| `legitimate_interest` | using those same facts, or similar ones, to understand how the product is used (feature usage, funnels, success rates) | No, after a documented balancing test | **Yes, on request** (Art. 21 right to object; the controller must stop unless it shows compelling grounds). Honour it by leaving that member out of analytics views, while their operational records stay |
| `consent` | behavioural tracking from the browser: clicks, impressions, search and filter use, validation friction, the visit and correlation cookies | Yes, where required (EU, EEA, UK; today's banner and `hub_sid` rule) | Yes: declining or withdrawing stops it |

**On "essential": confirmed for the narrow class, not for everything labelled "business".** Two separate legal questions are being merged under that word:

1. *Does the ePrivacy rule (EU Art. 5(3), UK PECR regulation 6) require consent?* It applies when information is **stored on, or read from, the member's device.** A server recording that a project was created reads nothing from the device; it is the request the member made. So business events recorded by the server don't need consent *for that reason.* But the cookies we use to link a click to its outcome (`hub_sid`, `hub_cid`) are device storage, and they are **not** "strictly necessary" (the ICO tests that from the user's side: without it the service "couldn't be provided on a technical level"; ours work without them). They stay consent-gated. The result: business events are always recorded; they just aren't linked to clicks for members who haven't agreed.
2. *Does the GDPR require consent to process the data?* No, if there is another basis: `contract` for the service's own records, `legitimate_interest` for usage analysis. Only the first is truly un-opt-out-able; the second carries the right to object.

Once a membership has ended, the `contract` basis weakens (there is no longer a service being delivered); the same events are then kept on `legitimate_interest`, with the purpose stated as keeping a returning member's history, and a request is how a member objects.

So the design does not claim business events "may not be opted out of". It records the `contract` class unconditionally, honours objections for the `legitimate_interest` class, and keeps `consent` for browser tracking. All three must be disclosed on the member-facing privacy page (`/privacy`, behind the `message_privacy` flag), including the retention periods.

### Retention schedule (decided)

The owner's rules for this: **business events are never dropped or anonymised automatically, only on request** ("we keep your seat warm at the table" has to be true: members come back years later), and analytics must still show **year-over-year trends**. IP addresses are dropped at 90 days. The schedule follows from those.

| Data | Basis | Kept identifiable | After that | Why |
|---|---|---|---|---|
| **Business events**: the service's own records *and* the facts analytics reads (a project created, a check-in saved, a notification sent, a login) | contract while a member; legitimate interest once membership has ended | **until the member asks** | on request: erased or anonymised, as they ask. No automatic limit | the "seat warm" promise; members return years later; year-over-year trends need the history. They hold no content, IP or device details, which is what makes keeping them reasonable |
| Interaction events (clicks, impressions, search, filters) and friction events (`*_failed`) | consent | **13 months** | the row is deleted; **anonymous daily, weekly and monthly rollups are kept indefinitely** | volume and sensitivity are the highest here; 13 months is CNIL's tracker lifetime and enough for any same-month comparison; the rollups keep long-run trends without identifiable rows |
| Server error events (`*_error`) | legitimate interest | **90 days** | deleted | they exist to debug; the stack trace lives in Sentry |
| Visit records (page views, sessions) | legitimate interest (support, security) | the page trail for **13 months** | collapsed to **one summary row per visit** (start, end, number of pages, no paths), kept until the member asks | "when did they last come back" survives for years; the path-by-path trail doesn't |
| **Raw IP address and raw user agent** (on sign-in events, and on old access rows until they are replaced) | legitimate interest (security, abuse) | **90 days** | IP truncated (last octet, or the lower 64 bits of an IPv6 address) or nulled; raw user agent nulled | the most sensitive columns; the place and the parsed device details (next row) are derived once at write time, so the raw values add nothing after that |
| **Device and viewport details** (browser and OS with versions, device type, viewport size, orientation: see [Device and viewport details](#device-and-viewport-details)) | consent (client-sourced), legitimate interest (the sign-in header parse) | **13 months**, on interaction events, sign-in events and visit summaries | the coarse fields (browser family, OS family, device type) stay on sign-in events and visit summaries; the detail is removed; rollups keep bucketed counts | detail answers "what do we need to support" and "when did their problem start"; it is the fingerprint-like part, so it expires on the same clock as the clicks and rollups never show a cell smaller than five members |
| Derived place (country, region, city) | follows its event | with its event | with its event | coarse (the ICO lists coarse city or region as acceptable detail) |
| Backups | | the provider's backup window | rolls off | erasure completes when backups expire; the privacy notice says so |
| `hub_sid` visit cookie | consent | 30 minutes idle (already) | | |
| `hub_cid` correlation cookie | consent | **60 seconds** (it only has to survive from the click to the request it makes) | | |

**Keeping business events indefinitely is a choice that needs three things to stay defensible**, and the design includes all three. (1) A stated purpose: the privacy notice says plainly that member history is kept so a returning member finds their seat as they left it, and for how long ("until you ask us to remove it"). (2) Erasure on request actually works: a member can ask, and `anonymise_user_events` (or full deletion, as they choose) is run, including for the class that has no automatic limit; Art. 17 lists "no longer necessary for the purposes" as a ground, so the stated purpose matters, and a request settles it. (3) A periodic review: every three years, someone looks at whether the purpose still holds and records the answer, because the ICO's test is that you "can keep it as long as one of those purposes still applies" and must be able to justify it. The residual risk is mostly for EU and UK former members, and the membership is about 90% US; it is a risk to accept knowingly, not one to hide.

Where the current system differs: `access_events` keeps raw IPs, user agents and places indefinitely and nothing prunes it (recorded in `docs/TODO.md` as "the owner's call, for now"). That is the one real exposure, and phase 0 closes it. `video_watch_segments`, `member_activities` and `audit_log` have no limit, which matches this schedule (kept until asked).

### Data inventory: what is kept, at what detail, for how long

The one table to read (and to publish, in plain words, on `/privacy`). Everything above and below must agree with it; if they don't, this table wins and the other is a bug.

| Data | What exactly is stored (granularity) | Stored together with (combinations) | Kept identifiable for | After that |
|---|---|---|---|---|
| **Business events**: a project created, a check-in saved, a notification sent or opened, a lesson completed | event name and time; who did it (user) and what it concerns (the member, the record); the correlation id; a few allowlisted facts (which action, a count, a status). No typed text | actor + record only. **Never** device, IP, viewport or place | **until the member asks** | on request: erased or anonymised, as they choose. No automatic limit |
| **Sign-in events** | time; user; **raw IP**; **raw user agent**; place (country, region, city); browser and OS **with versions**; device type | all together on the one event | raw IP and raw user agent **90 days**; browser and OS versions **13 months**; the rest until asked | at 90 days: IP truncated (last octet, or lower 64 bits for IPv6) or nulled, user agent nulled. | **Cookies** | `hub_sid`: the visit's random session id. `hub_cid`: the correlation id of the last click | set only where tracking is allowed | `hub_sid` 30 minutes idle; `hub_cid` 60 seconds | expire |

**Legacy until phase 4.** `access_events` still has a row per request (path, user agent, raw IP, place, device). Its raw IP and user agent go at 90 days from phase 0; its other columns are replaced by sign-in events and visit records in phase 4 and then retired.

**Never stored, anywhere:** text a member typed (search queries, form fields, messages) in the event log; names or emails in labels; a fingerprint hash or any identifier derived from combining device details; an IP address on interaction, friction, error or business events (only on sign-in events, and only for 90 days); the full combination of device details in a rollup.

**Where each device field is collected, and under what basis:** browser, OS and device type on sign-in events are parsed server-side from the header the browser already sent (legitimate interest, security); client hints, exact viewport and orientation are read by browser JavaScript, so they exist only on events from members who allowed tracking (consent). See [Device and viewport details](#device-and-viewport-details).

### Device and viewport details

For analytics the log records what a member's browser and screen actually are, in enough detail to answer "which Chrome and Safari versions, which OS versions, which window sizes and orientations do we need to support":

| Field | Example | Notes |
|---|---|---|
| `browser` / `browser_version` | Chrome / 126.0.6478.127 | full version where the browser reports it, otherwise what the user-agent string gives |
| `os` / `os_version` | macOS / 14.5 | **null when not knowable** (see below), never a misleading frozen value |
| `device_type` | desktop, phone, tablet | |
| `viewport_w`, `viewport_h` | 1437 x 812 (CSS pixels) | read when each event is recorded, so a resized window or rotated phone shows up |
| `orientation` | portrait, landscape | from the screen, not the user agent |
| `touch`, `pointer` | has touch points; `coarse` (finger), `fine` (mouse, trackpad), `none` | from the browser; **what tells an iPad from a Mac** (see [Decisions the rollups must support](#decisions-the-rollups-must-support)) |
| `display_mode` | `browser`, `standalone`, `minimal-ui`, `fullscreen`, `window-controls-overlay` | whether the Hub was opened as an installed app, from the `display-mode` media query (and `navigator.standalone` for older iOS Safari); see [Installed app](#installed-app) |
| `device_class` | desktop, phone, tablet | computed on the client from the above (user agent alone mislabels iPads) with the server's user-agent parse as the fallback for sign-in events |
| `device_source` | `client_hints` or `user_agent` | how reliable the versions are, so an analysis can filter to the trustworthy ones |

**Where each comes from, and what it can and can't tell us.** Browsers are deliberately removing detail from the user-agent string, so a plain parser cannot give exact versions any more:

- **Chrome and other Chromium browsers** reduce the user-agent string to a significant version and a generic device token; the full version, the real OS version and the device model are available only through User-Agent Client Hints, which a page must ask for (`navigator.userAgentData.getHighEntropyValues(["platformVersion", "fullVersionList", "model"])`). That API is experimental, not available in every widely used browser, and the browser may refuse. So the client asks for the hints where it can and falls back to the user-agent string.
- **Safari and Firefox** give a browser version in the user-agent string but no client hints. From general knowledge (not from a source I could open here): their macOS version in that string is a fixed value that doesn't change, and Windows 11 reports as Windows 10, so those OS versions are recorded as **null** rather than wrong. iOS reports its real version in the string.
- **The server** parses the user-agent header it already receives when someone signs in (with a maintained parser, not hand-written patterns), so sign-in events always have a browser and OS name and whatever versions the string honestly carries.
- **Viewport and orientation** come only from the browser (`innerWidth`, `innerHeight`, the screen's orientation), so they exist only on consented interaction events.

**Privacy handling.** Exact versions, an exact window size and an OS version together are a fingerprint. This is first-party data on events that already identify the member, so the concern is not tracking across sites (nothing is hashed, no fingerprint id is computed or stored, nothing is shared); it is that anonymous aggregates must not point at one person:

- Detailed fields live **with the event they are on** and expire with it (interaction events: 13 months). Business events don't carry them; a business event is tied back to the click and visit that produced it through the correlation id, which is where the device details live.
- **Sign-in events and visit summaries keep their browser and OS versions for 13 months** (decided), the same window as interaction events, then only the coarse fields: browser family, OS family, device type. So "did this member's problem start after a browser update?" can be answered for a year, and no indefinite per-person device history builds up on the records kept until a member asks. Exact viewport size and orientation are on interaction events only (they come from the browser, so they need consent) and go with them. The raw user agent and IP still go at 90 days; the parsed versions are what the extra months keep. Analytics never depended on this: the daily rollups below read sign-in events too, so versions are counted before anything is coarsened, including for members who never allowed tracking.
- **Rollups keep these distributions indefinitely, mostly one dimension at a time** (the decision data for browser, OS and layout support): browser by `major.minor` version; OS by `major.minor` version; viewport **width in 100-pixel bins** and **height in 100-pixel bins** (plus the named breakpoint bands: under 360, 360-479, 480-767, 768-1023, 1024-1279, 1280-1535, 1536 and up); orientation; device type. Counts only: events, visits and distinct members per day, week and month, with no member ids in a rollup. A single-dimension count ("members whose window is 1400-1499 pixels wide") identifies no one, so those are never suppressed. Combinations are allowed only where a decision needs them, and the complete list is [Decisions the rollups must support](#decisions-the-rollups-must-support); a cell of a combination under five distinct members is folded into "other". The test is the ICO's for statistics, "aggregate statistics that cannot identify people". A full cross-product (this Chrome on this OS at this window size) is deliberately not kept: in a membership this size it would be cells of one or two people, and it would be the most identifying thing in the log.
- **Page-level rollups, for optimising a page for the screens that use it.** Each page view records the viewport at that moment, so **route by width band, route by orientation and route by device type** are kept indefinitely (route is always the template, `/prickles/[id]`, never a real path). **Staff and members are separate audiences:** every one of those pairs is also kept by `audience` (`staff` or `member`, from who the actor was, not from where they were, so an admin looking at a member page counts as staff), because admins often work from different devices on their pages than members do. For the small audiences this matters: the admin area has a handful of users, so a page-by-width cell there can be one person. Staff-only routes are therefore **exempt from the five-member fold**: those rollups are counts per day, readable only by staff, and describe the staff's own screens; they are still personal data about those staff and are covered by the same notice. Member-facing pages keep the fold. Before any of this ages out, the **raw page views with their viewport are queryable for 13 months** (the events themselves), so a page can be analysed at full detail for a year and from rollups after that.
- **Viewport coverage is a number, not an assumption.** Each rollup also stores the share of visits that reported a viewport, so a chart can say "viewport known for 94% of visits". A member in the EU, EEA or UK who has not allowed tracking has no viewport in the log; their browser and OS versions are still counted, from the sign-in event. **The UK's statistical-purposes exception is a real option, and a decision, not a refusal.** The ICO's conditions (read directly, see Sources): the *sole* purpose is gathering statistics on how the service is used to improve it; the result is aggregate; it "does not allow you to monitor or track individual visitors"; individual-level data is kept only as long as needed to aggregate it; and there is a notice and a simple way to object. Our viewport collection fails the "don't track individuals" test today, because it rides on identified events. Using the exception would mean a **second, anonymous collection path**: the browser posts `{ route template, width, height, orientation, device class, audience }` with no user id, session or cookie, and the server only increments rollup counters, stores no event, and does not keep the request's IP. That serves UK members who haven't accepted tracking, and nobody else: EU and EEA members still need consent for browser-side collection (the French regulator has a similar exemption; the other regulators' positions are unsettled). The cost is a second path to maintain, a notice, and an objection switch. Whether it is worth it depends on one number we can read from the data: the share of members whose `access_events.country` is GB. If it is small, skip it; if it is a meaningful share of the people who haven't consented, build it as an optional phase after the rollups exist.
- **Consent follows the source.** Reading client hints and window size is JavaScript that makes the browser report information to our server, which the EDPB treats as access to the device (see the note in `docs/ANALYTICS.md`), so those fields are collected only where interaction tracking is allowed. The server-side parse of the header on sign-in does not read anything from the device and stays under legitimate interest (security).

### Decisions the rollups must support

Rollups exist to inform decisions, so their dimensions are chosen backwards from those decisions, not from what is easy to count. Each approved set below is a **one- or two-dimension table** (or, where a decision genuinely needs it, three), with counts of events, visits and distinct members per day, week and month. A set not on this list is not kept.

| Decision | What it needs | Approved rollup sets |
|---|---|---|
| Which browsers and versions to support, which features to use | each browser's version, and **which family the version belongs to** (a bare version number means nothing) | browser family x `major.minor`; OS family x `major.minor`; browser family x OS family (needed because every browser on iOS is WebKit, so "Chrome on iOS" is governed by the iOS version, not Chrome's) |
| Layout and breakpoints | the viewport, with no need to know the browser | width bins; height bins; width band x height band (above-the-fold); orientation x width band |
| Which platforms to build or polish for (iPhone, iPad, Android phone, Android tablet, desktop) and whether a native app is worth it | the **platform**: device class x OS family, plus whether the PWA is installed and touch is the input | **platform** (device class x OS family); platform x `display_mode` (installed app or browser tab); platform x `pointer` (touch or mouse); installs per week by platform (`app_installed` x platform, `install_prompt_available` x platform) |
| Tablet design: landscape against portrait | orientation by tablet, and by size | platform x orientation; platform x orientation x width band (tablets only) |
| Optimising one page for the screens that use it | the page by viewport | route x width band; route x platform; route x orientation; **route x device class x orientation** (the one three-way set, for pages used on tablets) |
| Staff pages against member pages | every set above, split by audience | `audience` (staff or member) x each set above |

Rules that keep this from becoming the fingerprint it must not be: a cell of any combined set with fewer than five distinct members is folded into "other", except on staff-only routes (see above); the sets above are the whole list, and **browser version x OS version x exact viewport is not on it**, nor is anything that adds a person-level identifier. Raw events, with the exact values, stay queryable for 13 months for any question the rollups can't answer.

**Two things a plain user-agent parser gets wrong, and so two extra fields.**

- **iPads look like Macs.** Safari on iPadOS asks for desktop websites by default and reports itself as a Mac (from general knowledge, not a source I could open here), so the user agent alone cannot tell an iPad from a laptop, and the "iPhone vs iPad vs Android" decisions would be quietly wrong. The browser adds what settles it: `touch` (whether it has touch points) and `pointer` (`coarse` for a finger, `fine` for a mouse or trackpad). A Mac that reports touch is an iPad; this is how `device_class` (desktop, phone, tablet) is computed, on the client, and why those fields exist.
- **An installed app is invisible to the user agent.** The Hub is a PWA (members on iOS must install it to receive push notifications). `display_mode` (`browser` or `standalone`) records whether it was opened as an installed app, which is the clearest single signal for "native app or not".

Both are small enumerations and only collected where tracking is allowed, like the viewport.

### Installed app

"Installed" means the same thing on every platform: the member added the Hub as an app, and it opens in its own window or full screen. The manifest sets `display: "standalone"`, so **iPhone Add to Home Screen, Android Install app (and Add to Home screen), and Chrome or Edge desktop's Install app (the icon in the address bar) all produce a launch where `display_mode` is `standalone`.** `components/InstallAppPrompt.tsx` already uses that same check. Because `display_mode` is recorded on every event, an installed launch shows up without anyone nudging anyone, and platform x `display_mode` separates the cases: standalone on iOS is Add to Home Screen, on desktop Chrome or Edge it is the address-bar install.

Two kinds of signal, because "is it installed" and "when did they install it" are different questions:

- **Every launch**: `display_mode` on each event, as above. Works on iOS, Android and desktop. An installed copy shares its sign-in and storage with the browser on the same device, so it needs no separate login and the consent choice carries over.
- **The moment of installing** (`app_installed`, from the browser's `appinstalled` event): Chrome and Edge on Android and desktop only. **iOS Safari has no install event**, so for iOS the first launch in standalone mode is the nearest thing, found by query ("this member's first `standalone` visit").
- **The offer** (`install_prompt_available`, from `beforeinstallprompt`, Chromium only): fires when the browser decides the Hub can be installed, including when the member never sees our own prompt. It lets us measure a nudge later (offered, accepted, dismissed) and count how many installs happen with no nudge at all, which is the baseline you'd want before deciding whether a nudge is worth building. The Hub has no desktop nudge today; the install in the screenshot is Chrome's own.

`app_installed` and `install_prompt_available` are consent-class events (the browser reports them), counted in rollups as event name x platform, so "installs per week on each platform" is a permanent chart.

### What a scrub keeps and removes

A scrub (when a window expires, or a member asks) **keeps the record's shape**: the same columns, the same row id, the same event. It removes or coarsens only the fields that can point at a person, and leaves everything that need not go. Each column of `events` is classed once, in the catalog, and the scrub routine reads the class; there is no per-event code.

| Class | Columns | When a window expires (interaction, friction, error) | When a member asks (any event type) |
|---|---|---|---|
| **Kept as is** | row id, event name, the allowlisted properties (facts such as which action, a count, a status, never typed text), route template, `source`, `occurred_at` for business events | kept | kept |
| **Time, coarsened** | `occurred_at` on interaction, friction and error events | **truncated to the day** | kept as is (exact time of a business fact stays; the audit rows it matches are anonymised by the same request) |
| **Identity** | actor user id, subject member id, `entity_id` when it names a person's record, `session_id`, `correlation_id` | **nulled** | **nulled** |
| **Network** | raw IP, raw user agent | already gone at 90 days | nulled |
| **Place** | country, region, city | kept (coarse) | nulled |
| **Device detail** | browser and OS versions, exact viewport width and height, orientation | **coarsened**: major version, 100-pixel bin, orientation kept | coarsened the same way |
| **Coarse device** | browser family, OS family, device type | kept | kept |
| **Marker** | `scrubbed_at`, `scrub_reason`: `expired` (a window ran out), `erased` (the member asked), `objected` (an objection under Art. 21), `withdrawn` (consent withdrawn), `staff` (a cleanup) | `expired` | `erased`, `objected` or `withdrawn` |

What is left after an expiry is the interaction event with no person attached, the time as a day, and the device as bins: still a useful row for a page-by-screen question years later, which is why rollups are not the only thing that survives. It is treated as anonymous only because nothing in it links to a person or to another record; whether the remaining combination of route, day and device bins is anonymous *enough* is exactly the kind of judgement counsel should confirm, and the fallback, if it is not, is to delete those rows outright (the rollups hold their counts).

The same principle applies to a member's request: a business event keeps its name, time and facts, and loses only the references that say whose it was. A deleted project is a soft-deleted record that stays until they ask; the request is what removes the person from it.

### Mechanism

- **Soft delete is a mechanism within a category, not a category with its own clock.** Every row has `deleted_at`; views read live rows only, and a soft-deleted row **keeps the retention of the category it belongs to.** A project a member deletes is hidden, and its records are kept until they ask, like every business record; an interaction event hidden because it was recorded wrongly still expires with the other interaction events. Nothing is purged because it was soft-deleted. Two things must be said plainly where a member sees them (the `/privacy` page and the delete action's wording): that deleting in the app hides something rather than removing it from our records, and that a request does remove it.
- **Removal happens on request, or when a window expires: by scrubbing, not by purging.** `anonymise_user_events(user_id)` (a member asked) and the expiry job run the same routine, which reads each column's class from the catalog and removes or coarsens only the personal ones, leaving the rest of the row intact (see [What a scrub keeps and removes](#what-a-scrub-keeps-and-removes)). The row is never physically removed: ids that other records point at (audit rows, correlation chains) stay valid, and there is no grace period to wait out; a mistake is recovered from backups, which roll off on the provider's schedule. Nothing runs it automatically for business events.
- **A scheduled job enforces the windows that exist** (interaction and friction events at 13 months, errors at 90 days, raw IP and user agent at 90 days), reading each event type's window from the catalog, so a new event can't be added without saying how long it lives. Business events' window is "until asked", also in the catalog, so it is a stated choice and not an omission.
- **Rollups before deletion.** The job never scrubs interaction or friction rows until their daily, weekly and monthly rollups exist (counts per event, route, control and the bucketed device dimensions (browser and OS major version, device type, viewport width band, orientation), with cells under five members folded into "other", plus distinct-member counts per period, which cannot be rebuilt from daily numbers). Year-over-year views read the rollups for anything older than 13 months.
- **Objection and withdrawal** are handled the same way: stop recording for that member (a per-member flag the receiver and `createNotifier` check), and apply `anonymise_user_events` to the classes that no longer have a basis.
- **`audit_log` keeps its rule** (history outlives deleted users), now explicitly "until asked" too: its entries name records and fields, so a member's request to be anonymised covers them as well.

## Access

One table, with the restrictions pushed into RLS and grants, as the repo already does for Slack message content:

- Members can insert their own events (today's policy) and read their own non-sensitive ones.
- Staff read through views. The sensitive columns (IP, place, user agent, GA client id) are excluded from the views' column lists and from `SELECT` grants on the table, like `bronze.slack_messages_meta`; a break-glass view (admin-only, itself logged) can read them.
- `events` itself is not readable by `authenticated` apart from a member's own rows; every audience reads a `security_invoker` view, so RLS still decides.
- Soft-deleted rows, and tombstones, are invisible to every view.

## Migration plan

Each phase ships on its own, keeps everything working, and can be stopped after any of them.

0. **Close today's exposure, now.** A scheduled job that, for `access_events`, first parses each stored user agent into browser, OS and device type with a maintained parser (new columns on `access_events`, filled for new rows and backfilled for old ones; versions only where the string carries them), then nulls raw IPs and user agents after 90 days (the places and parsed fields stay); the usage log stops storing the raw user agent in event context and keeps the parsed fields instead, plus the `/privacy` notice update: what is kept, for how long, the "seat warm" purpose, and how to ask for removal. Nothing is deleted. It needs no new design and removes the open-ended storage of raw IPs; the event log later reuses the same job. Pruning `analytics_events` waits until the rollups exist (phase 3), since losing year-over-year is the cost of pruning early.
1. **Generalise the table.** Rename `analytics_events` to `events` behind a compatibility view; add the new columns (`name` stays the event, plus `correlation_id`, `actor_kind`, `subject_member_id`, `entity_type`, `entity_id`, `deleted_at`); drop the cascade FK in favour of `anonymise_user_events`; add the `event_catalog` table and the registry-to-catalog check. The browser's per-batch context grows from a three-value viewport bucket to the device and viewport fields above (client hints where available, exact viewport and orientation); the receiver validates each field against an enum or a length-capped pattern. No other behavior change.
2. **Correlation.** Browser generates and sets `hub_cid`; `lib/supabase/server.ts` forwards `X-Correlation-Id`; `current_correlation_id()` and `audit_log.correlation_id`; server events carry it.
3. **Business, failed and error events.** Replace `action_completed` with declared Noun Verb triples; add `form_validation_failed` for client-side rejection; map the 41 actions; add the Business facts, Product friction and Engineering views. Update the Feature Usage tables to read them, and add the daily, weekly and monthly **rollups** for interaction and friction events that the 13-month window depends on.
4. **Page views, logins and sessions.** Record `page_viewed` and `login` in `events` (the network details once per sign-in, in restricted columns); port the sessionizing function and the activity feed's session rows to read `events`; **stop the proxy's per-request writes** (see Risks: decided) and retire `access_events` once parity is checked.
5. **Member activities as a projection.** Logins, writing progress, outreach and commitments become projections of business events instead of best-effort inserts; engagement scoring is checked against the old numbers before the inserts are removed.
6. **Later, if wanted:** video watch ranges as events or a view; partitioning `events` by month if volume calls for it (the activity-log doc already sets that bar at tens of millions of rows).

## Risks and open questions

- **Volume.** Interaction events (clicks, impressions) dwarf business events. At the current size one table is fine; the retention windows and a later monthly partition are the levers.
- **Proxy logging: decided.** The proxy currently writes one `access_events` row for *every* signed-in request (page loads, API calls, server-action posts, the header's 30-second On air poll), each with the path, user agent, raw IP and place. The only reason is to know a visit is still alive when the member is doing things that aren't page views (the browser reports page views separately). It costs a database write per request and puts the most sensitive columns on the highest-volume rows. Decision: **stop writing a row per request.** Record the network details *once per sign-in* (a `login` event), take page views from `page_viewed`, and let any event (business, interaction, `page_viewed`) extend a visit, as today's 30-minute-gap rule already does. Supabase also keeps its own auth-session record (created, refreshed, user agent, IP) that can fill any gap. **One visible consequence:** an idle tab no longer keeps a visit alive. Today the On air poll writes a row every 30 seconds while a tab is visible, so the activity feed's visit simply keeps getting longer; afterwards a visit ends 30 minutes after the last real event, which is closer to the truth. Nothing else moves: logins are mirrored from Supabase's own session table (`get_recent_login_sessions`), not from `access_events`, and engagement scoring reads `member_activities`. If idle tabs ever need to count, a heartbeat that fires at most every five minutes and only after real input would do it, without a row per request. Phase 4 below is where this lands; until then nothing changes.
- **IP and place: decided.** Raw IP and user agent are removed after 90 days and recorded only on sign-in events; the coarse place stays with its event. Counsel can confirm, but the exposure no longer grows without limit.
- **Indefinite retention of business events** is a deliberate choice ("seat warm"). It rests on a stated purpose, working erasure on request and a three-year review (see the schedule); the open question for counsel is whether that is enough for EU and UK former members, a small share of a mostly US membership.
- **Server-render navigations** read the correlation cookie from the *previous* interaction; this is fine for correlation but means a page view's `caused_by` can be the previous click.
- **Naming drift.** The catalog check is what stops a hundred slightly different event names; it has to fail CI, not warn.
- **Rewriting the 41 actions** is mechanical (the wrapper already exists), but the Feature Usage tables, the Explore page and the explorer's saved URLs all key on `action_completed`; phase 3 updates them together.

## Out of scope

Replacing `audit_log`, the Silver pipelines for Slack and attendance, `prickle_attendance`'s own table, Sentry, and any change to what is shown to members.
