# The event log (design)

**Status (2026-10-31): accepted through phase 0, which is built (#668 and #671); phases 1-6 are conditional and decided one phase at a time, only where a decision needs the data.** Everything below phase 0 is still a proposal; nothing in it is built except what is marked "exists". It consolidates the Hub's scattered behavioral logs into one low-level event log. The other logs, dashboards and the activity feed become *views* over it.

This is engineering's reading of the regulators' published guidance, not legal advice. Counsel should confirm the retention and consent choices before they are published to members (see [Sources](#sources-and-what-was-not-verified)).

## Decisions so far

1. **One low-level event log; everything else is a view over it.** The activity feed, sessions, analytics, funnels and per-feature dashboards are queries over events, not separate stores.
2. **No audience column.** Developers, product managers and the business get different *views*.
3. **A correlation id, generated by the client**, ties a click, the server work it causes and the database changes together.
4. **Keep everything legally permissible; one table by default.** RLS, column grants and views do the restricting. The lawful basis, the retention windows and what a scrub removes are in [Retention and erasure](#retention-and-erasure) and nowhere else.
5. **Business events are never dropped or anonymised automatically**, only on a member's request: "we keep your seat warm" has to be true, and year-over-year trends need the history.
6. **Segment-style Noun Verb names**, extended with `_failed` (the user's side) and `_error` (the server's side).

## Why

Today "who did what, when" is spread over five stores that overlap and disagree about retention:

| Store | What it is | Written by | Notes |
|---|---|---|---|
| `audit_log` | field-level changes to records | database triggers (any write path) | no FK to users; history outlives them |
| `member_activities` | the CRM timeline | Slack/attendance reprocessing; best-effort inserts for logins, writing progress, outreach; a few triggers | read by engagement scoring |
| `access_events` | every signed-in request, plus browser page views; user agent, GA id, IP and place | the proxy and `/api/track/page-view` | feeds the activity feed's session rows |
| `analytics_events` (**exists**) | clicks, impressions, search, server outcomes (`action_completed`), notifications sent/opened | the browser, server actions, `createNotifier` | erased with the account |
| `video_watch_segments` | watched ranges per video | the lesson player | heatmaps are built on it |

Page views are logged twice, a click and its outcome can only be joined by guessing from time, and each store has its own idea of who may read it and how long it lives.

What the log should make possible, with no new store each time:

- *Developer / UX:* did they open the filter in the search palette, and use it?
- *Product:* they pressed Enter and the form rejected it: which field, how often?
- *Business:* a project was created, a check-in saved, a notification sent.
- *On demand:* login events, video watch stats, one visit's whole story in order.

## The model

One append-only table, `events` (the existing `analytics_events`, generalised; a compatibility view keeps today's functions working during the move).

| Column | Meaning |
|---|---|
| `id`, `occurred_at`, `received_at` | identity and time (client clock corrected for skew, as today) |
| `name` | the event, Noun Verb in snake_case: `project_created` |
| `correlation_id` | the interaction this belongs to ([Correlation](#correlation)) |
| `session_id` | the visit (null for events with none: system sends, webhooks) |
| `actor_user_id`, `actor_kind` | who did it: `member`, `staff`, `system`. An admin in sudo is the actor, with `acting_as_member_id` set, as in the audit log |
| `subject_member_id`, `entity_type`, `entity_id` | what it concerns: the person and the record. First-class columns so "everything about this project" and "this member's timeline" are indexed queries |
| `source` | `client`, `server`, `system`, `trigger` |
| `properties` | the properties the event declares: never names, emails or typed text |
| `context` | route template, app version, and the [device fields](#device-and-viewport) |
| `deleted_at` | hides the row from every view. A mechanism within a category, not a category ([Mechanism](#mechanism)). A scrub also sets `scrubbed_at` and `scrub_reason` |

No foreign key to users: like `audit_log`, an event can outlive the account. Raw IP, user agent and the GA client id stay in this table too, in columns with tighter grants ([Access](#access)).

`actor_kind` and `correlation_id` are independent. An event with a server-generated correlation id (no click linked) is still `actor_kind = member` with the member's id; only cron, webhooks and migrations are `system`.

### Naming

Noun Verb in the past tense for something that happened (`project_created`, `prickle_checkin_saved`, `notification_sent`), stored in snake_case and shown as "Project Created". One attempt produces exactly one of:

- `project_created`: it worked.
- `project_create_failed { reason: validation | permission | precondition, fields? }`: the user's side. The request was refused, including a check the browser made before any server call. A product manager's event.
- `project_create_error`: the server's side. Something unexpected broke. An engineer's event, pointing at Sentry.

All three share a correlation id with the interaction events that led to them (`element_clicked`, ...). There is no generic `form_validation_failed`: every form belongs to an action, so it declares its own `_failed` event. The three are declared together as one *action*, so a success rate is computed from the group and the labels-on-one-metric shape is a view over it.

The 41 server actions wired in #210 are nearly all already Noun Verb; each becomes a declared triple, and `action_completed { action, ok }` goes away.

### The registry and the catalog

The **registry** exists today: `EVENTS` in `lib/analytics/events.ts`, a TypeScript object mapping each event name to the properties it may carry and their types. Anything not in it is dropped by the receiver, which is also the privacy filter:

```ts
element_seen: { name: text(80), route: text(120) },
```

The **catalog** is the same list with more facts per event, declared next to it in the same file (one source, not two lists). Per event:

| Field | Example | Used by |
|---|---|---|
| description | "A named control scrolled into view" | the Explore UI |
| views | `engineering` | which [views](#views) include it |
| basis | `consent` | the receiver (is consent required?) and `/privacy` |
| objectable | `true` | the opt-out flag |
| scrub classes | per column, see [What a scrub does](#what-a-scrub-does) | the scrub routine |
| retention | `13 months` or `until asked` | the scheduled job |
| action group | `project_create` (ties its `_created`, `_failed`, `_error`) | success rates |

A generated `event_catalog` table copies this to SQL so views, the scrub routine and the job read the same facts, and a CI check fails when the two disagree. A new event cannot be added without saying how long it lives.

## Correlation

One id ties the chain: **click -> browser events -> server action -> server events -> database changes**.

- **Generated by the browser** on each interaction as a UUID, attached to its own events and written to a short-lived cookie (`hub_cid`) synchronously in the click handler, so the next request carries it. Server actions can't add custom headers, so a cookie is the carrier (`hub_sid` already works this way).
- **Read by the server** in `lib/supabase/server.ts`, which already forwards the sudo header: it forwards `X-Correlation-Id` the same way (validated as a UUID; generated if absent, so cron and webhooks get one at their entry point).
- **Reaches the database trigger.** PostgREST exposes request headers to triggers as `request.headers`, which is how `current_acting_as_member_id()` works today. `current_correlation_id()` reads `x-correlation-id` and `audit_row_change()` stamps a new `audit_log.correlation_id`. From `project_created` you can jump to the field-level audit rows, and back to the click.
- **Untrusted**, since the client chooses it: used only to correlate, never to authorise, and joined on `(actor_user_id, correlation_id)`, so a member can only confuse their own chain.
- **Best effort, and we can narrow the gap.** A very fast double click, or two controls clicked quickly, can overwrite the cookie before the first request reads it. Passing the id into every action would be invasive. Instead, a shared `SubmitButton` that disables itself while its action is pending (there is none today: no `useFormStatus`, and `useTransition` in 19 files against 58 files with forms) removes most double submits, which is worth doing for its own sake.
- **No consent, no click link, still a record.** The cookie is set only where interaction tracking is allowed. Without it the server generates an id: business events and audit rows still correlate with each other, and just don't link back to a click.

## Views

The log is the store; these are queries. Audience is a property of the *view*. The [catalog](#the-registry-and-the-catalog) says which events each view includes.

| View | Audience | Includes |
|---|---|---|
| **Business facts** | business | the past-tense success events |
| **Product friction** | product management | `_failed` events, empty states seen, abandoned flows |
| **Engineering** | developers / UX | `_error` events, clicks, impressions, search and filter use, timings |
| **Activity feed** (`/admin/activity`) | staff | business facts and sessions merged with `audit_log`, keyset-paginated as today |
| **Sessions** | staff | `page_viewed` grouped into visits: replaces the sessionizing over `access_events` |
| **Member timeline** | staff | everything with this `subject_member_id` |
| **Funnels / Explore / Least-clicked** | everyone | what exists today, reading the same table |
| **Record history** | staff | `audit_log` for a record, linked by correlation id |

### Writing business facts: database triggers where there is a row

A fact about a record (a project created, a book added, a goal deleted) is best captured **by a database trigger on that table, in the same transaction as the write**, as `audit_log` and the check-in trigger already do. That is strictly less "best effort" than an insert from application code, which can fail after the real write succeeded. So the design is: tables that already carry the audit trigger also write the business event (`source = trigger`, with the correlation id from the request header); application code records only what has no row to hang a trigger on (clicks, a notification sent, a search).

### `member_activities`: a projection, not a second copy

A **projection** (read model) is data derived from another source so it can be read in a convenient shape, and which can be rebuilt from that source. `member_activities` is the CRM timeline engagement scoring reads. It stays a **real table**: it has other writers (Slack and attendance reprocessing) and stored `engagement_value` points, so a plain view over `events` can't be all of it. Today three paths fill it: reprocessing, a few triggers (check-ins), and best-effort inserts from application code next to the real action (logins, writing progress, outreach, commitments). The last path is the problem: every feature writes its fact twice, and a failed insert is logged and lost.

The proposal replaces only that last path. For those sources, the timeline row is written by the same trigger that records the business event (so it is atomic with the real write), with the type and points taken from the catalog, and a rebuild function can regenerate them from `events` (the "reprocessable" rule). Slack and attendance keep their pipelines. This does not make one table carry all data: `events` is the log of what happened, `member_activities` is a read model for "what did this member do" and scoring. It is the riskiest phase (scoring must match the old numbers first) and optional.

### What stays separate

`audit_log` is not merged. Database triggers capture the old and new value of every changed field for any write path (API routes, cron, the SQL editor), **fold** repeated changes in one transaction into a single row (a sync that flips a status and back writes nothing), and power the per-record change history. An application-level log would do all three worse. They are linked by the correlation id instead.

`video_watch_segments` stays: interval data with its own aggregation, and other work builds on it. A view can sit next to the events; later it could be re-expressed as `video_segment_watched` events.

## Retention and erasure

### What the guidance requires

- **No fixed period; you must justify one.** The ICO: the UK GDPR "does not set specific time limits for different types of data"; set standard retention periods, and erase *or anonymise* when identification is no longer needed. The EU GDPR's storage-limitation principle is the same.
- **Regulator benchmarks** (recommendations, not limits): CNIL on access logs, six months to one year (up to three with documented need); CNIL on consent-exempt audience measurement, a tracker lifetime of about 13 months and data kept at most 25 months.
- **Erasure (Art. 17)** without undue delay when data is no longer necessary, consent is withdrawn, or an objection is upheld; exceptions include legal claims and statistical purposes where erasure would seriously impair them.
- **California.** The CCPA thresholds probably don't reach this organisation; the principle (say how long, keep no longer than needed) is followed anyway. About 90% of members are in the US.

### Lawful basis per event type

Each catalog entry has a **basis**:

| Basis | Covers | Consent needed? | Member can stop it? |
|---|---|---|---|
| `contract` | the product's own record of what happened in the service the member signed up for: a project created, a commitment cancelled, a notification sent, a login | No | No. Access and erasure still apply |
| `legitimate_interest` | using those facts, and the sign-in network details, to understand how the product is used and keep it secure | No, after a documented balancing test | Yes, by **objection** |
| `consent` | anything the browser reports: clicks, impressions, search, filters, validation friction, viewport and device detail, the visit and correlation cookies | Yes where required (EU, EEA, UK; today's banner) | Yes, by **withdrawing** |

Two separate legal questions get merged under "essential": (1) *does ePrivacy require consent?* It applies when something is stored on or read from the member's device. A server recording that a project was created reads nothing from the device, so business events need no consent for that reason, but `hub_sid` and `hub_cid` are device storage and not strictly necessary (the service works without them), so they stay consent-gated. (2) *does the GDPR require consent to process it?* Not if another basis applies. So business events are always recorded, and aren't linked to clicks for members who haven't agreed. Once a membership ends the `contract` basis weakens, and the same events are kept on `legitimate_interest` for the stated purpose of keeping a returning member's history.

### Objection, withdrawal, erasure

Three different rights, one mechanism: a per-member `analytics_opt_out` flag with a reason, plus the scrub routine.

| | What it is | Applies to | Effect going forward | Past data |
|---|---|---|---|---|
| **Withdrawal** | taking back consent (the banner, or asking us) | `consent` events | the browser stops reporting; the visit and correlation cookies stop | scrubbed (the basis is gone) |
| **Objection** | Art. 21: the member objects to us analysing their usage on legitimate interest | `legitimate_interest` events | excluded from analytics views and rollups; their operational records stay | the analytics copies scrubbed |
| **Erasure** | Art. 17: remove or anonymise my data | all classes, including `contract` | as chosen | scrubbed, including business events |

`/privacy` offers one plain "leave me out" that sets the flag and does withdrawal plus objection together, so a member doesn't need to know which right they mean. Erasure is a separate request. The flag is checked by the receiver (nothing from that member is stored) and by open *measurement* only. Notification **state is business logic and is untouched**: whether a notification was read lives in `in_app_notifications.read_at` (set when opened, dismissed, or resolved by the feature with `resolveInAppNotifications`), and reminders ("you haven't checked out yet") are driven by the feature's own data (`prickle_checkins`, the dismissal tables, `member_reminder_log` for dedup and backoff), never by analytics events. `notification_sent` is the contract record that it went out. `notification_opened` is only a statistic about which link or channel led to the open, so it is the one thing skipped, along with the link tags, for a member who opted out.

### Retention schedule (decided)

The single source for how long things live. The job and `lib/retention.ts` read it; nothing else in this document restates it.

| Data | Basis | Kept identifiable | After that | Why |
|---|---|---|---|---|
| **Business events**: the service's own records and the facts analytics reads | contract, then legitimate interest after membership ends | **until the member asks** | on request: erased or anonymised | "seat warm"; members return years later; trends need history. They hold no content, IP or device detail |
| **Interaction and friction events** (clicks, impressions, search, filters, `_failed`) | consent | **13 months** | scrubbed ([below](#what-a-scrub-does)); **anonymous rollups kept indefinitely** | highest volume and sensitivity; 13 months is CNIL's tracker lifetime and covers same-month comparisons |
| **Server error events** (`*_error`) | legitimate interest | **90 days** (one constant) | deleted | they exist to debug and hold no stack trace; the error-reporting provider keeps its own copy under its own, currently shorter, retention, so the trace may be gone before the row |
| **Visit records** (page views, sessions) | legitimate interest | page trail **13 months** | one summary row per visit (start, end, page count, no paths), kept until asked | "when did they last come back" survives; the trail doesn't |
| **Raw IP and raw user agent** (on sign-in events; old access rows until replaced) | legitimate interest (security) | **90 days** | IP nulled or truncated; raw user agent nulled | the most sensitive columns; place and parsed device are derived once at write time |
| **Device and viewport detail** (versions, exact size, orientation) | consent (browser-sourced), legitimate interest (sign-in header parse) | **13 months**, on interaction events, sign-in events and visit summaries | coarse fields stay (browser family, OS family, device type); detail removed; rollups keep bucketed counts | fingerprint-like, so it expires with the clicks |
| Derived place (country, region, city) | follows its event | with its event | with its event | coarse |
| Backups | | the provider's window | rolls off | erasure completes when backups expire; `/privacy` says so |
| `hub_sid` visit cookie | consent | 30 minutes idle | | |
| `hub_cid` correlation cookie | consent | 60 seconds | | |

Keeping business events indefinitely is a choice that needs three things, and the design includes them: (1) a stated purpose on `/privacy` ("until you ask us to remove it", so a returning member finds their seat as they left it); (2) erasure on request that actually works (`anonymise_user_events`); (3) a review every three years of whether the purpose still holds. The residual risk is for EU and UK former members, a small share of a mostly US membership; it is accepted knowingly.

**Where today differs:** `access_events` keeps raw IPs, user agents and places indefinitely and nothing prunes it (`docs/TODO.md`: "the owner's call, for now"). That is the one real exposure, and phase 0 closes it. `video_watch_segments`, `member_activities` and `audit_log` have no limit, which matches "until asked".

### What a scrub does

A scrub, whether a window expired or a member asked, **keeps the row's shape** (same columns, same id, same event) and removes or coarsens only the fields that can point at a person. Each column is classed once in the catalog; the routine reads the class, with no per-event code.

| Class | Columns | Window expired (interaction, friction, error) | Member asked (any event) |
|---|---|---|---|
| **Kept** | row id, event name, declared properties (facts, never typed text), route template, `source`, `occurred_at` on business events | kept | kept |
| **Time** | `occurred_at` on interaction, friction and error events | truncated to the day | kept |
| **Identity** | actor user id, subject member id, `entity_id` when it names a person's record, `session_id`, `correlation_id` | nulled | nulled |
| **Network** | raw IP, raw user agent | already gone at 90 days | nulled |
| **Place** | country, region, city | kept (coarse) | nulled |
| **Device detail** | versions, exact viewport, orientation | coarsened (major version, 100-pixel bin) | coarsened the same way |
| **Coarse device** | browser family, OS family, device type | kept | kept |
| **Marker** | `scrubbed_at`, `scrub_reason`: `expired` (a retention window ran out, automatic), `requested` (the member asked: erasure, an objection or withdrawing consent), `staff` (a cleanup by staff) | `expired` | `requested` |

An expired interaction event is left with no person, a day and device bins: still useful for a page-by-screen question years later, and treated as anonymous because nothing links it to a person or another record. Whether that combination is anonymous *enough* is for counsel; the fallback is to delete those rows and rely on the rollups.

On request, a business event keeps its name, time and facts and loses only the references that say whose it was.

**Records a member owns by a required id are a separate case; the approach is decided (2026-10-31), the build is not.** Scrubbing nulls the identity columns of an *event*. A record such as a writing goal, progress entry, book or award has `member_id NOT NULL` (and foreign-keyed to `members`), so it cannot be scrubbed the same way. **Decided: re-point those records at a placeholder "former member" row**, which keeps the record's shape and loses the person. The catch is that the content itself can identify someone (a book title, a note in the member's own words), so a table whose content identifies gets its rows deleted instead; that is decided per table when it is built, next to its retention in the catalog. Nothing implements it yet: removal on request is a manual job for staff, and `/privacy` promises only "we either delete it or take your name off it", whichever we choose (the choice is ours, not the member's). A scrub is **irreversible and untraceable** (afterwards we can't find a person's rows to delete them later, or answer an access request about them), so a request for true deletion must be done *before* any anonymising. Tracked in `docs/TODO.md`, "Removal on request for records with a required member id".

### Mechanism

- **Soft delete is the standard way a member's business resources are deleted, and it has no retention clock of its own.** Deleting sets `deleted_at` (and a trigger records the `_deleted` event); views and the app read live rows only; the row keeps the retention of its category, "until the member asks", and a [scrub](#what-a-scrub-does) is the only thing that ever clears columns. It is disclosed once, on `/privacy`; delete screens carry no disclaimer. **Today this is not true:** member deletes of projects, goals, progress entries, starting balances, books and awards are row `DELETE`s with the content kept in `audit_log`, against the repo rule for Local tables (`CLAUDE.md`, "Soft delete in Bronze and Local"). Converting them is `docs/TODO.md`, "Soft-delete member business resources"; the privacy page's wording ("gone from the Hub... our change history keeps what it said") stays true either way.
- **Removal is by scrubbing, never purging.** `anonymise_user_events(user_id)` and the expiry job run the same routine. Ids that other records point at stay valid; mistakes are recovered from backups. Nothing runs automatically for business events.
- **A scheduled job enforces the windows**, reading each event's window from the catalog. Business events' window, "until asked", is also a catalog value, so it is a stated choice and not an omission.
- **Rollups before scrubbing.** The job never scrubs interaction or friction rows until their daily, weekly and monthly rollups exist (counts per event, route, control and the bucketed device dimensions, cells under five members folded into "other", plus distinct-member counts, which can't be rebuilt from daily numbers). Year-over-year reads rollups for anything older than 13 months.
- **`audit_log` keeps its rule** (history outlives deleted users), now "until asked" too: its entries name records and fields, so an erasure request covers them.

## Device and viewport

For decisions about browsers, operating systems, layouts and platforms, the log records what the member's browser and screen are.

| Field | Example | Notes |
|---|---|---|
| `browser`, `browser_version` | Chrome 126.0.6478.127 | full version where the browser reports it |
| `os`, `os_version` | macOS 14.5 | **null when not knowable**, never a misleading frozen value |
| `device_type` | desktop, phone, tablet | computed on the client from `touch` and `pointer` (the user agent alone mislabels iPads), with the server's user-agent parse as the fallback for sign-in events |
| `viewport_w`, `viewport_h` | 1437 x 812 | CSS pixels, read when each event is recorded |
| `orientation` | portrait, landscape | from the screen |
| `touch`, `pointer` | has touch points; `coarse` (finger), `fine` (mouse), `none` | what tells an iPad from a Mac |
| `display_mode` | `browser`, `standalone`, ... | whether the Hub was opened as an installed app |
| `device_source` | `client_hints` or `user_agent` | how reliable the versions are |

There is one device-type field (`device_type`); an earlier draft had a duplicate `device_class`.

**Where each comes from.**

- **Chromium** reduces the user-agent string; full versions, real OS version and device model come only from User-Agent Client Hints (`navigator.userAgentData.getHighEntropyValues`), which is experimental and may be refused. The client asks where it can and falls back to the string.
- **Safari and Firefox** give a browser version but no hints. From general knowledge (not a source opened here): macOS Safari's OS version is frozen and Windows 11 reports as Windows 10, so those OS versions are recorded as null. iOS reports its real version.
- **The server** parses the user-agent header at sign-in with a maintained parser. This reads nothing from the device and stays under legitimate interest.
- **Viewport, orientation, touch, pointer, display mode** come only from the browser, so only where interaction tracking is allowed.

**Rotation and resize.** Today the viewport is read only when an event batch is built, as a three-value bucket (`sm`/`md`/`lg`), and nothing listens for `resize` or `orientationchange`. People rotate or resize to reach something off-screen, which signals friction. A debounced `viewport_changed` interaction event (old and new orientation, width band, route template) fixes that, with the same consent rule.

**Privacy handling.** Exact versions, window size and OS version together are a fingerprint, so:

- Detail lives *with the event it is on* and expires with it. Business events carry none; they link to the click and visit through the correlation id.
- Sign-in events and visit summaries keep versions for 13 months, then only the coarse fields.
- **Rollups keep these distributions indefinitely, mostly one dimension at a time**: browser by `major.minor`; OS by `major.minor`; viewport width and height in 100-pixel bins and named bands (under 360, 360-479, 480-767, 768-1023, 1024-1279, 1280-1535, 1536+); orientation; device type. Counts only, with no member ids. A single-dimension count identifies no one, so it is never folded. A combination is kept only where a decision needs it, listed below; a cell under five distinct members folds into "other".
- A full cross-product (this Chrome on this OS at this window size) is deliberately not kept: at this size it is cells of one or two people.
- **Page-level rollups** (route template x width band, orientation, device type) are kept by `audience` (`staff` or `member`, from who the actor was), because admins use different devices on their pages. Staff-only routes are exempt from the five-member fold (a handful of users): counts per day, readable only by staff, covered by the same notice.
- **Coverage is a number.** Each rollup stores the share of visits that reported a viewport, so a chart can say "viewport known for 94% of visits".

### Decisions the rollups must support

Rollups are chosen backwards from decisions. A set not on this list is not kept.

| Decision | Approved rollup sets |
|---|---|
| Browsers and versions to support | browser family x `major.minor`; OS family x `major.minor`; browser family x OS family (every browser on iOS is WebKit, so it is governed by the iOS version) |
| Layout and breakpoints | width bins; height bins; width band x height band; orientation x width band |
| Platforms to polish (iPhone, iPad, Android, desktop) and whether a native app is worth it | platform (device type x OS family); platform x `display_mode`; platform x `pointer`; members launching as an installed app per month (single dimension, never folded) |
| Tablet landscape against portrait | platform x orientation; platform x orientation x width band (tablets only) |
| One page for the screens that use it | route x width band; route x platform; route x orientation; route x device type x orientation (the one three-way set) |
| Staff against member pages | `audience` x each set above |

**Browser version x OS version x exact viewport is not on the list**, nor is anything that adds a person-level identifier. Raw events with exact values stay queryable for 13 months for anything the rollups can't answer.

### Statistical-purposes exceptions (UK, France)

Both the UK (Data (Use and Access) Act 2025) and France (CNIL's audience-measurement exemption) allow statistics collection without consent under similar conditions: the sole purpose is statistics on how the service is used to improve it; the output is aggregate; individual visitors are not tracked; nothing is cross-referenced with other data or shared; there is a notice and a way to object. The UK condition on retention is that raw per-visit records may be held briefly, only as long as it takes to roll them into aggregates (the ICO suggests daily as a starting point), and must never be used to follow an individual; the CNIL recommends about 13 months for the cookie and 25 for data. The two are similar but not identical, and the CNIL's own pages are authoritative.

Our viewport and click collection rides on identified events, so it fails the "don't track individuals" test. Using the exceptions would mean a **second, anonymous collection path**: the browser posts `{ route template, width, height, orientation, device type, audience }` with no user id, session or cookie, and the server only increments rollup counters, stores no event and keeps no IP. A short-lived raw row is allowed, but only if it carries no user, session or visitor id: the ICO's prohibition is on monitoring individuals ("connecting a visitor ID to their site activity"), not on holding a row for a day. So "keep identified events, then erase fast" does not qualify, while "keep id-less hits for a day, then roll up and delete" would. EU members outside France still need consent for browser-side collection.

**Do we have members there? Not that we know of, and production can't answer yet.** `access_events` covers only the 11 members who have ever signed in to the Hub, none in the UK or France (5 US, 2 Costa Rica, 1 Canada, 1 Malta, 2 unrecorded), and the Kajabi contact data has no country field. The membership team confirms at most about one member in the UK and none known in France. **Decision: not worth building now.** Revisit if that count grows; once the Hub records a country per member, read it there.

### Installed app

"Installed" means the same on every platform: the member added the Hub as an app. The manifest sets `display: "standalone"`, so iPhone Add to Home Screen, Android Install app and Chrome or Edge desktop's address-bar install all launch with `display_mode = standalone`. `components/InstallAppPrompt.tsx` already uses that check.

- **Every launch:** `display_mode` on each event. An installed copy shares sign-in and storage with the browser, so it needs no separate login.
- **The moment of installing** (`app_installed`, from `appinstalled`): Chrome and Edge only. iOS Safari has no install event, so the first `standalone` visit is the nearest thing, found by query.
- **The offer** (`install_prompt_available`, from `beforeinstallprompt`, Chromium only): lets us measure a nudge later and count installs with no nudge, the baseline before deciding to build one.

Both are consent-class events. **Expect tiny numbers:** installs are capped by membership and are likely a handful. The useful long-term figure is a state, how many members launched as an installed app this month (single dimension, never folded); which platform they are on comes from raw events (13 months). Low installs are a weak signal about native-app demand, since iOS hides "Add to Home Screen" and nobody nudges. Better evidence: the phone share of visits, visit frequency among phone users, and how many members turned on browser push.

## Access

One table, with the restrictions in RLS and grants, as the repo does for Slack message content:

- Members can insert their own events and read their own non-sensitive ones.
- Staff read through views. The sensitive columns (IP, place, user agent, GA client id) are excluded from the views' column lists and from `SELECT` grants on the table, like `bronze.slack_messages_meta`. An admin-only break-glass view, itself logged, can read them.
- `events` is not readable by `authenticated` apart from a member's own rows; every audience reads a `security_invoker` view, so RLS still decides.
- Soft-deleted and scrubbed-away data is invisible to every view.

## Migration plan

**Phase 0 is built. Phases 1-6 are conditional:** each is decided on its own, when a question about the product needs what it would add, rather than as a committed plan. The first one with a concrete reason is the rollups in phase 3, which must exist before any usage events are pruned (the first reach 13 months in late 2027).

Each phase ships on its own, keeps the current system working and can be stopped after any of them. Phases 1–3 only add; phases 0 and 4 are the ones that delete or stop writing, so they carry the safeguards.

0. **Close today's exposure (built: #668 keeps the device, #671 is the nightly job; deadline was 2027-01-16).** The `/privacy` page already promises 90 days for raw IP and user agent. Checked against production on 2026-10-30, the oldest raw user agent is from 2026-10-18, the oldest raw IP from 2026-10-21 and the oldest user agent in a usage event from 2026-10-20, so the first value passes 90 days on 2027-01-16 (an earlier version of this doc said 2026-11-25, assuming user agents went back to the table's creation; the column is newer). Steps: parse each stored user agent into browser, OS and device type with a maintained parser (new columns on `access_events`, filled for new rows and backfilled); **verify the parsed columns for every row**; only then run the scheduled job that nulls raw IPs and user agents after 90 days (constants in `lib/retention.ts`). Stop storing the raw user agent in event context. This phase **does delete the raw values**, once derived; the places and parsed fields stay. Pruning `analytics_events` waits for phase 3's rollups.
1. **Generalise the table.** Rename `analytics_events` to `events` behind a compatibility view; add `correlation_id`, `actor_kind`, `subject_member_id`, `entity_type`, `entity_id`, `deleted_at`; drop the cascade FK in favour of `anonymise_user_events`; add the catalog table and registry check. Widen the batch context to the device fields; the receiver validates each against an enum or a length-capped pattern. Nothing else changes.
2. **Correlation.** The browser sets `hub_cid`; `lib/supabase/server.ts` forwards `X-Correlation-Id`; `current_correlation_id()` and `audit_log.correlation_id`; server events carry it. Add the shared `SubmitButton`. **Update `/privacy` in the same PR:** the cookie wording there (section "Your choices", "Cookies and similar storage") describes cookies by kind and is not a full list, so `hub_cid` goes next to the visit number as an optional cookie that is only set while usage statistics are on, with its 60-second lifetime, and the page test is updated with it.
3. **Business, failed and error events.** Replace `action_completed` with declared triples; map the 41 actions; add the Business, Product friction and Engineering views; add the rollups the 13-month window depends on; add `viewport_changed`. The Feature Usage tables, Explore and saved explorer URLs all key on `action_completed`: **emit the old and new events side by side for a transition window**, move the readers, then drop the old one.
4. **Page views, logins and sessions.** Record `page_viewed` and `login` in `events` (network details once per sign-in, in restricted columns); port the sessionizing function and the activity feed to read `events`; then **stop the proxy's per-request writes** (see Risks). Before retiring `access_events`, **run old and new side by side for a few weeks and diff** visits, session counts and last-seen per member; retire it only when they agree.
5. **Business facts by trigger, and `member_activities` as a projection** (optional). Tables that already have the audit trigger also write their business event in the same transaction; logins, writing progress, outreach and commitments get their timeline rows from that trigger instead of best-effort inserts, with a rebuild function. Check engagement scoring against the old numbers before removing the inserts. Needs member deletes to be soft deletes first (`docs/TODO.md`, "Soft-delete member business resources"), so a delete is an update the trigger can see.
6. **Later, if wanted:** video watch ranges as events or a view; monthly partitioning of `events` if volume calls for it (the activity-log doc sets that bar at tens of millions of rows).

## Risks and open questions

- **Volume.** Interaction events dwarf business events. One table is fine at this size; the retention windows and a later monthly partition are the levers.
- **Proxy logging: decided.** The proxy writes one `access_events` row for every signed-in request (page loads, API calls, action posts, the header's 30-second On air poll), each with path, user agent, raw IP and place, only so a visit stays alive between page views. Decision: stop writing a row per request; record network details once per sign-in, take page views from `page_viewed`, and let any event extend a visit under the existing 30-minute-gap rule. Supabase's own auth-session record can fill gaps. **Visible consequence:** an idle tab no longer keeps a visit alive, so a visit ends 30 minutes after the last real event, which is closer to the truth. Nothing else moves: logins are mirrored from `get_recent_login_sessions` and `/api/live-room` polls `zoom_participant_events`, not `access_events`. If idle tabs ever need to count, a heartbeat at most every five minutes and only after real input would do it. Lands in phase 4.
- **Business events kept indefinitely** is deliberate ("seat warm"). Whether a stated purpose, working erasure and a three-year review are enough for EU and UK former members is a residual risk the owner **accepted as written on 2026-10-31**, without a counsel review; revisit if the EU or UK share of former members grows.
- **Error-event window.** 90 days, one constant. The error-reporting provider's retention is currently shorter and is not tied to ours; it only means the trace can disappear before the event row does. The privacy notice names no error-reporting vendor, only "an error-reporting provider".
- **Server-render navigations** read the correlation cookie from the *previous* interaction; fine for correlation, but a page view's `caused_by` can be the previous click.
- **Naming drift.** The catalog check is what stops a hundred slightly different event names; it must fail CI, not warn.
- **Renaming `action_completed`** touches the Feature Usage tables, Explore and saved URLs together (phase 3's side-by-side window).
- **Decided 2026-10-31:** the scrub marker has three reasons, `expired`, `requested` and `staff` (which right a member invoked is recorded with the request, not in the marker), and the purpose review for indefinitely kept business events is every three years.

## Out of scope

Replacing `audit_log`, the Silver pipelines for Slack and attendance, `prickle_attendance`'s own table, Sentry, and any change to what is shown to members beyond the `/privacy` page.
