# The event log (design)

**Status: proposal, for review. Nothing here is built except what is marked "exists".** It consolidates the Hub's scattered behavioral logs into one low-level event log, with the other logs, dashboards and the activity feed becoming *views* over it.

## Decisions so far

These came out of discussion and are the constraints this design works within.

1. **One low-level event log; everything else is a view over it.** The member activity feed, sessions, analytics, funnels and the per-feature dashboards are queries over events, not separate stores.
2. **No audience column.** Developers, product managers and the business get different *views*, not a `level` field on every row. (How a view knows which events it includes is in [Views](#views).)
3. **Correlation ID, generated by the client**, ties a click, the server work it causes, and the database changes together, including the database trigger.
4. **Keep everything legally permissible; prefer soft deletes.** See [Retention, erasure and soft delete](#retention-erasure-and-soft-delete).
5. **One table by default.** Use RLS, column grants and views for restrictions rather than splitting tables.
6. **Segment-style Noun Verb event names**, extended with a user-side `failed` and a server-side `error`. See [Naming](#naming).

## Why

Today "who did what, when" is spread over five stores that overlap and disagree about retention:

| Store | What it is | Written by | Notes |
|---|---|---|---|
| `audit_log` | field-level changes to records | database triggers (any write path) | immutable-ish; no FK to users, history outlives them |
| `member_activities` | the CRM timeline | Slack/attendance reprocessing (Silver); best-effort inserts for logins, writing progress, outreach | read by engagement scoring |
| `access_events` | every signed-in request, plus browser page views; user agent, GA id, IP and place | the proxy and `/api/track/page-view` | feeds the activity feed's "session" rows and login activity |
| `analytics_events` (**exists**) | clicks, impressions, search, server outcomes (`action_completed`), notifications sent/opened | the browser, server actions, `createNotifier` | erased with the account |
| `video_watch_segments` | watched/viewed ranges per video | the lesson player | other work is building heatmaps on it |

Page views are logged twice (`access_events`, `analytics_events`), a click and its outcome can't be joined except by guessing from time, and each store has its own idea of who may read it and how long it lives.

What the unified log should make possible, with no new store each time:

- *Developer / UX:* "did they open the filter in the search palette, and use it?"
- *Product:* "they pressed Enter and the form rejected it: which field, how often?"
- *Business:* "a project was created", "a check-in was saved", "a notification went out".
- *Low-level data on demand:* login events, video watch stats, one visit's whole story in order.

## The model

One append-only table, `events` (the existing `analytics_events`, generalised; a compatibility view keeps today's functions working during the move).

| Column | Meaning |
|---|---|
| `id`, `occurred_at`, `received_at` | identity and time (client clock corrected for skew, as today) |
| `name` | the event, Noun Verb in snake_case: `project_created` |
| `correlation_id` | the interaction this belongs to (see [Correlation](#correlation)) |
| `session_id` | the visit (null for events with no visit: system sends, webhooks) |
| `actor_user_id`, `actor_kind` | who did it: `member`, `staff`, `system`; an admin in sudo is the actor with `acting_as_member_id` set, as in the audit log |
| `subject_member_id`, `entity_type`, `entity_id` | *what it concerns*: the person (when there is one) and the record. First-class columns, not free properties, so "everything about this project" and "this member's timeline" are indexed queries |
| `source` | `client`, `server`, `system`, `trigger` |
| `properties` | allowlisted properties from the event's declaration (see [The catalog](#the-catalog)): never names, emails or typed text |
| `context` | route template, viewport, app version; **not** the network details |
| `deleted_at` | soft delete (see below) |

No foreign key to users: like `audit_log`, an event can outlive the account (anonymised, see below). The network and device details that `access_events` keeps today (IP address, place, user agent, GA client id) stay in this same table in columns with tighter grants (see [Access](#access)), not in a second table.

### Naming

Segment's recommended style, Noun Verb, in the past tense, for something that happened: `project_created`, `prickle_checkin_saved`, `notification_sent`. Stored in snake_case (as the registry already is) and shown as "Project Created" in the UI by a formatter. Two extensions, as asked:

- **`<noun>_<verb>_failed`: the user's side.** The request was well formed and was refused: validation, permission, a precondition. `project_create_failed { reason: validation | permission | precondition, fields? }`. A product manager's event. It is also what "pressed Enter and the form rejected it" looks like, including when the check ran in the browser before any server call.
- **`<noun>_<verb>_error`: the server's side.** Something unexpected broke: `project_create_error`. An engineer's event (with a pointer to Sentry).

So one attempt produces exactly one of `project_created`, `project_create_failed`, `project_create_error`, plus the interaction events that led to it (`element_clicked`, `form_validation_failed`...), all sharing a correlation id. The 41 server actions wired in #210 are nearly all already Noun Verb (`project_created`, `commitment_cancelled`...); each becomes a triple declared in one place. `action_completed { action, ok }` is replaced by these.

### The catalog

Today the tracking plan is a TypeScript registry (`lib/analytics/events.ts`): which events exist and which properties they may carry. The design keeps that and adds, per event: a description, which **views** it belongs to, its **lawful basis** (`consent` or `operational`, below), whether it is **soft-deleted or purged** on erasure, and its retention window. A migration-time check keeps the TypeScript registry and a small `event_catalog` table in step, so SQL views and the privacy rules read the same facts the code does.

## Correlation

One id ties the chain: **click -> browser events -> server action -> server events -> database changes**.

- **Generated by the browser** on each interaction (click, submit, keypress that submits, navigation) as a UUID. It is attached to the browser's own events, and written to a short-lived first-party cookie (`hub_cid`) synchronously in the click handler, so the request that follows carries it. (Server actions can't add custom headers from the client, so a cookie is the carrier; the visit cookie `hub_sid` from #210 already works this way.)
- **Read by the server** in `lib/supabase/server.ts`, which already forwards the sudo header to the database: it forwards `X-Correlation-Id` the same way (validated as a UUID; if absent, the server generates one, so server-originated work like cron and webhooks gets one at its entry point).
- **Reaches the database trigger.** PostgREST exposes request headers to triggers as `request.headers`: this is exactly how `current_acting_as_member_id()` reads `X-Acting-As` today. A sibling `current_correlation_id()` reads `x-correlation-id`, and `audit_row_change()` stamps a new `audit_log.correlation_id` column. Events recorded by the server use the same value. So from `project_created` you can jump to the exact field-level changes in the audit log, and from an audit row back to the click that caused it.
- **Limits, stated plainly.** Writes from the SQL editor, a migration or a cron job with no request have no header: null (cron jobs that go through the app get a server-generated id). It is **untrusted**, since the client chooses it: it is only ever used to *correlate*, never to authorise, and joins are always on `(actor_user_id, correlation_id)` so one member can only confuse their own chain. A very fast double click can overwrite the cookie before the first request reads it; precise per-call correlation would mean passing the id as an argument to every action, which is invasive, so the cookie is accepted as best-effort.
- **No consent, no click link, still a record.** The correlation cookie is set only when interaction tracking is allowed. Without it the server generates an id, so business events and audit rows still correlate with each other; they just don't link back to a click.

## Views

The log is the store; these are queries. Audience is a property of the *view*, not of every row. A view includes events through the catalog (above), not through naming tricks, so adding an event means declaring which views carry it.

| View | Audience | Includes |
|---|---|---|
| **Business facts** | business | the past-tense success events: `project_created`, `notification_sent`... |
| **Product friction** | product management | the `_failed` events, `form_validation_failed`, empty states seen, abandoned flows |
| **Engineering** | developers / UX | `_error` events, clicks, impressions, search and filter use, timings |
| **Activity feed** (`/admin/activity`) | staff | business facts and sessions, merged with `audit_log` rows, keyset-paginated as today |
| **Sessions** | staff | `page_viewed` grouped into visits, with the page trail: replaces the sessionizing over `access_events` |
| **Member timeline** | staff | everything with this `subject_member_id` |
| **Funnels / Explore / Least-clicked** | everyone | what exists today, reading the same table |
| **Record history** | staff | `audit_log` for a record, linked to the events with the same correlation id |

`member_activities` stops being a store for the *append-only* sources (logins, writing progress, outreach, commitments): it becomes a projection of business events, reprocessable like the Slack and attendance rows already are, replacing the "best-effort insert alongside the primary action" pattern. Slack and prickle attendance keep their own reprocessing pipelines.

### What stays separate, and why

`audit_log` is not merged into the event log. It is the data-change journal: database triggers capture the old and new value of every changed field for any write path (API routes, cron, the SQL editor), it **folds** repeated changes made by one transaction into a single row (first old value, last new value, dropped if they net out: a sync that flips a status and flips it back writes nothing), and it powers the per-record change-history dialog. An application-level event log would do all three worse. The two are **linked** by the correlation id instead, which gets the "one story" without losing what the audit log is good at.

`video_watch_segments` stays for now: it is interval data with its own aggregation (heatmaps, engagement), and other work is building on it. Its watch ranges can be exposed through a view next to the events (or, later, re-expressed as `video_segment_watched` events); not in the first phases.

## Retention, erasure and soft delete

Principles: record what is legitimately needed, keep it as long as it is useful and permitted, never keep what must not be kept, and prefer reversible deletion. **This section needs counsel's review** (the lawful bases, the retention windows and how IP addresses are treated are legal questions, not engineering ones); the mechanism below is built to support the strictest reading.

- **Two kinds of event, two lawful bases**, recorded per event in the catalog:
  - `operational`: the product's own record of what happened (`project_created`, a notification sent, a login). Recorded regardless of the analytics choice, as the audit log and activity log already are.
  - `consent`: behavioral tracking (clicks, impressions, search, validation friction). Recorded only where the visitor has agreed, as today (`hub_sid`, the banner).
- **Soft delete first.** Every row has `deleted_at`. Views and the app read only live rows. Deleting is setting a timestamp, so it is reversible and auditable.
- **Anonymise rather than erase when a person leaves.** When an account is deleted or erasure is requested: the actor and subject columns are nulled and identifying context (user agent, IP, place, GA id) is blanked, in one routine, `anonymise_user_events(user_id)`. Operational events that are facts about the community (a project was created, a prickle took place) stay as anonymous rows; consent events are soft-deleted outright.
- **Purge after a grace period where the law requires it.** Soft-deleted rows that are identifiable, or past their retention window, are physically removed by a scheduled job after a short grace period (so an accidental delete is recoverable), and the retention windows live in the catalog: for example interaction events 13 months, network details (IP, place) 90 days, business events indefinitely. The numbers are for counsel and you to set; the mechanism is the point.
- **The audit log keeps its current rule** (history outlives deleted users), now explicitly under the same review.

## Access

One table, with the restrictions pushed into RLS and grants, as the repo already does for Slack message content:

- Members can insert their own events (today's policy) and read their own non-sensitive ones.
- Staff read through views. The sensitive columns (IP, place, user agent, GA client id) are excluded from the views' column lists and from `SELECT` grants on the table, like `bronze.slack_messages_meta`; a break-glass view (admin-only, itself logged) can read them.
- `events` itself is not readable by `authenticated` apart from a member's own rows; every audience reads a `security_invoker` view, so RLS still decides.
- Soft-deleted rows are invisible to every view.

## Migration plan

Each phase ships on its own, keeps everything working, and can be stopped after any of them.

1. **Generalise the table.** Rename `analytics_events` to `events` behind a compatibility view; add the new columns (`name` stays the event, plus `correlation_id`, `actor_kind`, `subject_member_id`, `entity_type`, `entity_id`, `deleted_at`); drop the cascade FK in favour of `anonymise_user_events`; add the `event_catalog` table and the registry-to-catalog check. No behavior change.
2. **Correlation.** Browser generates and sets `hub_cid`; `lib/supabase/server.ts` forwards `X-Correlation-Id`; `current_correlation_id()` and `audit_log.correlation_id`; server events carry it.
3. **Business, failed and error events.** Replace `action_completed` with declared Noun Verb triples; add `form_validation_failed` for client-side rejection; map the 41 actions; add the Business facts, Product friction and Engineering views. Update the Feature Usage tables to read them.
4. **Page views, logins and sessions.** Record `page_viewed` and `login` in `events` (with the network details in restricted columns); port the sessionizing function and the activity feed's session rows to read `events`; stop writing `access_events` once parity is checked, then retire it. The proxy's per-request logging exists to keep sessions alive across API-only activity and needs its own replacement before it can go.
5. **Member activities as a projection.** Logins, writing progress, outreach and commitments become projections of business events instead of best-effort inserts; engagement scoring is checked against the old numbers before the inserts are removed.
6. **Later, if wanted:** video watch ranges as events or a view; partitioning `events` by month if volume calls for it (the activity-log doc already sets that bar at tens of millions of rows).

## Risks and open questions

- **Volume.** Interaction events (clicks, impressions) dwarf business events. At the current size one table is fine; the retention windows and a later monthly partition are the levers.
- **Proxy logging.** Every signed-in request is written to `access_events` today so sessions stay alive; phase 4 needs a cheaper keep-alive (the session id already exists).
- **IP and place.** They are the most sensitive columns in the log. Whether to keep them at all, and for how long, is the first question for counsel.
- **Server-render navigations** read the correlation cookie from the *previous* interaction; this is fine for correlation but means a page view's `caused_by` can be the previous click.
- **Naming drift.** The catalog check is what stops a hundred slightly different event names; it has to fail CI, not warn.
- **Rewriting the 41 actions** is mechanical (the wrapper already exists), but the Feature Usage tables, the Explore page and the explorer's saved URLs all key on `action_completed`; phase 3 updates them together.

## Out of scope

Replacing `audit_log`, the Silver pipelines for Slack and attendance, `prickle_attendance`'s own table, Sentry, and any change to what is shown to members.
