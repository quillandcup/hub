# The event log (design)

**Status: proposal, for review. Nothing here is built except what is marked "exists".** It consolidates the Hub's scattered behavioral logs into one low-level event log, with the other logs, dashboards and the activity feed becoming *views* over it.

## Decisions so far

These came out of discussion and are the constraints this design works within.

1. **One low-level event log; everything else is a view over it.** The member activity feed, sessions, analytics, funnels and the per-feature dashboards are queries over events, not separate stores.
2. **No audience column.** Developers, product managers and the business get different *views*, not a `level` field on every row. (How a view knows which events it includes is in [Views](#views).)
3. **Correlation ID, generated by the client**, ties a click, the server work it causes, and the database changes together, including the database trigger.
4. **Keep everything legally permissible; prefer soft deletes.** Business events are recorded unconditionally only where they are the service's own record; usage analysis rests on legitimate interest with a right to object; browser tracking stays consent-gated. Retention windows are set per event type from the regulators' published guidance. See [Retention, erasure and soft delete](#retention-erasure-and-soft-delete).
5. **One table by default.** Use RLS, column grants and views for restrictions rather than splitting tables.
6. **Segment-style Noun Verb event names**, extended with a user-side `failed` and a server-side `error`. See [Naming](#naming).

## Why

Today "who did what, when" is spread over five stores that overlap and disagree about retention:

| Store | What it is | Written by | Notes |
|---|---|---|---|
| `audit_log` | field-level changes to records | database triggers (any write path) | immutable-ish; no FK to users, history outlives them |
| `member_activities` | the CRM timeline | Slack/attendance reprocessing (Silver); best-effort inserts for logins, writing progress, outreach | read by engagement scoring |
| `access_events` | every signed-in request, plus browser page views; user agent, GA id, IP and place | the proxy and `/api/track/page-view` | feeds the activity feed's "session" rows and login activity |
| `analytics_events` (**exists**) | clicks, impressions, search, server outcomes (`action_completed`), notifications sent/opened | the browser, server actions, `createNotifier` | erased with the account |
| `video_watch_segments` | watched/viewed ranges per video | the lesson player | other work is building heatmaps on it |

Page views are logged twice (`access_events`, `analytics_events`), a click and its outcome can't be joined except by guessing from time, and each store has its own idea of who may read it and how long it lives.

What the unified log should make possible, with no new store each time:

- *Developer / UX:* "did they open the filter in the search palette, and use it?"
- *Product:* "they pressed Enter and the form rejected it: which field, how often?"
- *Business:* "a project was created", "a check-in was saved", "a notification went out".
- *Low-level data on demand:* login events, video watch stats, one visit's whole story in order.

## The model

One append-only table, `events` (the existing `analytics_events`, generalised; a compatibility view keeps today's functions working during the move).

| Column | Meaning |
|---|---|
| `id`, `occurred_at`, `received_at` | identity and time (client clock corrected for skew, as today) |
| `name` | the event, Noun Verb in snake_case: `project_created` |
| `correlation_id` | the interaction this belongs to (see [Correlation](#correlation)) |
| `session_id` | the visit (null for events with no visit: system sends, webhooks) |
| `actor_user_id`, `actor_kind` | who did it: `member`, `staff`, `system`; an admin in sudo is the actor with `acting_as_member_id` set, as in the audit log |
| `subject_member_id`, `entity_type`, `entity_id` | *what it concerns*: the person (when there is one) and the record. First-class columns, not free properties, so "everything about this project" and "this member's timeline" are indexed queries |
| `source` | `client`, `server`, `system`, `trigger` |
| `properties` | allowlisted properties from the event's declaration (see [The catalog](#the-catalog)): never names, emails or typed text |
| `context` | route template, viewport, app version; **not** the network details |
| `deleted_at` | soft delete (see below) |

No foreign key to users: like `audit_log`, an event can outlive the account (anonymised, see below). The network and device details that `access_events` keeps today (IP address, place, user agent, GA client id) stay in this same table in columns with tighter grants (see [Access](#access)), not in a second table.

### Naming

Segment's recommended style, Noun Verb, in the past tense, for something that happened: `project_created`, `prickle_checkin_saved`, `notification_sent`. Stored in snake_case (as the registry already is) and shown as "Project Created" in the UI by a formatter. Two extensions, as asked:

- **`<noun>_<verb>_failed`: the user's side.** The request was well formed and was refused: validation, permission, a precondition. `project_create_failed { reason: validation | permission | precondition, fields? }`. A product manager's event. It is also what "pressed Enter and the form rejected it" looks like, including when the check ran in the browser before any server call.
- **`<noun>_<verb>_error`: the server's side.** Something unexpected broke: `project_create_error`. An engineer's event (with a pointer to Sentry).

So one attempt produces exactly one of `project_created`, `project_create_failed`, `project_create_error`, plus the interaction events that led to it (`element_clicked`, `form_validation_failed`...), all sharing a correlation id. The 41 server actions wired in #210 are nearly all already Noun Verb (`project_created`, `commitment_cancelled`...); each becomes a triple declared in one place. `action_completed { action, ok }` is replaced by these.

### The catalog

Today the tracking plan is a TypeScript registry (`lib/analytics/events.ts`): which events exist and which properties they may carry. The design keeps that and adds, per event: a description, which **views** it belongs to, its **basis** (`contract`, `legitimate_interest` or `consent`, below), whether a member can **object** to it, whether it is **soft-deleted or anonymised** on erasure, and its **retention window**. A migration-time check keeps the TypeScript registry and a small `event_catalog` table in step, so SQL views and the privacy rules read the same facts the code does.

## Correlation

One id ties the chain: **click -> browser events -> server action -> server events -> database changes**.

- **Generated by the browser** on each interaction (click, submit, keypress that submits, navigation) as a UUID. It is attached to the browser's own events, and written to a short-lived first-party cookie (`hub_cid`) synchronously in the click handler, so the request that follows carries it. (Server actions can't add custom headers from the client, so a cookie is the carrier; the visit cookie `hub_sid` from #210 already works this way.)
- **Read by the server** in `lib/supabase/server.ts`, which already forwards the sudo header to the database: it forwards `X-Correlation-Id` the same way (validated as a UUID; if absent, the server generates one, so server-originated work like cron and webhooks gets one at its entry point).
- **Reaches the database trigger.** PostgREST exposes request headers to triggers as `request.headers`: this is exactly how `current_acting_as_member_id()` reads `X-Acting-As` today. A sibling `current_correlation_id()` reads `x-correlation-id`, and `audit_row_change()` stamps a new `audit_log.correlation_id` column. Events recorded by the server use the same value. So from `project_created` you can jump to the exact field-level changes in the audit log, and from an audit row back to the click that caused it.
- **Limits, stated plainly.** Writes from the SQL editor, a migration or a cron job with no request have no header: null (cron jobs that go through the app get a server-generated id). It is **untrusted**, since the client chooses it: it is only ever used to *correlate*, never to authorise, and joins are always on `(actor_user_id, correlation_id)` so one member can only confuse their own chain. A very fast double click can overwrite the cookie before the first request reads it; precise per-call correlation would mean passing the id as an argument to every action, which is invasive, so the cookie is accepted as best-effort.
- **No consent, no click link, still a record.** The correlation cookie is set only when interaction tracking is allowed. Without it the server generates an id, so business events and audit rows still correlate with each other; they just don't link back to a click.

## Views

The log is the store; these are queries. Audience is a property of the *view*, not of every row. A view includes events through the catalog (above), not through naming tricks, so adding an event means declaring which views carry it.

| View | Audience | Includes |
|---|---|---|
| **Business facts** | business | the past-tense success events: `project_created`, `notification_sent`... |
| **Product friction** | product management | the `_failed` events, `form_validation_failed`, empty states seen, abandoned flows |
| **Engineering** | developers / UX | `_error` events, clicks, impressions, search and filter use, timings |
| **Activity feed** (`/admin/activity`) | staff | business facts and sessions, merged with `audit_log` rows, keyset-paginated as today |
| **Sessions** | staff | `page_viewed` grouped into visits, with the page trail: replaces the sessionizing over `access_events` |
| **Member timeline** | staff | everything with this `subject_member_id` |
| **Funnels / Explore / Least-clicked** | everyone | what exists today, reading the same table |
| **Record history** | staff | `audit_log` for a record, linked to the events with the same correlation id |

`member_activities` stops being a store for the *append-only* sources (logins, writing progress, outreach, commitments): it becomes a projection of business events, reprocessable like the Slack and attendance rows already are, replacing the "best-effort insert alongside the primary action" pattern. Slack and prickle attendance keep their own reprocessing pipelines.

### What stays separate, and why

`audit_log` is not merged into the event log. It is the data-change journal: database triggers capture the old and new value of every changed field for any write path (API routes, cron, the SQL editor), it **folds** repeated changes made by one transaction into a single row (first old value, last new value, dropped if they net out: a sync that flips a status and flips it back writes nothing), and it powers the per-record change-history dialog. An application-level event log would do all three worse. The two are **linked** by the correlation id instead, which gets the "one story" without losing what the audit log is good at.

`video_watch_segments` stays for now: it is interval data with its own aggregation (heatmaps, engagement), and other work is building on it. Its watch ranges can be exposed through a view next to the events (or, later, re-expressed as `video_segment_watched` events); not in the first phases.

## Retention, erasure and soft delete

**This is engineering's reading of the regulators' published guidance, not legal advice.** The numbers below are proposals backed by the sources in [Sources](#sources-and-what-was-not-verified); counsel should confirm them before they are published to members.

### What the guidance actually requires

- **No fixed period; you must justify one.** The ICO: the UK GDPR "does not set specific time limits for different types of data"; "it is up to you to justify this, based on your purposes", with a retention policy that sets "standard retention periods wherever possible", and erase *or anonymise* when identification is no longer needed (pseudonymised data usually still counts as identifiable). The same applies under the EU GDPR's storage-limitation principle.
- **Regulator benchmarks that exist** (recommendations, not statutory limits):
  - CNIL on access/audit logs: **six months to one year**; up to **three years** for internal-control logging only if the longer period is documented as necessary and proportionate.
  - CNIL on audience measurement that is exempt from consent: tracker lifetime about **13 months** (not extended on each visit), collected data kept at most **25 months**.
  - ICO on the UK's statistical-purposes exception: individual-level data kept "only as long as you need it" to aggregate it (daily aggregation as a starting point), and the exception "does not allow you to monitor or track individual visitors", for example by "connecting a visitor ID to their site activity". Our interaction events are per-member, so they sit *outside* that exception and rely on consent, which is how they already work.
- **Erasure (GDPR Art. 17)** must happen without undue delay when data is no longer necessary for its purposes, consent is withdrawn, or an objection is upheld; the exceptions include legal obligations, legal claims, and archiving or statistical purposes where erasure would seriously impair them.
- **California.** The statutory test for the CCPA/CPRA (annual revenue over about $26.6M, or data on 100,000+ consumers or households, or 50%+ of revenue from selling or sharing data) probably does not reach this organisation. The principle is still worth following: say how long each category is kept (or the criteria), and keep it no longer than reasonably necessary for the disclosed purpose. About 90% of the membership is in the US.

### Lawful basis per event type (replaces "consent vs operational")

Each event type in the catalog carries a **basis** and an **objectable** flag:

| Basis | What it covers | Consent needed? | Can a member opt out? |
|---|---|---|---|
| `contract` | the product's own record of what happened *in the service the member signed up for*: what `audit_log`, `member_activities`, in-app notifications and the check-in/commitment tables already record (a project created, a commitment cancelled, a notification sent, a login) | No | No: it is the service's data, and it is also what the member sees and relies on. Erasure and access still apply (below) |
| `legitimate_interest` | using those same facts, or similar ones, to understand how the product is used (feature usage, funnels, success rates) | No, after a documented balancing test | **Yes, on request** (Art. 21 right to object; the controller must stop unless it shows compelling grounds). Honour it by leaving that member out of analytics views, while their operational records stay |
| `consent` | behavioural tracking from the browser: clicks, impressions, search and filter use, validation friction, the visit and correlation cookies | Yes, where required (EU, EEA, UK; today's banner and `hub_sid` rule) | Yes: declining or withdrawing stops it |

**On "essential": confirmed for the narrow class, not for everything labelled "business".** Two separate legal questions are being merged under that word:

1. *Does the ePrivacy rule (EU Art. 5(3), UK PECR regulation 6) require consent?* It applies when information is **stored on, or read from, the member's device.** A server recording that a project was created reads nothing from the device; it is the request the member made. So business events recorded by the server don't need consent *for that reason.* But the cookies we use to link a click to its outcome (`hub_sid`, `hub_cid`) are device storage, and they are **not** "strictly necessary" (the ICO tests that from the user's side: without it the service "couldn't be provided on a technical level"; ours work without them). They stay consent-gated. The result: business events are always recorded; they just aren't linked to clicks for members who haven't agreed.
2. *Does the GDPR require consent to process the data?* No, if there is another basis: `contract` for the service's own records, `legitimate_interest` for usage analysis. Only the first is truly un-opt-out-able; the second carries the right to object.

So the design does not claim business events "may not be opted out of". It records the `contract` class unconditionally, honours objections for the `legitimate_interest` class, and keeps `consent` for browser tracking. All three must be disclosed on the member-facing privacy page (`/privacy`, behind the `message_privacy` flag), including the retention periods.

### Proposed retention schedule

| Data | Basis | Identifiable for | Then | Why |
|---|---|---|---|---|
| Interaction events (clicks, impressions, search, filters) | consent | **13 months** | row deleted; aggregate counts kept | year-over-year comparison needs about a year; matches CNIL's 13-month tracker and sits well inside its 25-month data ceiling |
| Product friction (`*_failed`, validation) | consent | **13 months** | row deleted; aggregates kept | same purpose and window |
| Engineering (`*_error`) | legitimate interest | **90 days** | deleted | they exist to debug; the stack trace lives in Sentry and a fix lands within weeks |
| Business events (`contract` class) | contract | **while the member's record exists, then 3 years after their last activity** | anonymised (identity removed, the fact kept) | the app already keeps former members' history so that returning members, resubscription detection and disputes work; CNIL's three-year ceiling for internal-control records is the benchmark for the outer bound. **Needs your confirmation: the current system keeps former members forever, and this is the first time a limit is proposed.** |
| Business events (`legitimate_interest` class) | legitimate interest | **13 months** | row deleted; aggregates kept | analytics, not records |
| Access and login records (who signed in, when) | legitimate interest (security) | **12 months** | deleted | CNIL's "six months to one year" for access logs; the top of the range because a year of sign-in history is useful for investigating account problems |
| **Raw IP address and user agent** | legitimate interest (security, abuse) | **90 days** | IP truncated (last octet or lower 64 bits) or nulled; user agent nulled | the most sensitive columns, needed only to investigate abuse close to the event; below CNIL's six-month floor deliberately, since the place is derived once at write time and the raw IP adds nothing after that |
| Derived place (country, region, city) | follows the event it is on | with its event | with its event | coarse (the ICO lists coarse city or region as acceptable statistical detail) |
| Soft-deleted rows | | **30 days** | physically purged | recoverable from a mistake, then really gone |
| Backups | | provider's backup window | rolls off | erasure completes when backups expire; say so in the privacy notice |
| `hub_sid` visit cookie | consent | 30 minutes idle (already) | | |
| `hub_cid` correlation cookie | consent | **60 seconds** (it only has to survive from the click to the request it makes) | | |

Where the current system differs: `access_events` keeps raw IPs, user agents and places indefinitely and nothing prunes it (recorded in `docs/TODO.md` as "the owner's call, for now"), `video_watch_segments` and `member_activities` have no limit, and `audit_log` is kept forever by design. The first two are the exposures; the schedule above can be applied to them **before** the event log exists (phase 0 below).

### Mechanism

- **Soft delete first.** Every row has `deleted_at`; views read live rows only.
- **Anonymise rather than erase when a person leaves.** `anonymise_user_events(user_id)` nulls the actor and subject columns and blanks identifying context (user agent, IP, place, GA id) in one pass. Facts about the community stay as anonymous rows; `consent`-basis rows are soft-deleted outright.
- **A scheduled job enforces the table above** (soft-delete when a row passes its window, purge 30 days later), reading each event type's window from the catalog, so a new event can't be added without saying how long it lives.
- **Objection and withdrawal** are handled the same way: stop recording for that member (a per-member flag the receiver and `createNotifier` check), and apply `anonymise_user_events` to the classes that no longer have a basis.
- **`audit_log` keeps its rule** (history outlives deleted users) under the same review: its entries name records and fields, so they should be anonymised along with the member record when that happens.

## Access

One table, with the restrictions pushed into RLS and grants, as the repo already does for Slack message content:

- Members can insert their own events (today's policy) and read their own non-sensitive ones.
- Staff read through views. The sensitive columns (IP, place, user agent, GA client id) are excluded from the views' column lists and from `SELECT` grants on the table, like `bronze.slack_messages_meta`; a break-glass view (admin-only, itself logged) can read them.
- `events` itself is not readable by `authenticated` apart from a member's own rows; every audience reads a `security_invoker` view, so RLS still decides.
- Soft-deleted rows are invisible to every view.

## Migration plan

Each phase ships on its own, keeps everything working, and can be stopped after any of them.

0. **Apply the retention schedule to what exists, now.** A scheduled job that nulls raw IPs and user agents on `access_events` after 90 days and deletes access rows after 12 months, plus `analytics_events` at 13 months (identifiable) and the notice update on `/privacy`. It needs no new design and removes today's open-ended exposure; the event log later reuses the same job.

1. **Generalise the table.** Rename `analytics_events` to `events` behind a compatibility view; add the new columns (`name` stays the event, plus `correlation_id`, `actor_kind`, `subject_member_id`, `entity_type`, `entity_id`, `deleted_at`); drop the cascade FK in favour of `anonymise_user_events`; add the `event_catalog` table and the registry-to-catalog check. No behavior change.
2. **Correlation.** Browser generates and sets `hub_cid`; `lib/supabase/server.ts` forwards `X-Correlation-Id`; `current_correlation_id()` and `audit_log.correlation_id`; server events carry it.
3. **Business, failed and error events.** Replace `action_completed` with declared Noun Verb triples; add `form_validation_failed` for client-side rejection; map the 41 actions; add the Business facts, Product friction and Engineering views. Update the Feature Usage tables to read them.
4. **Page views, logins and sessions.** Record `page_viewed` and `login` in `events` (the network details once per sign-in, in restricted columns); port the sessionizing function and the activity feed's session rows to read `events`; **stop the proxy's per-request writes** (see Risks: decided) and retire `access_events` once parity is checked.
5. **Member activities as a projection.** Logins, writing progress, outreach and commitments become projections of business events instead of best-effort inserts; engagement scoring is checked against the old numbers before the inserts are removed.
6. **Later, if wanted:** video watch ranges as events or a view; partitioning `events` by month if volume calls for it (the activity-log doc already sets that bar at tens of millions of rows).

## Risks and open questions

- **Volume.** Interaction events (clicks, impressions) dwarf business events. At the current size one table is fine; the retention windows and a later monthly partition are the levers.
- **Proxy logging: decided.** The proxy currently writes one `access_events` row for *every* signed-in request (page loads, API calls, server-action posts, the header's 30-second On air poll), each with the path, user agent, raw IP and place. The only reason is to know a visit is still alive when the member is doing things that aren't page views (the browser reports page views separately). It costs a database write per request and puts the most sensitive columns on the highest-volume rows. Decision: **stop writing a row per request.** Record the network details *once per sign-in* (a `login` event), take page views from `page_viewed`, and let any event (business, interaction, `page_viewed`) extend a visit, as today's 30-minute-gap rule already does. Supabase also keeps its own auth-session record (created, refreshed, user agent, IP) that can fill any gap. Phase 4 below is where this lands; until then nothing changes.
- **IP and place.** They are the most sensitive columns in the log. Whether to keep them at all, and for how long, is the first question for counsel.
- **Server-render navigations** read the correlation cookie from the *previous* interaction; this is fine for correlation but means a page view's `caused_by` can be the previous click.
- **Naming drift.** The catalog check is what stops a hundred slightly different event names; it has to fail CI, not warn.
- **Rewriting the 41 actions** is mechanical (the wrapper already exists), but the Feature Usage tables, the Explore page and the explorer's saved URLs all key on `action_completed`; phase 3 updates them together.

## Out of scope

Replacing `audit_log`, the Silver pipelines for Slack and attendance, `prickle_attendance`'s own table, Sentry, and any change to what is shown to members.

## Sources and what was not verified

Read directly:

- ICO, [Principle (e): Storage limitation](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/data-protection-principles/a-guide-to-the-data-protection-principles/storage-limitation/): no fixed periods, justify, erase or anonymise, retention schedules.
- ICO, [Storage and access technologies: what are the exceptions?](https://ico.org.uk/for-organisations/direct-marketing-and-privacy-and-electronic-communications/guidance-on-the-use-of-storage-and-access-technologies/what-are-the-exceptions/): the statistical-purposes exception (aggregate, "does not allow you to monitor or track individual visitors", individual-level data only as long as needed) and the strictly-necessary exception (judged from the user's side).
- CNIL, [recommendation on logging](https://www.cnil.fr/la-cnil-publie-une-recommandation-relative-aux-mesures-de-journalisation) (Nov 2021): six months to one year; up to three years for internal control if justified and documented. The page does not mention IP addresses.
- CNIL, [audience-measurement tools exempt from consent](https://www.cnil.fr/fr/cookies-et-autres-traceurs/regles/cookies-solutions-pour-les-outils-de-mesure-daudience): 13-month tracker lifetime, 25-month data limit (stated as recommendations).
- GDPR [Article 17](https://gdpr-info.eu/art-17-gdpr/) (erasure and its exceptions) and [Article 21](https://gdpr-info.eu/art-21-gdpr/) (right to object to legitimate-interest processing).
