## ship-via-pr

Finished work lands through a pull request. Nothing goes to `main` directly, admins included (the `main` ruleset in `github-repo-config.yml` forbids it), and `pr-watch.md` takes over once the PR exists.

1. **Work in your own worktree on a branch**, never in the main checkout (other sessions leave work in progress there). Copy `.env.local` per `worktree-setup.md`.
2. **Before opening the PR**: `pnpm typecheck`, the tests for what you changed (`tests-with-every-change.md`), and `pnpm check:migrations` if you added a migration. The pre-commit hook also runs a production build.
3. **Commit with explicit paths** (`git add <files>`), not `git commit -a`. Don't commit one-off data scripts, exports or anything with member data; the repo is public.
4. **Open the PR** with a description that says what changed and why, and keep it accurate as it changes (`pr-feedback.md`). Auto-merge is enabled on every non-draft PR by CI, so open a draft if the change shouldn't merge on green.
5. **Split big changes** into several smaller PRs that build on each other and merge in order, rather than one large one.
6. **Don't ask whether to open a PR.** "Commit/PR" is the default ending of a task. Do ask before anything the ruleset can't catch: force-pushing a shared branch, deleting branches or worktrees you didn't create, or running anything against production.
7. **A merge isn't done until its `main` run is green.** Merging a PR deploys nothing: it triggers the CI pipeline on `main`, which re-runs the checks on the merged commit, applies any new migrations (`push-migrations`), and only then deploys the code (`deploy`). That run can fail even when the PR's checks passed (two PRs that each passed alone can collide; migrations or config can be rejected by production), and a failure means your change was not promoted. So watch it for every PR, not just ones with migrations: find the run with `gh run list --branch main --limit 5`, then `gh run watch <run-id> --exit-status` in the background like `pr-watch.md`. Don't pipe it, and when it exits read the run's `conclusion` (`gh run view <run-id> --json conclusion`); the exit code alone has been wrong. A `cancelled` run is not a pass: `main` runs one at a time and a run still waiting is cancelled when a newer merge lands, so when merges come in close together yours is replaced. Then watch the newer run, which contains your commit, and your change counts as promoted only when that run succeeds. If it fails, read the log (`gh run view <run-id> --log-failed`) and fix forward with a new PR, or tell the user if it isn't yours. Report the outcome ("PR #N merged and deployed" or "PR #N merged but the main run failed at <step>"). A docs-only change (`docs-only-changes.md`) skips migrations and deploy, so its `main` run is quick and ends with those jobs skipped; say "merged, docs only, nothing deployed".
8. **After the main run succeeds**, clean up as `branch-hygiene.md` says: the remote branch is already gone (GitHub deletes it on merge), run `pnpm branches:prune --apply` for the local ones, and put any follow-up work on a new branch from `origin/main`, never on the merged one.

If the user says "merge to main" or "push to main", remind them `main` is protected and open the PR instead; they can use "Merge without waiting for requirements" on it if they really need to bypass checks.
