### Admin Route Protection

**RULE**: Access to the staff area is by permission (`src/lib/permissions.ts`, `docs/architecture/PERMISSIONS.md`), never "admin or not". Every `src/app/(admin)/admin/**/page.tsx` starts with `await requirePermission("<permission>")`, every server action in the staff area starts with `const auth = await requireActionPermission("<permission>"); if (!auth.ok) return { error: auth.error };`, and every staff route handler with `requireApiPermission(request, "<permission>")` (all from `src/lib/admin-auth.ts` and `src/lib/supabase/api-auth.ts`). The permission is the operation the code does (`pages.edit`, `outreach.manage`), and the roles are named bundles of them (`ROLE_PERMISSIONS`: `admin`, `assistant`, `community_manager`, `conversion_specialist`). Don't hand-roll `user_profiles` role checks or `role === "admin"` comparisons, don't list roles in a component (ask `can(actor, permission)`), and don't rely on the admin layout or the page to protect an action. `tests/lib/permission-guards.test.ts` scans every page, action and staff route for its guard and fails on a missing or unknown permission; `tests/lib/permissions.test.ts` writes out every role against every permission.

**The Roles page** (`/admin/roles`, `roles.read`) lists every permission and role from the registry, read-only; a new role needs a `ROLE_DESCRIPTIONS` entry and a withheld permission an `ASSISTANT_WITHHELD_REASONS` one.

**Adding one** (what to decide first, the standard verbs and names: `permissions-for-resources.md`): a permission is an entry in `PERMISSIONS`, a guard that uses it, and a decision for each role in `ROLE_PERMISSIONS` (and in the table in `tests/lib/permissions.test.ts`). A new admin page is also a line in `ADMIN_PAGE_PERMISSIONS` (`src/lib/admin-paths.ts`), which the proxy and the sidebar read: a page nobody lists is open only to the admin and the assistant. A role's own client reads tables through RLS, so a role that gets a page also gets policies (`is_<role>()` beside `is_admin()`, never a widened `is_admin()`).

Layers, per the Next.js auth guide (`node_modules/next/dist/docs/01-app/02-guides/authentication.md`):
- **Optimistic, in `src/proxy.ts`** (`src/lib/supabase/middleware.ts`): `/admin` and `/admin/*` (not `/administrivia`; see `isAdminPath` in `src/lib/admin-paths.ts`) → anonymous to `/login`, a signed-in user whose role doesn't open the path (`mayOpenAdminPath`: the page's permission from `ADMIN_PAGE_PERMISSIONS`) to `/no-access`. Reuses the user the proxy already loads, and reads the role from the `app_role` claim of the access token its `getUser()` just verified. The proxy never reads `user_profiles`. The claim is added by the Supabase custom access token hook (`public.custom_access_token_hook`, migration `20260926000900`, enabled by `[auth.hook.custom_access_token]` in `supabase/config.toml`): the role string, or JSON `null` when there's no `user_profiles` row. Anything that isn't a staff role, including a missing claim (hook not enabled, or its lookup failed), goes to `/no-access`.
- **Secure, next to the data**: `requirePermission("staff.access")` in `src/app/(admin)/layout.tsx` and `requirePermission("<permission>")` in every admin page (memoized with `cache()`, so layout + page share one role lookup), same redirects. Pages repeat it because layouts don't re-run on client navigation and don't stop a page segment from rendering. It reads `user_profiles.role` on purpose, and so do the action and route guards: **never authorize from the `app_role` claim.** A token keeps the role it was minted with until it refreshes, up to `auth.jwt_expiry` (3600s, i.e. up to 1 hour). A demoted admin keeps an `admin` claim for up to that long, so the proxy lets them past the pre-filter and the page-level check stops them. A newly promoted staff member gets sent to `/no-access` by the proxy until their token refreshes (up to 1 hour, or at once if they sign out and back in).
- **Server actions** are directly callable POST endpoints, so each staff action checks for itself with `requireActionPermission("<permission>")` (returns `{ ok: false, error }` rather than redirecting, with the effective `role` for finer checks; `startSudo` throws it). `tests/lib/permission-guards.test.ts` fails if an action in a `"use server"` file under `src/app/(admin)/` (or `src/app/actions/sudo.ts` and `record-history.ts`) or a route in a staff-only API folder is missing its check; list deliberate exceptions there with a reason.

**Roles** (`ROLE_PERMISSIONS`): `admin` holds every permission; `assistant` is the admin's list less `ASSISTANT_WITHHELD` (today only `care.member_activity.read`, the privacy page's "never an assistant"), and an assistant's RLS is still only what a plain user gets until `is_admin()` is extended on purpose (`docs/TODO.md`, "Back the assistant role in the database"). **Community manager (`user_profiles.role = 'community_manager'`)**: a member who is a semi-volunteer (paid in comps, no contract); a fixed, mostly read-only set: the Calendar View, the member list and a member's page, At-Risk, a prickle's page, Community Stats, Slack Engagement, Resubscriptions, and Hedgie Care (`care.read`, `care.write`). Finer controls inside those pages are permissions too (`STAFF_FEATURES` in `src/lib/staff-access.ts`, a subset of the registry: `staffCan(role, "care.write")` is `can({ role }, "care.write")`), hidden until granted. `member.activity_tab_limited` is the member page's Activity tab with only the member's own activity (`member_activities` rows: no audit entries, page visits or staff notes, no central log link), enforced in the database too (`get_activity_feed` and `count_activity_feed` serve a community manager only with a member and only the `activity` kind, `20270817000000`; `docs/architecture/ACTIVITY_AND_AUDIT_LOG.md`, "The community manager's Activity tab"). **Conversion specialist (`conversion_specialist`)**: marketing; landing pages (read, edit, publish; not delete), outreach, browsing the media library, and the reserved email, scheduled email, announcements and aggregate cohort permissions; **no** members area, changelog or export (`20270930000000`: `is_conversion_specialist()` and policies on the landing page, site template, outreach tables and on `members` rows with status `lead` or `cancelled` only; `supabase/tests/database/conversion_specialist_role.test.sql`). Opt-in is the rule for every new role: pages, permissions and DB tables each start at none. Data is guarded by RLS, not by the page: policies use `is_community_manager()` / `is_conversion_specialist()`; never widen `is_admin()` for them.

**Preview as a role**: an admin can look at the staff area as any staff role below the admin (user menu → "Preview as...", pick a role in the dialog, "Start preview"; exit from the banner). A `staff_preview_role` cookie (`src/lib/staff-preview.ts`) lowers the *effective* role for a real admin only (anyone else's cookie is ignored): the proxy, `requirePermission()` (returns `role` and `realRole`), `requireActionPermission()` and the sidebar then treat them as that role, so a page the role may not open sends them to the role's home (`staffHome`) and an action it may not do is refused. API routes use the real role (preview is not applied). It is UI and routing only: data is still read with the admin's RLS access, so test a database limit with a real account of that role. Not sudo (sudo changes the member acted as, never the staff role). A new role is previewable automatically (`PREVIEWABLE_ROLES` is every staff role below the admin).

**Staff-less users go to `/no-access`, never a member page**: member pages send anyone without a member record to `/admin`, so redirecting non-admins back to `/dashboard` would loop. `src/app/no-access/page.tsx` sits outside both route groups and must never redirect a signed-in user.

**Second sign-in step (TOTP, `docs/trust/STAFF_MFA.md`, `src/lib/staff-mfa.ts`)**: all four guards (the proxy, `requirePermission`, `requireActionPermission`, and `requireApiPermission` for API routes) hold staff to aal2 when their account has a verified factor, and, from `staffMfaRequiredFrom` in `config/app.ts` (unset = off), to having one. Pages redirect through the `staffMfa` gate to `/mfa` and back; actions return `MFA_REQUIRED_ERROR`; `/mfa` sits outside both route groups like `/no-access`. The proxy reads the token's `aal` claim and `user.factors` from the `getUser()` it already ran; the page and action guards use `src/lib/staff-mfa.server.ts`. A new admin guard or entry point needs the same check.

Sudo doesn't affect any of these checks: the sudo cookie changes the effective *member*, not the signed-in admin. API routes use `requireApiPermission` (`src/lib/supabase/api-auth.ts`) instead.

The hook is tested by `supabase/tests/database/custom_access_token_hook.test.sql` (pgTAP, rolled back; `pnpm test:pgtap`, which CI also runs). Because the proxy has no fallback, **no one reaches `/admin` on a project until the hook is enabled there** (and they've signed in again or their token has refreshed). See "Supabase config as code" below for how it gets enabled.
