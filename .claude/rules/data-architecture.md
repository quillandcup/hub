## Data Architecture

**Bronze Layer** (raw imports from external systems):
- `calendar_events`, `zoom_attendees`, `zoom_meetings`, `kajabi_members`, `subscription_history`, `slack_messages`, `slack_reactions`, `slack_channels` (channels and, with `is_mpim`, group DMs the bot is in), `slack_users`, `slack_channel_members` (who is in each conversation now; `left_at` is when they last left), `slack_channel_member_events` (append-only history of joins and leaves, from Slack's join/leave notices, webhook events and the member list; read it as periods through the `slack_channel_membership_periods` view), `slack_custom_emoji` (`deleted_at` soft delete), `slack_files` (files on messages and the path of our copy in the private `slack-files` bucket; service role only), `resend_events` (email events from Resend: sent, delivered, opened, clicked, bounced...; append-only, service role only, written by `/api/webhooks/resend` and the nightly `/api/reconcile/email`; the member timeline rows, `member_activities` with source `resend`, are rebuilt from it one email at a time; `ResendEventRepository`; see `docs/EMAIL_TIMELINE.md`)
- `stripe_invoices` and `stripe_charges` (who was billed what and when: amounts in cents, status, period, paid date, the failure code; no raw record, card details or customer email or name; service role only; `BillingRepository`; pull import in the manual Stripe import and the nightly `/api/reconcile/stripe-billing`, upsert on Stripe's id; see `lib/stripe/billing-import.ts`; the same nightly job and manual import also fill `stripe_customers`, `stripe_products` and `stripe_subscriptions` first, through `lib/stripe/core-import.ts`: upsert only, nothing removed, and each step runs even if the other fails)
- **Slack content is service role only**: `slack_messages` (text, files, raw payload) and `slack_files` can't be read by admins. Admin pages read `bronze.slack_messages_meta` (who, where, when, thread shape, `has_files`; no content; a `security_invoker` view over column grants on `slack_messages`, so its metadata columns need a `GRANT SELECT (col)` when added); code that needs the text runs server-side with the service role after checking the caller. `raw_payload` on `slack_users`, `slack_channels`, `slack_reactions` and `slack_channel_member_events` is hidden the same way with column grants, so `select("*")` on those fails for a signed-in user, and a column added to one of them needs its own `GRANT SELECT (col) ... TO authenticated` (`slack_content_privacy.test.sql` fails if one is missed).
- **Pattern**: UPSERT on natural keys for idempotency

**Local Layer** (operational data owned by this app):
- `member_hiatus_history`, `member_name_aliases`, `ignored_zoom_names`, `restricted_slack_channels` (private Slack channels whose messages staff can't read; a row = restricted, every change audited and shown in the Activity Log's Privacy view; restricting clears the text already in `member_activities` and rebuilds leave it out; managed at `/admin/data/slack-channels`), `chat_channels`, `chat_channel_members`, `chat_messages`, `chat_message_contents`, `chat_reactions` (the read-only Hub mirror of bridged Slack conversations, projected from Bronze by `/api/process/chat`; ids are stable across reprocessing; content in its own table so RLS can gate it; service role writes; see `docs/SLACK_BRIDGED_CHAT.md`), `prickle_types`, `staff`, `calendar_feed_tokens` (secret per-member token for the subscribable `/api/calendar/feed/<token>.ics` feed), `calendar_feed_items` (prickles, weekly slots and events a member added to that feed by hand), `member_ask_me_about` (profile "Ask me about…" topics), `member_notes` (a member's private notes to self about another member; author-only RLS with no admin access, hidden in sudo), `prickle_checkins` (a member's check-in for a prickle: mood before and after on two labeled 1-5 scales, optionally the feeling named on the Feeling Wheel (Willcox, 1982), their intention, and whether they got what they came for; see `docs/CHECKINS.md`; readable by the member and admins, writable only by the member, read-only in sudo; option keys in `lib/prickle-checkins.ts`), `prickle_checkin_dismissals` and `prickle_checkout_dismissals` (prickles whose check-in offer or check-out a member dismissed: hidden from the dashboard, the search palette and upcoming prickles, and no Slack DM; the check-out one holds the dashboard's "What did you write?" dismissals), `notification_preferences` (a member's per-kind, per-channel overrides of the notification defaults in `lib/notifications/registry.ts`; no row = default; member-writable, admin-readable, read-only in sudo), `in_app_notifications` (what the in-app channel sent a member, kept for good: the `/notifications` inbox table, the latest few under the header bell, and a banner while unread and still time-sensitive (`OutboundMessage.timeSensitiveUntil`, `banner_until`); read when opened, its banner dismissed, "Mark all as read", or the feature resolves it with `resolveInAppNotifications`; server-written, member and admin readable, the member can only set `read_at`; hidden in sudo), `member_reminder_log` (reminders sent: intro in #start-here, prickle reminders; backoff and dedup for `/api/internal/member-reminders`, see `lib/member-reminders.ts`; service role only), `member_onboarding` (a member's Getting started tour: steps marked done by hand, dismissed/completed; other steps count as done from the member's own data, see `lib/onboarding.ts`; hidden and read-only in sudo), `push_subscriptions` (browsers a member turned Browser notifications on for: Web Push endpoint and keys, so service role only; `deleted_at` when turned off or the push service says it's gone; see `lib/channels/web-push.ts`), `media_assets` (the media library catalog, `media_` ids; `kind` is `image` today, videos and files later: an uploaded image, the original kept untouched in the private `media` bucket, with title, alt text, tags, focal point, owner and `is_public`; sized copies are derived on request by `lib/media/` and served at `/api/media/<id>/<preset>`; staff manage the shared library, a member their own; through `MediaRepository`; see `docs/MEDIA_LIBRARY.md`), `mentorships` (the Big Sister program: every new member, however they arrived, matched with a big sister for 30 days; `started_on` and `kind` come from the sign-up in `lib/arrivals.ts`, never typed; `outcome_note` is the big sister's reason a trial didn't continue, written through `set_mentorship_note`; admin only, since it names new members; whether a trial converted is derived from membership history in `lib/mentorship.ts`, never stored; the Big Sister badge counts them through `mentorship_counts()`, members read their own side through `my_mentorships()`), `big_sister_volunteers` (members who volunteer to be a big sister, soft-deleted with `deleted_at`; self-serve under the hosting eligibility rule; see `docs/BIG_SISTERS.md`), `outreach_prospects` (Instagram accounts that might be ideal Hedgies, with a rules-based fit score and a review status; admin only; `ProspectRepository`; see `docs/PROSPECTING.md`), `slack_identities` (Slack user id → Hub account allowed to sign in from Slack; server-written only) and `slack_sign_in_tokens` (hashed single-use button tokens and codes the Slack app hands out); see `lib/slack-sign-in.ts`, both service role only
- `hub_sessions` (the schedule of an event made in the Hub, which has no Google Calendar item: title, description, host, guest speaker, location, start and end; written through `HubSessionRepository`, whose `create`/`update` project it into a prickle (source `hub`, `prickles.hub_session_id`) that the event stands on; temporary, until events are written back to Google Calendar). A `community_events` row (an "event"; the table is not called `events`, which invites confusion with analytics events) holds only what the calendar and prickles have no place for (audience, registration, photos, focus...) and stands on exactly one prickle (`community_events.prickle_id`, NOT NULL, unique); its title, description, location, host, speakers and times are read from the `community_event_details` view (`EventDetail`, `lib/data/events.ts`), never stored on the event (see `docs/CALENDAR_EVENTS.md`).
- **Pattern**: Normal CRUD operations (INSERT, UPDATE, DELETE)
- **NOT reprocessed** - these tables ARE the source of truth

**Silver Layer** (canonical state, computed from Bronze + Local):
- `members`, `prickles`, `attendance`, `member_activities`
- **Pattern**: `prickles` UPSERT on their source key (`calendar_event_id` for calendar prickles, `zoom_meeting_uuid` and start time for PUPs: a PUP whose end moves keeps its id, one whose start moves is a new prickle) and DELETE orphans whose source is gone, so **prickle ids — and `/prickles/<id>` URLs — are stable** across reprocessing (safe to reference; add `ON DELETE CASCADE`/`SET NULL` for the rare real delete); DELETE + INSERT for `attendance`; `members` uses a custom atomic upsert (see below) to preserve historical attendance via the `ON DELETE CASCADE` FK; `member_activities` uses two patterns depending on source — DELETE+INSERT by `source` + date range for reprocessable mirrors (Slack, one week per `reprocess_slack_activities_atomic` call because rewriting 90 days in one statement ran past the 8s statement timeout; prickle attendance, mirrored atomically inside `reprocess_prickle_attendance_atomic`), and a best-effort single insert alongside the primary action for append-only sources (writing-progress, outreach touches, logins) that are never reprocessed. See `docs/ACTIVITY_AND_AUDIT_LOG.md`.

**Gold Layer** (aggregated views):
- Currently computed on-demand in dashboard queries
